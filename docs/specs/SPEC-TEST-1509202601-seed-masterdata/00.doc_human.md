# SPEC-TEST-1509202601 — Seed Masterdata (modo developer)

**Documento:** Explicación general · **Fase:** ✅ aprobada (2026-09-17).

## ¿Qué problema resuelve?

Mientras se prueban cambios, un desarrollador necesita frecuentemente
vaciar y volver a cargar datos de ejemplo en sus catálogos de prueba,
para poder rearmar un escenario desde cero. Antes de esta herramienta,
eso se hacía a mano cada vez — un trabajo lento, repetitivo, y que
además consumía tiempo (y tokens, cuando lo hacía la IA) sin agregar
valor real al trabajo de fondo.

Esta spec agrega una herramienta de terminal, exclusiva para el modo
de desarrollo local, que le permite a un desarrollador reiniciar y
repoblar sus catálogos de prueba sin depender de nadie más.

## ¿Cómo funciona, a grandes rasgos?

La herramienta trabaja en dos pasos, que se pueden usar por separado o
encadenados en una sola operación:

1. **Vaciar**: borra por completo los datos de uno o varios catálogos
   de prueba — nunca su configuración (sus campos, su motor de
   estados siguen intactos, listos para recibir datos nuevos). El
   sistema calcula solo el orden correcto de borrado, respetando qué
   catálogo depende de cuál, para que ninguno se rechace por seguir
   siendo referenciado por otro que todavía no se vació — pero el
   desarrollador puede pedir un orden distinto si lo prefiere. Antes
   de borrar, siempre muestra qué va a hacer y pide confirmación.

2. **Cargar**: puebla esos catálogos con datos de ejemplo, descritos
   en un archivo que el propio desarrollador edita con su editor de
   siempre (nunca desde una pantalla de la aplicación). Cada registro
   se crea pasando por el mismo camino real que usaría un usuario
   final o la aplicación externa (Flutter) al dar de alta algo — con
   sus mismas reglas de negocio, numeración interna y asignación
   automática de identificadores — nunca insertando datos directo en
   la base, para que el escenario de prueba sea siempre representativo
   de un caso real. Si algo falla a mitad de camino, no queda nada a
   medio cargar: se deshace todo lo de esa corrida, sin excepción.

Ambos pasos se pueden encadenar en un solo comando, para reiniciar y
repoblar un catálogo de un saque.

## Historia

Durante la construcción se encontró un comportamiento real de Postgres
que no se había anticipado: el mecanismo más directo para vaciar una
tabla de una sola vez lo rechaza si CUALQUIER otra tabla de toda la
base tiene una referencia hacia ella — sin importar el orden en que se
intente, y aunque esa otra tabla no tenga nada que ver con el
catálogo que se está vaciando. La herramienta se corrigió para usar un
mecanismo de borrado más gradual, que sí respeta el orden calculado.

## ¿Quién usa esta funcionalidad?

Exclusivamente desarrolladores del equipo, desde su entorno local de
desarrollo — nunca corre en un ambiente desplegado real. No es una
funcionalidad para gente de ADN, soporte, ni para ningún usuario final.

## Lo que esta spec NO hace

Nunca toca catálogos que no sean de prueba (los de negocio real,
usuarios, roles, empresas y similares quedan siempre afuera). No tiene
ninguna pantalla propia: el archivo de datos de ejemplo se edita a
mano, con el editor de código de siempre. Tampoco corre en ningún
ambiente que no sea el desarrollo local de cada desarrollador.
