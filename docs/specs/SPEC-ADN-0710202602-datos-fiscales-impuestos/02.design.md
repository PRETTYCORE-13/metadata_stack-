## 5. Servicio `pty_sql_fiscal_impuestos_venta` (R16-R26)

Nav `/fiscal/impuestos_venta`, tope 1000 renglones.

| Parámetro | Tipo | Obligatorio |
|---|---|---|
| `direccion_id` | entero | sí |
| `fecha` | fecha | no (hoy en hora de México) |
| `materiales` | lista_enteros | sí |
| `unidades` | lista_enteros | no (0 o ausente = unidad de venta) |
| `cantidades` | lista_decimales | sí |
| `montos` | lista_decimales | sí |

Salida, un renglón por posición recibida (R21):

| Columna | Contenido |
|---|---|
| `posicion`, `material_id`, `unidad_id` | Identifican el renglón |
| `estado` | `ok`, `direccion_invalida`, `sin_cp_entrega`, `renglon_incompleto`, `material_invalido`, `unidad_no_valida`, `sin_datos_fiscales`, `sin_litros`, `sin_tasa_ieps`, `sin_tasa_iva` (primero que aplique, en ese orden) |
| `zona` | `general` o `frontera` |
| `motivo_general` | Si la zona es `general`: lista de condiciones de R12 que fallaron (`cp_entrega`, `cp_expedicion`, `padron`, `clave_producto`) (R12.3) |
| `desglosa_ieps` | Del cliente (R15) |
| `litros` | Litros por unidad base × factor de la unidad × cantidad |
| `ieps_tipo_id`, `ieps_forma`, `ieps_tasa_id`, `ieps_base`, `ieps_valor`, `ieps_importe` | Foto del IEPS (R23) |
| `iva_tipo_id`, `iva_forma`, `iva_tasa_id`, `iva_base`, `iva_valor`, `iva_importe` | Foto del IVA (R23) |
| `branch_id`, `sales_unit_id` | Alcance (igual que el servicio de precio) |

Cálculo por renglón (R19, R24):

```
ieps_importe = porcentaje  → round(monto × valor / 100, 6)
               cuota_litro → round(litros × valor, 6)
               ninguno     → 0
iva_base     = monto + ieps_importe
iva_importe  = porcentaje  → round(iva_base × valor / 100, 6)
               exento      → 0
```

Elección de tasa (R2, R20): `LATERAL` por renglón y tipo, tasas vivas y
activas con `vigente_desde <= fecha` y (`vigente_hasta` vacío o
`>= fecha`), `zona IN ('general', <zona del renglón>)`, ordenadas con la
de la zona del renglón primero, `LIMIT 1`.

Estructura del SQL (se valida contra Postgres en E1):

```sql
WITH par AS (fecha por omisión),
dir AS (   -- dirección viva, cliente Activo; CP de entrega y su marca; desglosa; sucursal por sales_unit
  ...),
suc AS (   -- pty_fis_sucursales de esa sucursal: marca del CP de expedición y padrón vigente en la fecha
  ...),
renglones AS (
  SELECT * FROM unnest(:materiales, COALESCE(:unidades, '{}'), :cantidades, :montos)
         WITH ORDINALITY AS t(material_id, unidad_pedida, cantidad, monto, posicion)),
mat AS (   -- material vivo y Activo, sus tipos (impuesto/forma), litros, marca de su clave SAT, factor de la unidad
  ...),
zona AS (  -- frontera solo si las 4 condiciones; si no, general + motivo_general
  ...)
SELECT ... FROM renglones
  LEFT JOIN mat ... LEFT JOIN LATERAL (tasa IEPS) ... LEFT JOIN LATERAL (tasa IVA) ...
ORDER BY posicion
```

Cuando la dirección no es válida, los renglones salen igual, con
`direccion_invalida` (mismo criterio que el servicio de precio, R21).

Rendimiento (R26): una fila de dirección, una de sucursal, y por renglón
dos búsquedas por índice en una tabla de pocas decenas de tasas. Se
mide en E3 con 50 renglones.

API (R25): Endpoint `POST impuestos-venta` desde el tab Contrato del
Servicio, como `precio-venta`.

### 6.1 Script de carga de códigos postales (D10)

Carpeta `carga_cp/` de esta spec (versionada, para que la tenga quien
publique):

| Archivo | Contenido |
|---|---|
| `codigos_postales.csv` | Las dos hojas del SAT tal cual (`clave,estado,municipio,localidad,estimulo,fin_vigencia`), con las claves rellenadas a 5 dígitos. Incluye el origen (archivo y revisión) en `LEEME.md` |
| `cargar_codigos_postales.sql` | Script de `psql` |
| `LEEME.md` | Cómo correrlo y cómo regenerar el CSV cuando el SAT publique otra versión |

El script, en una sola transacción:

1. Falla si el catálogo `pty_sat_codigopostal` o su estado Activo no
   existen en ese ambiente (hay que publicar el catálogo antes).
2. `\copy` del CSV a una tabla temporal.
3. Descarta lo que no es una clave de 5 dígitos (la fila de nota del
   SAT).
4. `INSERT ... ON CONFLICT (clave) WHERE delete_guid IS NULL DO UPDATE`
   (usa el índice único de §2.4): un CP nuevo se da de alta y uno que ya
   existe se actualiza solo si cambió algo. Así el mismo script sirve
   para la carga inicial y para cada versión nueva del SAT.
5. Llena los mismos datos de control que un alta del motor (verificado
   en SPEC-ADN-0510202601 A2): `estado_id` = Activo del catálogo,
   `insert_guid` (32 hexadecimales), `fecha_registro` (UTC, al segundo).
   Sucursal, unidad de venta, almacén y creador quedan vacíos, igual que
   un alta de sistema. Al actualizar, `update_guid` nuevo.
6. Informa cuántos dio de alta y cuántos actualizó.

No da de baja los CP que el SAT quite en una versión futura: eso se
decide cuando pase (hoy ninguno tiene fin de vigencia).

## 7. Cuidados conocidos

- Agregar campos a un BC con tabla existente **fuera** de un
  `Repo.transaction` externo (interbloqueo del generador).
- Revisar que las propiedades nuevas de campo pasen por la lista de
  sincronización de `importar_contexto/1`.
- El generador corre **todas** las migraciones pendientes: revisar
  `priv/repo/migrations` antes de crear catálogos. Hoy hay una sin
  seguimiento, `20260928211336_agregar_campos_a_meta_fixture_cliente_…`,
  que no es de esta spec: preguntar al usuario antes de empezar B.
- En Windows, `_build` guarda copia de `priv/`.
- Publicar lo hace otra persona: `03.tasks.md` documenta paquete,
  orden y datos que no viajan.
