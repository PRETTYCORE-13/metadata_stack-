# SPEC-SYS-1809202603 — Propagación de Extensiones (CORE)

**Documento:** Explicación general · **Fase:** ✅ aprobada (2026-09-18).

## ¿Qué problema resuelve?

Cada cliente que usa nuestro sistema corre sobre una base común, el
"núcleo" (lo llamamos CORE o extensión) que compartimos entre todos.
Cuando mejoramos ese núcleo — arreglamos un error, agregamos una
función — esa mejora tiene que llegar, tarde o temprano, a cada cliente
que la está esperando. A eso le llamamos "propagar": tomar esa mejora,
ya armada y probada una sola vez, y llevarla tal cual —sin tocarla, sin
volver a armarla— a cada lugar donde hace falta. Como repartir el mismo
paquete cerrado a varios destinos, en vez de armar un paquete nuevo
para cada uno.


## ¿Cómo funciona, a grandes rasgos?

El camino de una mejora se puede pensar como tres escalones de confianza:
primero se prueba en un ambiente interno (**unstable**, el menos
exigente), después en uno intermedio donde se valida más en serio
(**testing**), y recién después se considera lista para producción
(**stable**). "Propagar" es mover ese mismo paquete ya probado de un
escalón al siguiente, o entregárselo directamente a un cliente real —
es el paquete idéntico que ya funcionó en el escalón anterior, nunca
uno armado de nuevo para la ocasión.

**El orden nunca se salta**: algo tiene que pasar por `testing` antes
de llegar a `stable`, y por `stable` antes de llegar a un cliente real
(producción) — nunca directo de `unstable` a `stable`, ni de `stable` a
un cliente sin haber pasado por ahí primero. Es una barrera a
propósito: nada llega a un cliente real sin haber pasado por los dos
escalones anteriores.

Tampoco los tres escalones se mueven de la misma forma: `unstable`
recibe cada mejora automáticamente, apenas se termina de programar.
`testing` y `stable`, en cambio, nunca se mueven solos — alguien del
equipo de plataforma tiene que decidir, a mano, que esa mejora ya está
lista para pasar al siguiente escalón.

Cada vez que el núcleo cambia —aunque sea un arreglo chiquito— nace una
"versión" distinta a la anterior. Es el mismo concepto de todos los
días: cuando WhatsApp saca una actualización, sigue siendo la misma
app, pero es una versión nueva de esa app. Acá, en vez de un número
como "2.3.1", cada versión se identifica con el código único de ese
cambio en el historial de código (lo que en la jerga técnica se llama
"commit") — así no hay ambigüedad sobre cuál versión es cuál.

Esta spec agrega tres cosas nuevas sobre ese mecanismo:

- **Una foto de estado**: un vistazo único que muestra qué versión
  corre en cada escalón y en cada cliente, todo junto, sin tener que
  entrar ambiente por ambiente.
- **Una guarda de sentido común**: si le pedimos actualizar algo que ya
  está exactamente en esa versión, el sistema avisa y no hace nada —
  ya no reinicia de más.
- **Elegir a mano qué versión propagar**: normalmente se toma "lo
  último disponible", pero a veces lo último todavía no terminó de
  validarse — esta spec permite elegir un punto específico del
  historial en vez de tomar siempre el más reciente a ciegas.
- **La versión, visible para cualquiera**: no hace falta ser
  administrador de plataforma para saber qué versión corre en un
  sistema puntual — queda visible directo en el pie de página de la
  aplicación (junto al "Prettycore 2026" de siempre), con su fecha al
  lado. Útil para un diagnóstico rápido con un cliente, sin necesitar
  acceso técnico.

Además, se suma una pantalla dedicada (dentro del panel de
administración de plataforma) donde se ve, en una sola vista tipo
"línea de tiempo", en qué versión está parado cada escalón y cada
cliente, quién escribió cada mejora y quién decidió aplicarla — y desde
ahí mismo se puede disparar una propagación o, si algo salió mal,
volver a la versión anterior — todo sin necesitar terminal.

## Volver atrás (rollback)

Cuando una versión nueva trae un problema, se puede volver a la
anterior. El código siempre se puede revertir sin drama. Los cambios en
la base de datos que trajo esa versión son otra historia: si fueron
cambios "seguros" (por ejemplo, una tabla nueva que todavía está
vacía), el sistema los revierte solo. Si fueron cambios que ya pudieron
haber afectado datos reales de algún cliente (por ejemplo, borrar una
columna), el sistema NO los revierte solo — avisa exactamente qué
frenó el proceso y por qué, y deja esa decisión en manos de un
administrador humano. Es una barrera a propósito: preferimos frenar y
preguntar antes que borrar algo por error.

## ¿Quién usa esto y cuándo?

Lo usa el equipo de plataforma cada vez que sale una mejora del núcleo
y hay que llevarla a los clientes — algo que pasa seguido (a diferencia
de dar de alta un cliente nuevo, que es raro). La pantalla está
restringida a los administradores de plataforma, porque toca sistemas
en producción con datos y usuarios reales.

## Lo que esta spec NO hace

No cubre cómo se da de alta un cliente nuevo (eso ya está resuelto en
otra spec). Tampoco cubre la propagación de catálogos o configuraciones
de negocio propias de cada cliente — solo el núcleo compartido; eso
queda para una spec futura y separada.
