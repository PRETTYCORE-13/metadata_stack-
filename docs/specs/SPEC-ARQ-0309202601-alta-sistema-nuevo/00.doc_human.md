# SPEC-ARQ-0309202601 — Alta de Sistema Nuevo

**Documento:** Explicación general · **Fase:** ✅ aprobada (2026-09-03).

## ¿Qué problema resuelve?

Hasta ahora el sistema solo sabía desplegarse a sí mismo una única
vez — un solo nombre de servidor, una sola base de datos, un solo
dominio, todo fijo de antemano en el mecanismo de automatización. El
plan de negocio necesita alojar varios sistemas de distintos clientes
en la misma infraestructura compartida, cada uno con sus propios
datos y su propio despliegue, sin que lo que pasa en uno afecte a los
demás — arrancando por un cliente de CRM. Esta spec construye el
mecanismo para dar de alta un sistema nuevo (no el contenido de
negocio de ningún cliente puntual, eso queda para otra spec) y para
poder después publicarle actualizaciones sin arriesgar tocar por error
el sistema de otro cliente.

## ¿Cómo funciona, a grandes rasgos?

Alguien del equipo de Desarrollo ejecuta un mecanismo con el nombre
del sistema nuevo. Antes de crear nada, el sistema valida en varios
lugares distintos que ese nombre no esté usado todavía — para evitar
chocar por error con otro sistema, incluso uno que pertenece a otra
funcionalidad de la plataforma y no aparece en el registro habitual.
Confirmado que el nombre está libre, se crea de punta a punta: una
base de datos propia y aislada para ese cliente (dentro de un servidor
de base de datos compartido, pensado para funcionar igual el día que
se mude a un servicio de nube más robusto, sin tener que cambiar nada
más que una dirección), un despliegue propio de la aplicación, y una
dirección web propia para ese cliente (su propio subdominio, siempre
con conexión segura). Al final del proceso, el sistema nuevo
queda anotado en una lista oficial de sistemas válidos, que es la que
usa el resto de la plataforma para saber a quién se le puede publicar
algo — un sistema creado pero no anotado ahí se considera una alta
incompleta.

Las mejoras al núcleo compartido de la plataforma (no específicas de
ningún cliente) pasan, aparte, por tres escalones de confianza antes
de llegar a un cliente real: se prueban primero en un ambiente
interno, después en uno intermedio, y recién cuando se validan ahí se
habilitan para producción — un cliente real nunca puede recibir algo
que no pasó por los tres escalones. Y publicar algo hecho a medida
para un cliente puntual siempre exige indicar explícitamente a cuál
cliente va dirigido — nunca hay un destino "por default" que pueda
mandar algo al lugar equivocado sin querer.

## Historia

El plan original pensaba en que cada developer simulara su propio
servidor de base de datos en su propia máquina, y en usar el mecanismo
estándar de direcciones web seguras que trae Kubernetes de fábrica.
Los dos se descartaron después de revisar el servidor real: se usa en
cambio un único servidor de base de datos compartido (más fiel al
modelo real de "un servidor, muchas bases"), y las direcciones web se
resuelven con un mecanismo ya construido y probado en otra
funcionalidad de la plataforma, porque el servidor real ni siquiera
tenía instalado lo que el plan original necesitaba.

## ¿Quién usa esta funcionalidad?

El equipo de Desarrollo, que da de alta un sistema nuevo desde su
propia terminal, con acceso directo al servidor — nunca la gente de
ADN. La gente de ADN, en cambio, usa el resultado: publica
funcionalidad a un sistema ya dado de alta indicando siempre
explícitamente a cuál apunta, sin poder dar de alta un sistema nuevo
por su cuenta.

## Lo que esta spec NO hace

No construye el contenido de negocio del CRM ni de ningún cliente —
solo el mecanismo para alojarlo. No resuelve respaldo, alta
disponibilidad ni monitoreo del servidor compartido — problemas reales
identificados en el camino, pero que quedan para otra spec. Y no migra
la base de datos de producción a un servicio de nube real — deja el
mecanismo listo para apuntar ahí el día que exista, sin ejecutar esa
migración de infraestructura.
