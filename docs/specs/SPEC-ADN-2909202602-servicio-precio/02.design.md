# SPEC-ADN-2909202602 — Servicio de precio de venta

**Documento:** Design · **Fase:** en definición.

## 1. Decisiones de fondo

| # | Decisión | Por qué |
|---|---|---|
| D1 | El servicio es una Consulta SQL de uso **Servicio** (SPEC-SYS-2509202601 §11): `pty_sql_materiales_precio_venta`, con nav `/materiales/precio_venta` | Es lógica de negocio `pty_`: se publica con `motor.publicar` y el núcleo no sabe de precios |
| D2 | Un renglón por producto pedido, con una columna **`estado`**: `ok`, `sin_precio` o `direccion_invalida` | Una función SQL no lanza errores propios; así se cumplen R3, R5 y R6 con un solo contrato |
| D3 | La vista `pty_sql_materiales_precio_base` de SPEC-ADN-2909202601 **se retira** | R10: la cascada vive en un solo lugar. La vista no tiene consumidores |
| D4 | Tope de 1,000 renglones (el default de la SYS) | Un pedido real ronda los 50 productos (R15) |

## 2. Parámetros

| Parámetro | Tipo | Obligatorio | Uso |
|---|---|---|---|
| `direccion_id` | entero | sí | Dirección de entrega (R1) |
| `productos` | lista de enteros | sí | Ids de `pty_mat_materiales`; los repetidos se resuelven una vez (R4) |
| `fecha` | fecha | no | Si llega vacía: hoy en `America/Mexico_City` (R1) |

## 3. SQL del servicio

> **Actualizado el 2026-10-06 por SPEC-ADN-0510202601 §5.** El SQL de
> abajo es el original, por caja. El vigente agrega el parámetro
> `unidades`, busca por (material, unidad), deriva desde la unidad de
> precio del material y regresa `precio`, `unidad_id`, `origen`,
> `unidad_ancla_id`, `precio_ancla` y `recargo` en lugar de
> `precio_caja`. La cascada y la regla de vigencias no cambian. El SQL
> vigente vive en la Consulta SQL y en la guía de uso (`05.usage.md`).

```sql
WITH par AS (
  SELECT COALESCE(:fecha, (now() AT TIME ZONE 'America/Mexico_City')::date) AS fecha
),
dir AS (   -- R2/R3: se deduce todo de la dirección; vacía si no es válida
  SELECT d.id, c.pty_cs_clientes_mat_precios AS lista_cliente,
         c.pty_cs_clientes_cs_canales AS canal_id, su.branch_id AS sucursal_id,
         su.branch_id, d.pty_cs_direcciones_sales_unit AS sales_unit_id
    FROM pty_cs_direcciones d
    JOIN pty_cs_clientes c     ON c.id = d.encabezado_id AND c.delete_guid IS NULL
    JOIN meta_schema_estados ec ON ec.id = c.estado_id AND ec.nombre = 'Activo'
    LEFT JOIN meta_schema_sales_unit su ON su.id = d.pty_cs_direcciones_sales_unit
   WHERE d.id = :direccion_id AND d.delete_guid IS NULL
),
candidatos AS (   -- cascada de SPEC-ADN-2909202601
  SELECT 1 AS nivel, lista_cliente AS lista_id FROM dir
  UNION ALL
  SELECT 2, ca.pty_cs_canales_mat_precios
    FROM dir JOIN pty_cs_canales ca ON ca.id = dir.canal_id
  UNION ALL
  SELECT 3, pb.encabezado_id
    FROM dir JOIN pty_mat_precios_branch pb
      ON pb.pty_mat_precios_branch_branch = dir.sucursal_id
     AND pb.pty_mat_precios_branch_es_maestra AND pb.delete_guid IS NULL
),
precios AS (
  SELECT DISTINCT ON (p.pty_mat_precios_det_mat_materiales)
         p.pty_mat_precios_det_mat_materiales AS material_id,
         k.nivel, k.lista_id,
         p.pty_mat_precios_det_precio AS precio_caja,
         p.pty_mat_precios_det_vigente_desde AS vigente_desde
    FROM candidatos k
    JOIN pty_mat_precios l      ON l.id = k.lista_id AND l.delete_guid IS NULL
    JOIN meta_schema_estados el ON el.id = l.estado_id AND el.nombre = 'Activo'
    JOIN pty_mat_precios_det p  ON p.encabezado_id = k.lista_id AND p.delete_guid IS NULL
                               AND p.pty_mat_precios_det_mat_materiales = ANY(:productos)
    JOIN pty_mat_materiales m   ON m.id = p.pty_mat_precios_det_mat_materiales AND m.delete_guid IS NULL
    JOIN meta_schema_estados em ON em.id = m.estado_id AND em.nombre = 'Activo'
    CROSS JOIN par
   WHERE p.pty_mat_precios_det_vigente_desde <= par.fecha
     AND (p.pty_mat_precios_det_vigente_hasta IS NULL OR p.pty_mat_precios_det_vigente_hasta >= par.fecha)
   ORDER BY p.pty_mat_precios_det_mat_materiales, k.nivel, p.pty_mat_precios_det_vigente_desde DESC
),
pedidos AS (
  SELECT DISTINCT unnest(:productos) AS material_id
)
SELECT pe.material_id,
       pr.precio_caja, pr.nivel, pr.lista_id, pr.vigente_desde,
       CASE WHEN NOT EXISTS (SELECT 1 FROM dir) THEN 'direccion_invalida'
            WHEN pr.material_id IS NULL        THEN 'sin_precio'
            ELSE 'ok' END AS estado,
       (SELECT branch_id FROM dir)     AS branch_id,
       (SELECT sales_unit_id FROM dir) AS sales_unit_id
  FROM pedidos pe
  LEFT JOIN precios pr ON pr.material_id = pe.material_id
```

Qué requisito cubre cada parte:

- **R1, R8**: `par.fecha` sustituye al "hoy" de la vista anterior.
- **R2, R3**: `dir` sale vacía si la dirección no existe, está borrada o
  su cliente no está Activo; entonces todos los renglones llevan
  `direccion_invalida`.
- **R4, R5**: `pedidos` hace `DISTINCT` de los productos y es la base
  del `LEFT JOIN`, así que sale un renglón por producto y ninguno se
  pierde.
- **R6**: un producto inexistente, dado de baja o sin precio vigente no
  entra a `precios`, así que sale `sin_precio` con precio vacío.
- **R8, R9**: la misma cascada, el mismo filtro de lista Activa por
  nombre de estado y el mismo desempate por `vigente_desde` que
  SPEC-ADN-2909202601 C1 y D4.
- **R13, alcance**: `branch_id` y `sales_unit_id` son los de la
  dirección: su campo de negocio **Unidad de venta**
  (`pty_cs_direcciones_sales_unit`) y la sucursal de esa unidad.
  **Corregido 2026-09-30 (hallazgo de B6, autorizado por el usuario):**
  la primera versión regresaba las columnas de control `d.branch_id` y
  `d.sales_unit_id`, que en una dirección real están vacías (es detalle
  del cliente). Como el alcance deja pasar las filas con alcance vacío,
  un usuario de otra sucursal veía los precios. La plataforma acota con ellos cuando llama un usuario desde
  la pantalla; ahí, si la dirección está fuera de su alcance, el
  resultado llega **vacío** y hay que tratarlo como "dirección no válida
  para ti". Una regla de BC corre como sistema y no se acota. Por API se
  acota por `empresa_id`, que este servicio no expone (SPEC-SYS-2509202601
  R44 ajustado). Se documenta en el Contrato.
- **R14, rendimiento**: una sola dirección. `candidatos` tiene a lo más
  3 listas, y cada búsqueda en `_det` usa el prefijo `(encabezado_id,
  _mat_materiales)` del índice único del motor con `= ANY(:productos)`.
  El costo crece con los productos pedidos, no con el tamaño de las
  listas. Es mejor que la vista anterior, que leía la lista completa.

## 4. Retiro de la vista (R10, D3)

`pty_sql_materiales_precio_base` se elimina con el flujo normal de
Consulta SQL, que genera la migración `eliminar_vista`, una vez que el
servicio esté verificado. SPEC-ADN-2909202601 se actualiza:
- Su `02.design.md` §3 remite a este servicio.
- Su tarea E1 ya no publica la vista.

## 5. API (R12)

Un Endpoint sobre el Servicio (SPEC-SYS-2509202601, diseño §11.6), método `POST`,
ruta `precio-venta`, con una credencial para la app móvil. Ejemplo de
cuerpo:

```json
{"direccion_id": 1, "productos": [101, 102, 103], "fecha": "2026-10-02"}
```

## 6. Uso desde un BC (R11)

Desde la regla `Post` de un futuro Pedido, al agregar renglones:

```elixir
MetaBcApi.ejecutar_servicio("pty_sql_materiales_precio_venta",
  %{"direccion_id" => dir, "productos" => ids, "fecha" => fecha})
```

Con el resultado, cada renglón guarda `precio_caja`, `nivel` y `lista_id`
(R7), y se bloquea si su `estado` no es `ok`. (Desde SPEC-ADN-0510202601:
`precio` y `unidad_id` en lugar de `precio_caja`, más `origen`.) El Pedido no es parte de
esta spec; aquí solo se verifica con una regla de prueba.
