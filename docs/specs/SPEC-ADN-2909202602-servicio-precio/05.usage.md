# SPEC-ADN-2909202602 — Servicio de precio de venta

**Documento:** Guía de uso · Grupos A-D verificados en dev (2026-09-30).
La publicación a otros ambientes (grupo E) todavía no.

## 1. Objetivo

Obtener el **precio por caja sin impuestos** de uno o varios productos
para una dirección de entrega y una fecha, siguiendo la cascada de
precios: lista especial del cliente → lista de cadena de su canal →
lista maestra de la sucursal. Es el único lugar donde vive esa cascada
(R10); el pedido, la app y cualquier integración lo consultan aquí.

## 2. ¿Quién utiliza esta funcionalidad?

- **Quien programa reglas de BC** (por ejemplo, el futuro Pedido): lo
  llama desde una regla.
- **La app móvil y las integraciones**: lo llaman por API.
- **Quien administra precios**: no lo usa directamente, pero sus datos
  (listas, canales, sucursales) son los que el servicio lee.

## 3. Conceptos que debo conocer

- **Servicio**: `pty_sql_materiales_precio_venta`, una Consulta SQL de
  uso Servicio en BC List → Materiales → **Precio de venta**. Su
  pestaña Contrato muestra parámetros, columnas y el Endpoint.
- **Nivel**: de qué lista salió el precio. 1 = especial del cliente,
  2 = cadena del canal, 3 = maestra de la sucursal.
- **Estado** de cada renglón:

| `estado` | Significa | Qué debe hacer quien lo usa |
|---|---|---|
| `ok` | Hay precio vigente | Usar `precio_caja` |
| `sin_precio` | El producto no existe, está dado de baja o no tiene precio vigente en ningún nivel | **Rechazar el renglón** con un mensaje que nombre el producto (R6.1). Nunca usar 0 ni un valor inventado |
| `direccion_invalida` | La dirección no existe, está borrada o su cliente no está Activo | Rechazar todo el pedido |

## 4. Flujo general

1. Quien llama manda la dirección, los productos y, si quiere, la fecha.
2. El servicio deduce el cliente, su canal y la sucursal a partir de la
   dirección.
3. Por cada producto busca el precio vigente en ese orden de listas.
4. Regresa **un renglón por producto pedido** (los repetidos, una vez;
   ninguno se omite) con su `estado`.

## 5. Guía paso a paso

### 5.1 Parámetros

| Parámetro | Tipo | Obligatorio | Notas |
|---|---|---|---|
| `direccion_id` | entero | sí | Dirección de entrega |
| `productos` | lista de enteros | sí | Ids de `pty_mat_materiales` |
| `fecha` | fecha | no | Si no llega, hoy en hora de México. Por API, texto `AAAA-MM-DD` |

### 5.2 Desde una regla de BC

```elixir
MetaBcApi.ejecutar_servicio("pty_sql_materiales_precio_venta", %{
  "direccion_id" => direccion_id,
  "productos" => [101, 102, 103],
  "fecha" => ~D[2026-10-02]
})
```

- Regresa `{:ok, %{columnas: [...], filas: [%{"material_id" => 101,
  "precio_caja" => Decimal, "nivel" => 1, ...}]}}` o `{:error, motivo}`.
- Corre como sistema: no se acota por el alcance del usuario.
- Corre dentro de la transacción de la regla: ve los cambios que la
  regla ya hizo, aunque todavía no se confirmen, y un error no aborta la
  transacción.

### 5.3 Por API

- `POST http://<servidor>/api/consultas/precio-venta`
- Encabezado `Authorization: Bearer <llave>`.
- Cuerpo:

```json
{"direccion_id": 1, "productos": [101, 102, 103], "fecha": "2026-10-02"}
```

- Respuesta: `{"data": [ {renglón}, ... ], "meta_campos": [...]}`.
- También responde a `GET` con los parámetros en la URL
  (`?direccion_id=1&productos=101,102,103`), pero para la app se usa
  **POST**: un pedido puede traer muchos productos y en `GET` el cuerpo
  se ignora.
- **La llave es de cada ambiente.** Se crea en engrane → **Servicios** →
  Precio de venta → "+ Credencial" y se muestra una sola vez. En dev
  existe la credencial "prettycore".

### 5.4 Columnas del resultado

| Columna | Contenido |
|---|---|
| `material_id` | Producto pedido |
| `precio_caja` | Precio por caja sin impuestos (vacío si no es `ok`) |
| `nivel` | 1, 2 o 3 (vacío si no es `ok`) |
| `lista_id` | Lista de precios de donde salió |
| `vigente_desde` | Desde cuándo rige ese precio |
| `estado` | `ok`, `sin_precio` o `direccion_invalida` |
| `branch_id`, `sales_unit_id` | Sucursal y unidad de venta de la dirección |

## 6. Ejemplos prácticos

**Postman, dev, 2026-09-30.** `POST /api/consultas/precio-venta` con
`{"direccion_id": 1, "productos": [1, 2, 3]}` → 200, tres renglones con
`branch_id = 2`, `sales_unit_id = 2` y `estado = "sin_precio"` (en dev
no había renglones de precio cargados).

**Casos verificados** (grupo B, con datos de prueba): producto solo en
la maestra → nivel 3; en cadena y maestra → nivel 2; en las tres →
nivel 1; precio especial vencido o futuro → cae al nivel 2; dos precios
vigentes en la misma lista → gana el de `vigente_desde` más reciente.

## 7. Casos comunes

- **Todo sale `sin_precio`**: en ese ambiente no hay renglones de
  precio para esos productos, o el cliente, el canal y la sucursal no
  tienen lista asignada.
- **Todo sale `direccion_invalida`**: la dirección no existe o su
  cliente está en Baja.
- **Un precio nuevo no aparece**: revisar su `vigente_desde` (si
  empieza mañana, hoy no aplica) y que la lista esté Activa.
- **Un usuario ve el resultado vacío desde una pantalla**: la dirección
  es de una sucursal fuera de su alcance (R13). Desde una regla o por
  API no aplica.

## 8. Errores y situaciones especiales

| Respuesta | Cuándo |
|---|---|
| 400 | Falta `direccion_id` o `productos`, o un valor no es del tipo esperado. Aparece también si se manda `GET` con los datos en el cuerpo |
| 401 | Llave faltante, incorrecta o revocada |
| 404 | La ruta no existe o el Endpoint está en borrador |
| 422 | El resultado pasa el tope de 1,000 renglones |
| 504 | Tardó más del tiempo máximo |

## 9. Resultado esperado

Un renglón por producto pedido, en menos de un milisegundo para un
pedido de 50 productos (B8: 0.72 ms), listo para que el pedido guarde
`precio_caja`, `nivel` y `lista_id` en cada renglón o lo rechace si su
`estado` no es `ok`.
