# SPEC-ADN-2209202601 — Configuración de Sales Unit (app móvil)

**Documento:** Guía de uso · Grupos A-E, 100% verificados contra Postgres real.

## 1. Objetivo

Armar y mantener la configuración de ~120 parámetros de la app móvil,
compartida por perfil (no por unidad), con dos ejes de asignación
independientes: Ventas (Sales Unit) y Reparto (Almacén).

## 2. ¿Quién utiliza esta funcionalidad?

Gente de ADN, con el rol `pty-dsd-admin`, desde el Motor BC
(`/sysadmin/bc-list/<catalogo>/motor`) para los 4 catálogos maestro.
Un desarrollador de la app móvil (u otro sistema) consume la
configuración efectiva por código, vía
`MetadataApp.Adn.ConfigSalesUnit.efectiva_ventas/1` /
`efectiva_reparto/1` (todavía sin endpoint HTTP propio — eso es
Grupo F/tareas futuras, ver §6).

## 3. Conceptos que debo conocer

- **Parámetro Base** (`pty_config`): la lista cerrada de los ~120
  parámetros — código, tipo de dato, valor default. Nada más en el
  sistema puede inventar un parámetro que no esté acá.
- **Perfil de Configuración** (`pty_config_perfiles` +
  `pty_config_perfilesdet`): un set de valores reusable, uno por
  parámetro. Se arma UNA vez y se asigna a muchas Sales Unit/Almacenes.
- **Eje Ventas / Eje Reparto**: dos formas independientes de asignar un
  Perfil — una Sales Unit (`pty_config_perfiles_salesu`) o un Almacén
  (`pty_config_perfiles_invlocation`), cada uno con sus propias
  Excepciones puntuales. Una misma Sucursal puede tener perfiles
  distintos (o el mismo) para cada eje.
- **Excepción**: un valor que reemplaza al del Perfil para un parámetro
  puntual, solo en esa Sales Unit/Almacén.
- **"Vivo"**: en todo este sistema significa estado **Activo** del
  autómata, no solo `delete_guid` — un Parámetro/Perfil/asignación
  dado de baja deja de contar (completitud, resolución efectiva) sin
  borrarse.

## 4. Flujo general

1. Cargar los Parámetros Base que hagan falta (una sola vez, catálogo
   `pty_config`).
2. Armar un Perfil de Configuración y cargarle un valor por parámetro.
3. Asignar el Perfil a una Sales Unit (eje Ventas) y/o a un Almacén
   (eje Reparto).
4. Si una unidad puntual necesita algo distinto, cargarle una
   Excepción — solo el parámetro que difiere.
5. La app móvil (o quien consuma) pide la configuración efectiva por
   Sales Unit o por Almacén — nunca resuelve la cascada ella misma.

## 5. Guía paso a paso

### 5.1 Cargar un Parámetro Base

1. `/sysadmin/bc-list/pty_config/motor` → tab Configuración → "+
   Agregar registro" (patrón BC básico de siempre).
2. Completar `parametro` (código técnico único), `parametro_tipo`
   (boolean/integer/decimal/string/enum) y `parametro_valor` (default).
3. Guardar — dispara la transición `alta`, que ya valida que el código
   no esté repetido (regla `parametro_codigo_unico`).

### 5.2 Armar un Perfil de Configuración

1. `/sysadmin/bc-list/pty_config_perfiles/motor` → dar de alta el
   Perfil (campo `descripcion`).
2. **Para cargarle valores, NO uses el "+ Agregar renglón" genérico de
   la Ficha 360°/Grid Editable** — no valida el tipo (hallazgo real de
   esta spec, ver `02.design.md` §5.0). Usá
   `MetadataApp.Adn.ConfigSalesUnit.agregar_valor_perfil(perfil_id,
   parametro_id, valor)` — valida el tipo contra el Parámetro Base y
   rechaza duplicados antes de guardar.
3. `MetadataApp.Adn.ConfigSalesUnit.completitud_perfil(perfil_id)`
   devuelve `%{completo?: bool, faltantes: [parametro_id, ...]}` — un
   Perfil incompleto es válido mientras se termina de armar.

### 5.3 Asignar el Perfil a una Sales Unit o un Almacén

1. `/sysadmin/bc-list/pty_config_perfiles_salesu/motor` (eje Ventas) o
   `pty_config_perfiles_invlocation/motor` (eje Reparto) → "+ Agregar
   registro" — elegir la Sales Unit/Almacén (referencia real, combo
   restringido) y el Perfil, más los responsables (obligatorios, R19-R20):
   en eje Ventas, **Empleados** y **Supervisores**; en eje Reparto,
   **Supervisores**. Son informativos: no cambian la configuración que
   recibe la app. Una asignación creada antes de estos campos los tiene
   vacíos, y la pantalla pide llenarlos al editarla.
2. Una Sales Unit/Almacén solo puede tener UNA asignación viva por eje
   — un segundo intento se rechaza (índice único real, `{:error,
   changeset}` limpio).

### 5.4 Cargar una Excepción puntual

Igual que §5.2 (mismo motivo, misma solución):
`ConfigSalesUnit.agregar_excepcion_ventas(sales_unit_config_id,
parametro_id, valor)` o `agregar_excepcion_reparto/3` — nunca el "+
Agregar renglón" genérico.

### 5.5 Consultar la configuración efectiva

`ConfigSalesUnit.efectiva_ventas(sales_unit_id)` /
`efectiva_reparto(inventory_location_id)` — devuelve un mapa
`%{"codigo_parametro" => valor_tipado, ...}` con TODOS los Parámetros
Base vivos, ya resueltos (Excepción → Perfil → default) y tipados
(booleano/número real, no texto). Si la Sales Unit/Almacén no tiene
ninguna asignación todavía, devuelve igual — puros defaults.

### 5.6 Dar de baja un Perfil

Solo se puede si NO tiene ninguna asignación viva en NINGUNO de los
dos ejes — el sistema lo rechaza explícitamente
(`perfil_sin_asignaciones_vivas`), verificado incluso con Ventas Y
Reparto asignados a la vez: hay que liberar las dos antes de poder dar
de baja el Perfil.

## 6. Casos comunes

- **"Cargué un renglón con el tipo equivocado y no se rechazó"** —
  seguro se usó el "+ Agregar renglón" genérico del Motor BC en vez de
  las funciones de `ConfigSalesUnit` (§5.2/§5.4). Es un límite conocido
  del motor para catálogos detalle, no un bug — ver `02.design.md` §5.0.
- **"No puedo dar de baja un Perfil"** — tiene una asignación viva en
  Ventas o en Reparto (o las dos). Reasignar esa Sales Unit/Almacén a
  otro Perfil, o darla de baja, antes de reintentar.
- **"efectiva_ventas me devuelve un parámetro con el default aunque el
  Perfil lo tiene cargado"** — revisar que la asignación esté en
  estado Activo (una asignación de baja no resuelve nada, aunque siga
  existiendo el registro).

## 7. Resultado esperado

Dado un Parámetro Base, un Perfil con valores cargados, y una
asignación a una Sales Unit/Almacén (con o sin Excepciones), la
configuración efectiva de esa unidad refleja la cascada completa sin
que el consumidor tenga que calcular nada. Cambiar un valor del Perfil
propaga automáticamente a todas las unidades que lo usan, sin tocarlas
una por una.
