# SPEC-ADN-2209202601 — Configuración de Sales Unit (app móvil)

**Documento:** Requirements · **Fase:** en definición.

## 1. Parámetros Base

R1. EL SISTEMA DEBE mantener un catálogo cerrado de Parámetros Base,
cada uno con: código técnico único, etiqueta, tipo de dato (booleano,
entero, decimal, texto o lista cerrada de opciones) y un valor
default.

R2. CUANDO se intenta dar de alta un Parámetro Base con un código ya
usado por otro Parámetro Base vivo, EL SISTEMA DEBE rechazarlo.

R3. CUANDO se da de baja un Parámetro Base que ya tiene valores
cargados en algún Perfil o Excepción, EL SISTEMA DEBE conservar esos
valores sin borrarlos, pero excluir ese parámetro de la validación de
completitud (R9) y de la resolución de configuración efectiva (R16)
desde ese momento en adelante.

## 2. Perfiles de Configuración

R4. EL SISTEMA DEBE permitir dar de alta un Perfil de Configuración
identificado por nombre, y cargarle, renglón por renglón, un valor
para los Parámetros Base que corresponda. Un mismo Perfil es
reutilizable por CUALQUIERA de los dos ejes de asignación (§3) — no
hay un catálogo de Perfil separado por eje.

R5. CUANDO se carga un renglón de valor dentro de un Perfil, EL
SISTEMA DEBE exigir que el parámetro referenciado sea un Parámetro
Base vivo — nunca un texto libre tipeado a mano.

R6. EL SISTEMA DEBE rechazar dos renglones para el mismo Parámetro
Base dentro de un mismo Perfil (un valor por parámetro, sin
duplicados).

R7. CUANDO se carga o edita el valor de un renglón de Perfil, EL
SISTEMA DEBE validar que el valor cumple el tipo de dato declarado en
su Parámetro Base (ej. rechazar texto en un parámetro booleano).

R8. EL SISTEMA DEBE poder indicar, para cualquier Perfil, si está
completo (tiene un renglón cargado para cada Parámetro Base vivo) o
cuáles parámetros le faltan — un Perfil incompleto es un estado válido
mientras se termina de armar, no un error.

R9. CUANDO se intenta dar de baja un Perfil que todavía tiene alguna
asignación viva en cualquiera de los dos ejes (§3), EL SISTEMA DEBE
rechazarlo — hay que reasignar esas asignaciones a otro Perfil
primero.

## 3. Ejes de asignación: Ventas (Sales Unit) y Reparto (Almacén)

La configuración de la app móvil se asigna por DOS ejes independientes
— la ruta de venta (Sales Unit) y la ruta de reparto (Almacén/
Inventory Location) — porque una misma Sucursal puede necesitar
config distinta para cada rol de app móvil. Estructuralmente son
idénticos (R10-R14 aplican igual a ambos, un eje = una entidad
distinta), solo cambia a qué entidad de sistema apunta cada uno.

R10. EL SISTEMA DEBE permitir asignar, a una Sales Unit real del
sistema, una configuración de eje Ventas con: el Perfil de
Configuración que le aplica, y opcionalmente renglones de Excepción
(un valor puntual que reemplaza al del Perfil para ese parámetro).

R11. EL SISTEMA DEBE permitir lo mismo que R10, pero para un Almacén/
Inventory Location real del sistema (eje Reparto), de forma
completamente independiente del eje Ventas — una misma Sucursal puede
tener perfiles distintos (o el mismo) para cada eje, sin relación
forzada entre ambos.

R12. EL SISTEMA DEBE rechazar más de una configuración de eje Ventas
para la misma Sales Unit, y más de una configuración de eje Reparto
para el mismo Almacén (relación uno a uno, por eje).

R13. EL SISTEMA DEBE permitir asignar, en cualquiera de los dos ejes,
un Perfil incompleto (R8) — la resolución de configuración efectiva
(R16) cubre lo que falte con el default del Parámetro Base.

R14. CUANDO se carga un renglón de Excepción (en cualquiera de los dos
ejes), EL SISTEMA DEBE exigir que el parámetro referenciado sea un
Parámetro Base vivo (misma regla que R5), y rechazar dos renglones
para el mismo parámetro dentro de la misma Sales Unit/Almacén (misma
regla que R6).

R15. CUANDO se carga o edita el valor de una Excepción (en cualquiera
de los dos ejes), EL SISTEMA DEBE validar que cumple el tipo de dato
de su Parámetro Base (misma regla que R7).

## 4. Configuración efectiva

R16. CUANDO se solicita la configuración efectiva de una Sales Unit
(eje Ventas) o de un Almacén (eje Reparto), EL SISTEMA DEBE devolver,
para cada Parámetro Base vivo, el primero que exista de esta cascada:
(1) la Excepción de esa Sales Unit/Almacén para ese parámetro, (2) el
valor cargado en el Perfil asignado a ese eje para ese parámetro, (3)
el default del Parámetro Base. Los dos ejes se resuelven de forma
independiente — no se combinan en una sola respuesta salvo que el
cliente pida explícitamente los dos.

R17. CUANDO se solicita la configuración efectiva de una Sales Unit u
Almacén que no tiene ninguna asignación de ese eje todavía, EL SISTEMA
DEBE responder igual, usando el default de cada Parámetro Base vivo
(nunca un error ni una lista vacía).

R18. La app móvil (u otro cliente) consumidora de la configuración
efectiva NUNCA DEBE tener que resolver la cascada de R16 por su
cuenta — recibe ya el valor final por parámetro.

## 5. Fuera de alcance de esta spec

- La lista real de los ~120 parámetros de negocio (carga de datos de
  ADN, no diseño).
- Variabilidad de un parámetro por debajo de Sales Unit/Almacén
  (producto, turno, usuario) — si aparece ese caso real, se vuelve a
  evaluar acá antes de extender el modelo.
- Una respuesta COMBINADA de los dos ejes en una sola llamada (R16) —
  si la app móvil necesita eso, se agrega como requisito nuevo cuando
  haya un caso real.
- La pantalla/UI concreta de administración (`02.design.md`).
- Migración de los valores hoy guardados en XML hacia este modelo
  nuevo (tarea aparte si hace falta conservar el valor vigente de cada
  Sales Unit/Almacén existente).
