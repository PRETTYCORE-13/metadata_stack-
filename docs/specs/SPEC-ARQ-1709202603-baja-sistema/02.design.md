# SPEC-ARQ-1709202603 — Baja de Sistema

**Documento:** Design · **Fase:** ✅ aprobada (2026-09-21).

Contraparte de `SPEC-ARQ-0309202601-alta-sistema-nuevo` — reusa
exactamente las mismas convenciones de nombre de recurso (tabla §1 de
esa spec: `metadata-<sistema>`, `db_<sistema>`, `<sistema>-env`,
`<sistema>.ventaenruta.com.mx`), el mismo `MetadataApp.MotorAlta`, y el
mismo `MetadataApp.Ssh` — nada de esto reconstruye un mecanismo nuevo,
todo es la operación inversa de lo que ya existía.

## 1. Orden de los pasos (R1-R7)

Al revés del alta (que primero crea la base y recién después expone el
dominio), la baja va de "más visible/reversible" a "menos
reversible", **con el respaldo siempre primero, antes de tocar nada**:

1. **Respaldar la base** (R7) — `pg_dump` completo a un archivo en el
   servidor. Si algo falla después de este paso, el dato ya está a
   salvo.
2. **Borrar Deployment/Service/Secret en k3s** — la app deja de estar
   accesible primero, para no seguir aceptando tráfico contra un
   sistema que se está desarmando.
3. **Borrar la base de datos**.
4. **Quitar DNS + Caddy** — en ese orden (borra el registro en
   Cloudflare, después el bloque del Caddyfile), mismo mecanismo
   `MetadataApp.Ssh` que expone el dominio al dar de alta, al revés.
5. **Sacar el sistema de `priv/sistemas.json`** (R5) — commit + push,
   mismo patrón que `registrar_sistema/2` del alta.
6. **Verificar** (R6) — confirma contra el servidor real que no queda
   Deployment en k3s ni bloque en el Caddyfile, antes de reportar
   éxito.

## 2. Respaldo automático (R7)

`MotorAlta.respaldar_base/2` corre `pg_dump` DENTRO del pod de Postgres
(mismo mecanismo de acceso que `crear_base/2` — "aws-postgres" no tiene
puerto publicado fuera del clúster, ver design.md §2 del alta) con la
salida redirigida a un archivo en el HOST real (`/home/elixir/backups/
db_<sistema>_<timestamp>.sql`), nunca dentro del pod — si el pod se
recicla, el respaldo no se va con él.

Formato SQL plano a propósito, no el formato custom de `pg_dump`:
restaurable con un `psql -f` directo, sin depender de `pg_restore` ni
de que quien lo necesite sepa del formato binario de Postgres.

Idempotente (R4): si `db_<sistema>` ya no existe (un intento anterior
ya la había borrado), no hay nada que respaldar — `{:ok,
:ya_no_existia}`, no es error.

**Fuera de alcance a propósito** (ver Preguntas abiertas del
`01.requirements.md`): el respaldo queda en el mismo servidor, no en
otro lado. Restaurarlo es un procedimiento manual, documentado en
`05.usage.md`, no un mecanismo automático — no hay garantía de que un
respaldo viejo restaure limpio contra una versión de código mucho más
nueva (migraciones agregadas después de la foto), riesgo real que
quedó documentado ahí mismo cuando se lo verificó en vivo.

## 3. Confirmación explícita (R3)

`Mix.Tasks.Motor.Baja` pide escribir el nombre exacto del sistema antes
de ejecutar cualquier paso (`Mix.shell().prompt/1`, comparación de
string exacta) — no un simple sí/no. Motivo: un Enter de más, o copiar
y pegar el comando completo sin pensarlo, no debe poder dar de baja el
sistema equivocado. Si la respuesta no coincide, `Mix.raise` — cero
pasos ejecutados, nada tocado.

## 4. Rechazo de nombres inválidos (R2)

`MotorAlta.validar_puede_bajar/2` — al revés de `validar_nombre/2` (que
exige que el sistema NO esté registrado, para el alta), acá exige que
SÍ lo esté, y rechaza explícitamente los tres canales de plataforma
(`unstable`/`testing`/`stable`) aunque en teoría pudieran tener un
Deployment real en k3s — nunca se dan de baja por este mecanismo.

**Hueco real encontrado (2026-09-21, verificando el mecanismo en vivo)**:
esta validación solo mira `priv/sistemas.json` — si una alta se cortó
ANTES de llegar a registrar el sistema ahí (ej. una migración falló a
mitad de camino), el sistema queda con infraestructura real en el
servidor pero sin estar "registrado", y `validar_puede_bajar/2` rechaza
la baja igual que rechazaría un nombre inventado. Mismo problema de
fondo que ya resolvió `SPEC-ARQ-0309202601`/design.md §6 para el ALTA
(dos fuentes no alcanzan si el archivo puede desincronizarse de la
realidad del clúster) — **no resuelto todavía del lado de la baja**,
quedó como limpieza manual esa vez. Ver Preguntas abiertas.

## 5. Idempotencia (R4)

Cada paso, independiente de los demás, tolera reintentarse:

- k3s: `--ignore-not-found` en los tres recursos.
- Base de datos: `DROP DATABASE IF EXISTS ... WITH (FORCE)` — el
  `FORCE` corta conexiones activas antes de soltarla (la app recién
  bajada puede tener conexiones colgando un instante).
- DNS: `Cloudflare.eliminar_registro_a/2` — `{:ok, :no_existia}` si el
  registro ya no está, nunca error.
- Caddy: `Caddy.quitar/2` — mismo criterio, `{:ok, :no_existia}` si el
  host no tiene bloque.
- `priv/sistemas.json`: `desregistrar_sistema/2` — si el sistema ya no
  está en el archivo, solo reintenta el `git push` por si había quedado
  pendiente, sin reescribir nada.

## 6. Riesgo — blast radius

- **Confirmación humana como única barrera antes del borrado
  irreversible** (R3) — no hay una segunda confirmación (ej. un email,
  una aprobación de otra persona) para un sistema con datos reales de
  producción. Mitigado en parte por R7 (el respaldo automático sale
  primero, siempre), pero sigue siendo una decisión de una sola persona
  en el momento. Ver Preguntas abiertas sobre una salvaguarda extra
  para producción real.
- **El mismo mecanismo de SSH que usa `mix motor.alta`** — cualquier
  timeout/cuelgue de `MetadataApp.Ssh` (ver hallazgo real 2026-09-21,
  corregido con el wrapper `timeout` del lado de quien corre `mix`)
  afecta a la baja igual que a la alta.
- **El hueco de R2 de §4 arriba** — hoy, un sistema con infraestructura
  huérfana (alta cortada antes de registrarse) no se puede limpiar con
  este mecanismo tal cual, solo a mano.
