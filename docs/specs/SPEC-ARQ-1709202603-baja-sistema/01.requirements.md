# SPEC-ARQ-1709202603 — Baja de Sistema

**Documento:** Requirements · **Fase:** ✅ aprobada (2026-09-21) — implementada y verificada en real.

## 1. Propósito

Hoy existe un mecanismo (`mix motor.alta`) para crear un sistema nuevo:
base de datos + app en k3s + DNS/Caddy + registro en
`priv/sistemas.json`. No existe la contraparte: dar de baja un sistema
completo (por ejemplo, uno de prueba que ya cumplió su propósito) se hace
a mano, paso por paso, sin ningún mecanismo ni salvaguarda — **caso real,
2026-09-17**: se dio de baja el sistema de prueba `crm` (base de datos,
Deployment/Service/Secret en k3s, registro DNS en Cloudflare, y bloque en
el Caddyfile) a mano, uno por uno, sin ninguna confirmación ni chequeo
automático de que todos los pasos terminaran bien. Este spec define el
mecanismo para dar de baja un sistema existente de forma completa, segura
y verificable.

## 2. Alcance

**Incluye:**
- Mecanismo para dar de baja un sistema completo: eliminar su base de
  datos, su Deployment/Service (y cualquier Secret asociado) en k3s, su
  registro DNS, y su bloque en el Caddyfile remoto.
- Quitar el sistema de `priv/sistemas.json` como parte de la baja.
- Alguna forma de confirmar qué se va a borrar ANTES de borrarlo
  (dado que incluye al menos un paso irreversible: la base de datos).
- Comportamiento retomable si la baja se corta a mitad de camino: volver
  a ejecutar el mecanismo sobre un sistema que ya quedó parcialmente
  borrado no debe fallar ni duplicar pasos, solo terminar lo que falta.

**No incluye:**
- Backup/exportación de los datos del sistema antes de borrarlo — queda
  como pregunta abierta (§5) si hace falta como parte de este mecanismo
  o si es responsabilidad de quien pide la baja, resuelta a mano aparte.
- Baja de un catálogo puntual dentro de un sistema que sigue existiendo
  — eso es otro mecanismo aparte, ya cubierto hoy.
- Baja de los canales de plataforma (`unstable`/`testing`/`stable`) —
  esos no son sistemas dados de alta y no viven en `priv/sistemas.json`;
  no aplica este mecanismo.
- Automatizar cuándo o por qué se decide dar de baja un sistema — eso es
  una decisión de negocio de cada caso, fuera de este spec.

## 3. Contexto real (2026-09-17)

Durante pruebas del mecanismo de alta se dio de baja `crm` completo, en
este orden, contra el servidor real:
1. Borrar Deployment + Service + Secret (`metadata-crm`,
   `metadata-crm-env`) en el namespace `metadata-stack` de k3s.
2. Borrar la base de datos `db_crm`.
3. Borrar el registro DNS tipo A (`crm.ventaenruta.com.mx`) en
   Cloudflare.
4. Quitar el bloque de `crm.ventaenruta.com.mx` del Caddyfile remoto y
   recargar Caddy.
5. Revertir el registro de `crm` en `priv/sistemas.json` (commit
   separado, sin mecanismo dedicado).

Cada paso se hizo con un script suelto, sin ninguna confirmación previa
ni verificación automática de que el resultado final fuera consistente
(se verificó a mano, leyendo el estado de k3s/Caddy/DNS después de cada
paso). Funcionó, pero no es repetible ni seguro para que lo corra
cualquiera sin conocer el detalle técnico.

## 4. Requisitos funcionales (borrador — EARS)

### R1. Baja completa de un sistema existente
CUANDO alguien del equipo de Desarrollo ejecuta el mecanismo de baja con
el nombre de un sistema dado de alta, EL SISTEMA DEBE eliminar su base de
datos, su Deployment/Service/Secret en k3s, su registro DNS y su
exposición en el reverse proxy, sin afectar a los demás sistemas del
mismo clúster.

### R2. Rechazo de nombres inválidos para la baja
CUANDO se pide dar de baja un nombre que no está registrado en
`priv/sistemas.json`, o que es uno de los canales de plataforma
(`unstable`/`testing`/`stable`), EL SISTEMA DEBE rechazar la operación
sin tocar ningún recurso.

### R3. Confirmación explícita antes de un borrado irreversible
CUANDO se ejecuta el mecanismo de baja, EL SISTEMA DEBE exigir una
confirmación explícita de quien lo ejecuta (por ejemplo, repetir el
nombre del sistema) antes de borrar la base de datos, dado que ese paso
es irreversible y el sistema puede contener datos reales de negocio.

### R4. Baja retomable si se corta a mitad de camino
CUANDO la baja de un sistema se interrumpe antes de terminar todos sus
pasos (por una falla de red, SSH, o de cualquier servicio externo), EL
SISTEMA DEBE poder retomarse ejecutando el mecanismo de nuevo, sin fallar
por pasos que ya se completaron ni dejar recursos a medio borrar sin
posibilidad de terminarlos.

### R5. Actualización del registro de sistemas válidos
CUANDO la baja de un sistema termina exitosamente, EL SISTEMA DEBE
quitarlo de `priv/sistemas.json` como parte del mecanismo — un sistema
borrado de la infraestructura real pero que sigue apareciendo ahí se
considera una baja incompleta.

### R6. Verificación posterior a la baja
CUANDO el mecanismo de baja termina, EL SISTEMA DEBE poder confirmar que
ningún componente del sistema dado de baja sigue activo (sin Deployment
en k3s, sin registro DNS, sin bloque en el Caddyfile) antes de reportar
éxito.

### R7. Respaldo automático antes de borrar la base (resuelto 2026-09-17)
CUANDO se ejecuta el mecanismo de baja, EL SISTEMA DEBE respaldar la base
de datos completa ANTES de borrarla -- sin backup manual previo de por
medio, para cubrir tanto un borrado accidental como confirmar el sistema
equivocado a pesar de R3. El respaldo queda en el mismo servidor, en
formato restaurable con `psql` directo (sin herramientas aparte).

## 5. Preguntas abiertas

- ¿El mecanismo debe poder usarse igual para un sistema con datos reales
  de producción, o conviene alguna salvaguarda adicional (ej. un flag
  `--confirmo-produccion` o similar) para distinguirlo de dar de baja un
  sistema de prueba?
- Si falla un paso intermedio (ej. Cloudflare no responde) pero el resto
  ya se completó, ¿se considera baja "completa con advertencia" o queda
  bloqueada hasta poder terminar ese paso puntual?
- ¿Quién puede ejecutar la baja? Hoy no hay ninguna restricción definida
  sobre quién puede correr el mecanismo de alta más allá de "alguien del
  equipo de Desarrollo" — ¿aplica la misma apertura acá, dado que el
  riesgo de un borrado accidental es mayor que el de una alta accidental?
- **(2026-09-21, encontrado verificando en real)** `validar_puede_bajar/2`
  (R2) solo mira `priv/sistemas.json` — un sistema con infraestructura
  real pero cuya alta se cortó antes de registrarse ahí no se puede
  limpiar con este mecanismo, hay que hacerlo a mano. ¿Vale la pena
  agregar la misma validación de tres fuentes que ya usa el alta
  (`validar_no_existe_en_servidor/2` de `SPEC-ARQ-0309202601`), o
  alcanza con dejarlo documentado como limitación conocida?
