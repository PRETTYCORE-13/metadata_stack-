# SPEC-SYS-2209202602 — Propagación de Artefactos de Negocio

**Documento:** Requirements · Spec de **documentación retroactiva**
(a pedido explícito, 2026-09-22): describe el mecanismo YA existente
de respaldo/propagación de artefactos de negocio (catálogos `pty_*`),
sin cambiar comportamiento del sistema. Cierra la nota pendiente de
`SPEC-SYS-1809202603` (`01.requirements.md` líneas 31-36), que dejó
esto marcado como "spec futura y separada" sin escribirla nunca.

## 1. Contexto y decisión de alcance

**Decisión confirmada por el usuario (2026-09-22, vía AskUserQuestion)**:
esta spec documenta el mecanismo actual, **no** diseña uno nuevo. El
sistema ya se comporta como se describe abajo — nada de lo que sigue
implica trabajo de implementación.

**Fuera de alcance, a propósito**: un canal `testing`/`stable` propio
por artefacto de negocio (independiente del de la extensión/CORE),
versionado con historial de publicaciones anteriores (hoy solo se
conserva la última), y rollback de un catálogo individual sin afectar
a los demás. Si en el futuro se decide construir alguno de estos, es
una spec nueva y separada — no una ampliación de esta.

## 2. Vocabulario

- **Artefacto de negocio**: un catálogo `pty_*` construido con el
  Business Process Builder — su schema, migraciones, autómata,
  plantillas y reglas.
- **Publicar**: `mix motor.publicar --sistema=<sistema> <catalogo>`
  (`MetadataApp.MetaPublicador`) — el único camino que hace que un
  artefacto de negocio quede desplegado en un sistema real y
  respaldado en GitHub, en el mismo paso.
- **Extensión / CORE**: el binario completo de la plataforma que corre
  en cada ambiente — término ya fijado por `SPEC-SYS-1809202603`. Un
  artefacto de negocio publicado viaja empaquetado ADENTRO de la
  extensión, nunca por separado.
- **Tepache**: bundle de previsualización (`mix motor.tepache` /
  `mix motor.tepache.importar`) — comparte el mecanismo de empaquetado
  con `motor.publicar`, pero nunca despliega a producción.

## 3. Requisitos (comportamiento actual)

R1. CUANDO un desarrollador de ADN corre `mix motor.publicar
--sistema=<sistema> <catalogo>`, EL SISTEMA DEBE guardar una copia
completa del artefacto (schema, migraciones, `.meta.json`, autómata,
plantillas, reglas) en un GitHub Release con tag `bc-<catalogo>`,
antes de desplegar nada al sistema destino.

R2. CUANDO ya existe un release `bc-<catalogo>` y el mismo catálogo se
vuelve a publicar, EL SISTEMA DEBE reemplazar el bundle anterior de ese
release (`--clobber`) — el release conserva únicamente la última
versión publicada, sin historial de versiones previas navegable.

R3. CUANDO se construye cualquier imagen normal de la plataforma (cada
push a `main`), EL SISTEMA DEBE restaurar automáticamente todos los
releases `bc-*` existentes antes de compilar, de forma que cualquier
artefacto de negocio publicado en algún momento quede incluido en esa
imagen sin acción manual adicional.

R4. CUANDO se propaga una imagen de un ambiente al siguiente
(`mix motor.propagar_extension <ambiente> unstable testing` o
`testing stable`), EL SISTEMA DEBE mover la imagen completa — todos
los artefactos de negocio publicados hasta ese momento, sin
posibilidad de seleccionar o excluir uno individual.

R5. CUANDO un catálogo todavía no fue publicado ni una sola vez, EL
SISTEMA NO DEBE tener ninguna copia de respaldo de él en GitHub — se
pierde si la máquina local donde se construyó se pierde antes del
primer `motor.publicar`.

R6. CUANDO un desarrollador quiere un respaldo de un catálogo sin
publicarlo ni desplegarlo a ningún sistema real, EL SISTEMA DEBE
permitir subir un bundle de previsualización a un GitHub Release
propio (`mix motor.tepache`, tag `TEPACHE-NNNNNN`), recuperable en
cualquier máquina con `mix motor.tepache.importar <tag>`.

R7. CUANDO se necesita recuperar en una máquina nueva un catálogo que
ya fue publicado al menos una vez, EL SISTEMA DEBE permitir bajarlo
completo con `mix motor.tepache.importar bc-<catalogo>` — el mismo
comando de importación de tepaches funciona contra el tag real
`bc-<catalogo>` porque la descarga es genérica por patrón de archivo
(`*.tar.gz`), no por el prefijo `TEPACHE-`.
