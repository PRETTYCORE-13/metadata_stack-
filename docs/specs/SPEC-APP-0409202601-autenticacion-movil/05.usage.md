# SPEC-APP-0409202601 — Autenticación móvil (Flutter) contra usuarios de metadata_stack

**Documento:** Guía de uso · Grupos A-G, 100% ejecutados y verificados
contra Postgres real y HTTP real (2026-09-04).

## 1. Objetivo

Loguear desde la app móvil Flutter contra los mismos usuarios de
metadata_stack, sin depender de la cookie de sesión web, con un par de
tokens (access + refresh) por dispositivo, revocables individualmente
— y desde el panel web, ver y cerrar sesiones móviles activas.

## 2. ¿Quién utiliza esta funcionalidad?

- **Usuario final de la app Flutter**: ingresa URL de instancia +
  email, después contraseña; queda logueado entre aperturas de la app
  sin volver a escribirla.
- **Cualquier usuario autenticado, desde el panel web**
  (`/sysadmin/sesiones-movil`): ve y cierra sus propias sesiones
  móviles. No requiere ningún permiso especial — es autoservicio sobre
  las propias sesiones (siempre `current_scope.usuario`, sin selector
  de usuario), no una herramienta para administrar a otros.
- **Quien integra el lado Flutter**: este documento es el contrato de
  servidor que esa app consume — el código Flutter/Dart en sí no es
  parte de este repo.

## 3. Conceptos que debo conocer

- **Access token**: vida corta (2 horas), se manda en cada request
  autenticado a la API. Vencido, se rechaza sin importar nada más.
- **Refresh token**: vida larga (60 días), guardado en el dispositivo,
  sirve solo para pedir un access token nuevo — nunca viaja como
  credencial de un request de negocio.
- **Sesión móvil / dispositivo**: cada login desde Flutter genera su
  propio refresh token, independiente de cualquier otro dispositivo o
  de la sesión web.
- **Instancia**: un despliegue de metadata_stack completo, en su
  propia URL, con su propia base — un usuario solo existe dentro de
  UNA instancia.
- **Empresa activa**: se resuelve sola con `empresa_default_id` del
  usuario, sin selector — igual que ya hace la web.

## 4. Flujo general

1. La app manda instancia (URL) + email a `POST /api/movil/verificar`
   ANTES de pedir la contraseña (R11).
2. Si el email existe ahí, pide contraseña y llama
   `POST /api/movil/login` (R1/R2) — recibe `access_token`,
   `refresh_token` y la empresa activa.
3. En cada request de negocio manda `Authorization: Bearer
   <access_token>`; cuando vence, pide uno nuevo con
   `POST /api/movil/token/refrescar` (R3/R4), sin repetir contraseña.
4. Si se pierde el dispositivo o el usuario cierra sesión a propósito:
   `DELETE /api/movil/sesion` (R8) desde la app, o desde el panel web
   (R7).

## 5. Guía paso a paso

### 5.1 Verificar instancia + usuario (antes de pedir contraseña)

```
POST /api/movil/verificar
{ "email": "usuario@ejemplo.com" }
```

200 (existe): `{ "existe": true, "empresa": { "nombre": "Empresa Default S.A." } }`
404 (no existe): `{ "existe": false, "error": "usuario_no_encontrado" }`

### 5.2 Login

```
POST /api/movil/login
{ "email": "usuario@ejemplo.com", "password": "...", "etiqueta_dispositivo": "iPhone de Juan" }
```

`etiqueta_dispositivo` es opcional (default `null`, se muestra como
"Sesión sin nombre" en el panel web).

200:
```json
{
  "access_token": "...",
  "refresh_token": "...",
  "access_token_expira_en": 7200,
  "usuario": { "id": 1, "email": "usuario@ejemplo.com", "alias": "Juan" },
  "empresa": { "id": 3, "nombre": "Empresa Default S.A." }
}
```
401 (credenciales inválidas): `{"error": "credenciales_invalidas"}`

### 5.3 Renovar el access token

```
POST /api/movil/token/refrescar
{ "refresh_token": "..." }
```
200: `{ "access_token": "...", "access_token_expira_en": 7200 }`
401 (vencido/revocado/inexistente): `{"error": "refresh_token_invalido"}` — la app debe volver a `/login`.

### 5.4 Logout explícito

```
DELETE /api/movil/sesion
{ "refresh_token": "..." }
```
204 sin body (idempotente: si ya no existía, también 204).

### 5.5 Ver y cerrar sesiones desde el panel web

1. Entrar a `/sysadmin/sesiones-movil` (logueado, sin permiso especial).
2. La lista muestra cada sesión: `etiqueta_dispositivo` (o "Sesión sin
   nombre"), cuándo se creó, última vez usada.
3. Botón "Cerrar sesión" por fila — revoca esa sesión de inmediato.

## 6. Ejemplos prácticos

### Ejemplo: pedir un access token nuevo sin repetir la contraseña

Con un `refresh_token` todavía vigente (dentro de los 60 días y no
revocado), `POST /api/movil/token/refrescar` devuelve un
`access_token` nuevo de 2 horas — la app nunca vuelve a pedirle la
contraseña al usuario mientras el refresh token siga siendo válido.

### Ejemplo: revocar y confirmar que deja de servir

Después de `DELETE /api/movil/sesion` (o de cerrar esa sesión desde el
panel web), el MISMO `access_token` que todavía tenía firma y
expiración válidas deja de aceptarse igual — la verificación en cada
request confirma contra la base que la sesión sigue existiendo, no
solo la firma del token.

## 7. Casos comunes

- **"La app no me deja pasar de la pantalla de instancia"** — `/verificar`
  devolvió `existe: false`: ese email no pertenece a ningún usuario de
  esa instancia puntual (revisar que la URL ingresada sea la correcta).
- **"Cerré sesión desde el celular y sigo viéndola en el panel web"**
  — no debería pasar: el logout (R8) revoca de inmediato. Si persiste,
  confirmar que la app efectivamente llamó `DELETE /api/movil/sesion`
  con el refresh token correcto.
- **Varios dispositivos con la misma cuenta** — cada login es una
  sesión independiente; cerrar una no afecta a las demás ni a la
  sesión web.

## 8. Errores y situaciones especiales

- **Demasiados intentos fallidos** (login o `/verificar`): `429
  {"error": "demasiados_intentos", "reintentar_en_segundos": N}` — el
  límite es por email (no por IP), 5 fallos en 15 minutos; un login
  exitoso limpia el contador. Aplica a los dos endpoints por igual,
  para que `/verificar` no sea una forma de probar emails sin límite.
- **Refresh token vencido, revocado o inexistente**: siempre `401
  {"error": "refresh_token_invalido"}` — la app debe volver a
  `/login`, no hay forma de "renovar" desde ese estado.
- **Access token vencido**: se rechaza sin importar qué tan reciente
  sea el vencimiento — no hay tolerancia.
- **`confirmed_at` del usuario**: no se valida en el login móvil,
  mismo comportamiento que el login web con contraseña hoy.

## 9. Resultado esperado

Después de un login exitoso, la app puede usar el `access_token` en
requests de negocio durante 2 horas, renovarlo con el `refresh_token`
sin repetir contraseña durante hasta 60 días, y el usuario puede en
cualquier momento ver esa sesión listada en `/sysadmin/sesiones-movil`
y cerrarla — confirmable con un intento posterior de refrescar esa
sesión, que debe devolver `401`.
