# SPEC-SYS-1809202601 — Despublicar un catálogo huérfano

**Documento:** Guía de uso · Grupos A-B, 100% verificados en real
(2026-09-18).

## 1. Objetivo

Eliminar por completo (metadata + tabla física) un catálogo que quedó
"huérfano": existe en un ambiente desplegado pero ya no existe en
ningún lado local (ni header, ni `.ex`, ni migración) — típicamente
producto de un rename mal hecho. No requiere que exista de antemano
una migración de `DROP` generada.

## 2. ¿Quién utiliza esta funcionalidad?

El equipo de plataforma o de ADN, desde terminal (repo clonado +
credenciales SSH del ambiente cargadas en `/sysadmin/ambientes`). No
hay pantalla — es una herramienta de terminal para un caso puntual y
excepcional, no un flujo de trabajo frecuente.

## 3. Conceptos que debo conocer

- **Catálogo huérfano**: existe (header + tabla física, posiblemente
  con datos reales) en un ambiente desplegado, pero NO existe local —
  ni en `meta_schema_header`, ni como archivo `.ex`, ni como
  migración. Si el catálogo SÍ existe local todavía, esta herramienta
  lo rechaza — para ese caso está "Eliminar" en BC List +
  `mix motor.despublicar` normal.
- **Generar vs. propagar**: son dos pasos deliberadamente separados.
  Generar la migración de `DROP` (paso local) es distinto de aplicarla
  a un ambiente puntual (paso de propagación) — porque pueden tener
  destinos distintos.
- **Ambiente explícito**: nunca hay un ambiente por default, mismo
  criterio que `motor.publicar`/`motor.despublicar`/
  `endpoint.despublicar` — siempre se elige a propósito.

## 4. Flujo general

1. Confirmar que el catálogo detectado como huérfano NO existe local.
2. Generar (y correr local) la migración de `DROP` con
   `mix motor.generar_drop_huerfano`.
3. Propagar esa migración a un ambiente puntual con
   `mix motor.despublicar` (sin ningún cambio respecto al uso normal
   de ese comando).
4. Si el catálogo no es `pty_*`/`demo100_*` (no está gitignored):
   commitear la migración para que llegue a `testing`/`stable` por
   promoción normal.

## 5. Guía paso a paso

### 5.1 Generar la migración de DROP

```
mix motor.generar_drop_huerfano <catalogo> --confirmar=<catalogo>
```

1. El comando rechaza la operación si `<catalogo>` SÍ existe local
   todavía (apunta a "BC List → Eliminar" como alternativa correcta).
2. `--confirmar=<catalogo>` es obligatorio y tiene que coincidir
   exactamente con el nombre — si no coincide, rechaza sin tocar nada.
3. Si pasa ambos chequeos, escribe el archivo de migración en
   `priv/repo/migrations/` y la corre YA MISMO en local — esto limpia
   cualquier tabla física huérfana que también haya quedado local, y
   confirma que la migración compila y corre antes de mandarla a
   cualquier otro lado.
4. Este comando NO dispara ningún deploy — solo deja la migración
   lista en disco.

### 5.2 Propagar a un ambiente puntual

```
mix motor.despublicar --sistema=<sistema> <catalogo>
```

Mismo comando que ya existe para cualquier catálogo eliminado
"prolijamente" — no tiene ningún cambio especial para el caso
huérfano, ya sabe encontrar la migración generada en el paso anterior
y armar/subir/disparar el bundle correspondiente.

### 5.3 Dejarlo permanente (si el catálogo no es de prueba)

Si el catálogo no es `pty_*`/`demo100_*`, la migración generada es un
archivo normal versionado — conviene `git add`/commit/push para que
llegue a `testing`/`stable` por promoción normal y a cualquier
checkout nuevo. Es recomendado, no obligatorio: el paso 5.2 ya resuelve
"ya, ahora, en un ambiente puntual" por sí solo.

## 6. Ejemplos prácticos

### Ejemplo real: catálogo `historico`

```
mix motor.generar_drop_huerfano historico --confirmar=historico
mix motor.despublicar --sistema=unstable historico
```

Resultado verificado en `unstable`: la tabla física `historico` y su
header desaparecieron, y la ruta `/historico` (que antes daba
`Ecto.MultipleResultsError` por compartir navegación con
`pty_h_historico`) volvió a navegar sin ambigüedad.

### Ejemplo real: catálogo huérfano ajeno que bloqueaba deploys

De paso, se usó el mismo mecanismo para eliminar
`pty_dsd_mat_material_precios`, otro catálogo huérfano (sin relación
con el caso anterior) que venía bloqueando todos los despliegues del
equipo.

## 7. Casos comunes

- **"¿Por qué me rechaza si el catálogo todavía existe local?"** — es
  a propósito (R3): para ese caso ya está el camino normal, "Eliminar"
  en BC List + `mix motor.despublicar`. Esta herramienta es solo para
  cuando NO hay ningún rastro local.
- **Correr el comando dos veces, o contra un ambiente donde el
  catálogo ya no existe** — es seguro: el comando es idempotente,
  avisa que no había nada que borrar y no falla.

## 8. Errores y situaciones especiales

- **`--confirmar` no coincide con el nombre tipeado**: rechazado antes
  de tocar nada.
- **El catálogo SÍ existe local**: rechazado con mensaje explícito,
  apuntando a "BC List → Eliminar" como alternativa.
- **El catálogo ya no existe en el ambiente destino**: `mix
  motor.despublicar` responde de forma idempotente — avisa, no falla.

## 9. Resultado esperado

Después de propagar, confirmar en el ambiente destino que la tabla
física y el header del catálogo desaparecieron, y que cualquier ruta
de navegación que antes colisionaba con él vuelve a resolver sin
ambigüedad.
