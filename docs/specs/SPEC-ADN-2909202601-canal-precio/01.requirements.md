# SPEC-ADN-2909202601 — Lista de precios por canal ("lista de cadena")

**Documento:** Requirements · **Fase:** en definición.

## 0. Dependencias

Esta spec usa piezas que todavía no existen. Se construyen en la misma
spec o en otra, pero deben existir antes de que la cascada (§2)
funcione de punta a punta:

- **Precios dentro de una lista**: renglones de producto con precio por
  caja, sin impuestos, y vigencia (desde/hasta). Hoy una lista de
  precios solo tiene nombre.
- **Listas de la sucursal y su lista maestra**: una sucursal puede tener
  varias listas de precios habilitadas y, a lo más, una marcada como su
  lista maestra.
- **Pedido**: el documento que consume el precio resuelto (§3). Mientras
  no exista, la cascada se consume como servicio de consulta de precio.

## 1. Lista de cadena del canal

R1. Cada canal DEBE tener asignada **exactamente una** lista de precios
de cadena. Es obligatoria porque en la plataforma toda referencia a
otro catálogo es obligatoria. Un canal sin precios de cadena se asigna
a la lista "SIN LISTA DE CADENA" (ver R1.1).

R1.1. EL SISTEMA DEBE contar con dos listas de precios **vacías por
convención**: "SIN LISTA ESPECIAL", para clientes sin precios
especiales, y "SIN LISTA DE CADENA", para canales sin precios de cadena.
Como la búsqueda es producto por producto (R7), una lista vacía nunca
resuelve un precio y la cascada pasa sola al siguiente nivel. Estas dos
listas NO DEBEN tener productos; si se les cargan, esos precios empiezan
a ganar en todos los clientes o canales que apunten a ellas. (Decidido
con el usuario el 2026-09-29, para no volver opcionales las referencias
de la plataforma).

R2. La lista de cadena de un canal DEBE ser la misma para todas las
sucursales. EL SISTEMA NO DEBE permitir una lista de cadena distinta
por sucursal para un mismo canal.

R3. CUANDO se asigna una lista de cadena a un canal, EL SISTEMA DEBE
exigir que sea una lista de precios viva (no dada de baja), elegida del
catálogo de listas y nunca capturada como texto libre.

R4. CUANDO se intenta dar de baja una lista de precios que está
asignada como lista de cadena de algún canal (vivo o dado de baja), EL
SISTEMA DEBE rechazarlo. Primero hay que quitarla o reasignarla en ese
canal. Incluye canales dados de baja porque un canal reactivado debe
volver con una lista válida.

R5. CUANDO se cambia o se quita la lista de cadena de un canal, EL
SISTEMA DEBE aplicar el cambio solo a los precios que se resuelvan de
ahí en adelante, sin alterar los precios ya guardados en pedidos
existentes.

## 2. Cascada de precio base

R6. CUANDO se solicita el precio base de un producto para un cliente en
una fecha, EL SISTEMA DEBE buscarlo en este orden y quedarse con el
primer nivel que tenga ese producto con precio vigente en esa fecha:

  1. La lista especial del cliente.
  2. La lista de cadena del canal del cliente.
  3. La lista maestra de la sucursal del cliente.

R7. La búsqueda de R6 DEBE resolverse **producto por producto**. Que
la lista especial del cliente exista no implica que cubra todos los
productos: los que no estén en ella siguen al nivel 2 y, si hace falta,
al nivel 3.

R8. CUANDO un producto está en una lista pero su precio no está vigente
en la fecha solicitada (todavía no empieza o ya venció), EL SISTEMA
DEBE tratarlo como si no estuviera en esa lista y continuar con el
siguiente nivel.

R9. CUANDO la lista de un nivel no tiene el producto (incluidas las
listas vacías de R1.1), o la sucursal no tiene lista maestra, EL
SISTEMA DEBE saltar ese nivel y continuar con el siguiente, sin
considerarlo un error.

R10. CUANDO un producto no tiene precio vigente en ninguno de los tres
niveles, EL SISTEMA DEBE marcarlo como "sin precio", indicando cuál
producto es, y NO DEBE asignarle precio cero ni permitir venderlo sin
precio.

## 3. Trazabilidad

R11. CUANDO EL SISTEMA resuelve el precio base de un producto, DEBE
entregar junto con el precio el nivel del que salió (cliente, canal o
sucursal) y la lista exacta de la que salió.

R12. CUANDO se guarda un pedido, EL SISTEMA DEBE conservar en cada
renglón el precio base resuelto, su nivel y su lista de origen, de modo
que consultar el pedido después muestre exactamente lo que se cobró,
aunque las listas hayan cambiado.

## 4. Rendimiento

R13. CUANDO se resuelven los precios de un pedido completo, EL SISTEMA
DEBE resolver todos sus productos en una sola operación, con un tiempo
de respuesta que no crezca de forma notable con el número de renglones
del pedido ni con el número de niveles de la cascada.

## 5. Fuera de alcance

- Descuentos comerciales y por volumen, IEPS e IVA: se aplican sobre
  el precio base que resuelve esta spec, en su propia spec.
- Una lista maestra de toda la empresa como cuarto nivel, debajo de la
  sucursal. Si se necesita, se agrega aquí como un nivel más de R6.
- Lista de cadena distinta por sucursal (descartada en R2).
