# SPEC-ADN-2909202601 — Lista de precios por canal ("lista de cadena")

**Documento:** Design · **Fase:** en definición.

## 1. Decisiones de fondo

| # | Decisión | Por qué |
|---|---|---|
| D1 | La lista de cadena es un **campo referencia en `pty_cs_canales`**, no un BC aparte | Relación 1:1 (R1, R2): un BC aparte solo agrega un alta por canal, autómata y permisos, sin ganar nada |
| D2 | La cascada vive en una **Consulta SQL (BC tipo 4)**, `pty_sql_precio_base` | Los `pty_` no viajan en el repo: un módulo Elixir del núcleo que consulte tablas `pty_` rompe CI y los demás sistemas. La SQL View se publica con `motor.publicar` junto con sus catálogos y ya expone `GET /api/pty_sql_precio_base` |
| D3 | La vista resuelve el precio **vigente hoy** (hora de México) | Una vista no recibe parámetros (SPEC-SYS-2509202601). El precio de un pedido es el del día en que se captura |
| D4 | Con vigencias traslapadas del mismo producto en la misma lista, **gana la de "vigente desde" más reciente** | Programar un cambio de precio es agregar un renglón con fecha futura, sin tener que cerrar el anterior. Es determinista y no necesita validar traslapes |
| D5 | La sucursal del cliente se toma de la **dirección de entrega**: unidad de venta → sucursal | Un cliente puede tener direcciones en distintas sucursales. El precio depende de dónde se entrega, no de quién captura |

## 2. Modelo de datos

### 2.1 Prerrequisitos (§0 de requirements), incluidos en esta spec

**`pty_mat_precios`** (ya existe, maestro, autómata Activo/Baja) recibe
dos tablas detalle:

**`pty_mat_precios_det`**: precios de la lista.

| Campo | Tipo | Nota |
|---|---|---|
| `material` | referencia → `pty_mat_materiales` | |
| `precio_caja` | decimal(14,4) | Sin impuestos. 4 decimales para derivar el precio por pieza sin perder centavos |
| `vigente_desde` | date | Obligatorio |
| `vigente_hasta` | date | Opcional (vacío = sin fin) |

**`pty_mat_precios_branch`**: sucursales donde aplica la lista.

| Campo | Tipo | Nota |
|---|---|---|
| `branch` | referencia → `meta_schema_branch` | Catálogo de sistema referenciable (`@catalogos_sistema`) |
| `es_maestra` | boolean | Lista maestra de esa sucursal |

- **Unicidad de la maestra**: a lo más una lista maestra por sucursal,
  contando todas las listas. Se garantiza con un índice único parcial,
  `(pty_mat_precios_branch_branch) WHERE es_maestra AND delete_guid IS NULL`.
- La migración manual lleva `pty_mat_precios_branch` en el nombre (regla
  de CI para migraciones sobre tablas `pty_`).
- Permisos de detalle: insertar, actualizar y borrar renglones solo en
  el estado Activo del maestro.

### 2.2 Canal

**`pty_cs_canales`** + campo `lista_cadena`, referencia →
`pty_mat_precios`, opcional (R1). El combo solo ofrece listas vivas
(R3), igual que cualquier referencia.

### 2.3 Regla de baja de lista (R4)

En la transición `baja` de `pty_mat_precios`, regla PRE built-in
`sin_relacionados`:

```json
{"entidad": "pty_cs_canales", "campo_relacion": "pty_cs_canales_lista_cadena"}
```

Va **sin `filtro` por estado**. El `filtro` de `sin_relacionados` compara
contra un valor fijo, y el id del estado "Activo" de `pty_cs_canales` no
es el mismo en todos los ambientes, así que filtrar por él se rompe al
publicar. Por eso R4 bloquea también contra canales dados de baja.

Recomendación, fuera de esta spec: poner la misma regla contra
`pty_cs_clientes` (lista especial) y `pty_mat_precios_branch`.

## 3. La cascada: `pty_sql_precio_base`

Uso **Consulta** (no Diccionario), no visible en el menú.

```sql
WITH hoy AS (
  SELECT (now() AT TIME ZONE 'America/Mexico_City')::date AS fecha
),
candidatos AS (
  -- Nivel 1: lista especial del cliente
  SELECT d.id AS direccion_id, 1 AS nivel, c.pty_cs_clientes_mat_precios AS lista_id,
         d.branch_id, d.sales_unit_id
    FROM pty_cs_direcciones d
    JOIN pty_cs_clientes c ON c.id = d.encabezado_id
   WHERE c.pty_cs_clientes_mat_precios IS NOT NULL
  UNION ALL
  -- Nivel 2: lista de cadena del canal del cliente
  SELECT d.id, 2, ca.pty_cs_canales_lista_cadena, d.branch_id, d.sales_unit_id
    FROM pty_cs_direcciones d
    JOIN pty_cs_clientes c  ON c.id  = d.encabezado_id
    JOIN pty_cs_canales  ca ON ca.id = c.pty_cs_clientes_cs_canales
   WHERE ca.pty_cs_canales_lista_cadena IS NOT NULL
  UNION ALL
  -- Nivel 3: lista maestra de la sucursal de la dirección
  SELECT d.id, 3, pb.encabezado_id, d.branch_id, d.sales_unit_id
    FROM pty_cs_direcciones d
    JOIN meta_schema_sales_unit su ON su.id = d.pty_cs_direcciones_sales_unit
    JOIN pty_mat_precios_branch pb ON pb.pty_mat_precios_branch_branch = su.branch_id
                                  AND pb.pty_mat_precios_branch_es_maestra
                                  AND pb.delete_guid IS NULL
)
SELECT DISTINCT ON (k.direccion_id, p.pty_mat_precios_det_material)
       k.direccion_id,
       p.pty_mat_precios_det_material AS material_id,
       k.nivel,
       k.lista_id,
       p.pty_mat_precios_det_precio_caja AS precio_caja,
       p.pty_mat_precios_det_vigente_desde AS vigente_desde,
       k.branch_id, k.sales_unit_id
  FROM candidatos k
  JOIN pty_mat_precios l     ON l.id = k.lista_id AND l.delete_guid IS NULL
  JOIN pty_mat_precios_det p ON p.encabezado_id = k.lista_id AND p.delete_guid IS NULL
  CROSS JOIN hoy
 WHERE p.pty_mat_precios_det_vigente_desde <= hoy.fecha
   AND (p.pty_mat_precios_det_vigente_hasta IS NULL OR p.pty_mat_precios_det_vigente_hasta >= hoy.fecha)
 ORDER BY k.direccion_id, p.pty_mat_precios_det_material, k.nivel,
          p.pty_mat_precios_det_vigente_desde DESC;
```

Qué requisito cubre cada parte:

- **R6, R7**: `DISTINCT ON (dirección, material) ... ORDER BY nivel`.
  Gana el nivel más particular, producto por producto.
- **R8**: el `WHERE` de vigencia se aplica antes de elegir el nivel.
  Un precio vencido no bloquea el nivel siguiente.
- **R9**: cada rama descarta su nivel si no hay lista (`IS NOT NULL`,
  `JOIN`).
- **R10**: un producto **sin renglón** en la vista para esa dirección no
  tiene precio. Quien consume la vista (el pedido) lo bloquea.
- **R11**: salen `nivel` y `lista_id` junto con el precio.
- **Alcance de datos**: `branch_id` y `sales_unit_id` de la dirección
  son las columnas de control con las que la SQL View acota al usuario.

Pendientes para 03.tasks:

- **Estado de la lista**: el `JOIN` filtra `delete_guid`, pero falta
  excluir listas en estado Baja. Hay que confirmar cómo se ve el estado
  en la tabla sin depender de un id fijo por ambiente.
- **Zona horaria**: `America/Mexico_City` es fijo. Si hay clientes en
  otras zonas (frontera norte), un pedido capturado cerca de medianoche
  podría tomar el precio del día equivocado. Es aceptable en la fase 1.

### 3.1 Rendimiento (R13)

- Consultar por una dirección trae **todos sus productos con precio en
  una sola lectura** (unos cientos de renglones), sin importar cuántos
  renglones tenga el pedido ni cuántos niveles tenga la cascada.
- Postgres empuja un filtro sobre `direccion_id` y `material_id` dentro
  del `DISTINCT ON`, porque son sus llaves. No recorre las demás
  direcciones.
- Índice manual necesario:
  `pty_mat_precios_det (encabezado_id, pty_mat_precios_det_material, pty_mat_precios_det_vigente_desde DESC)`.
  Hay que verificar si el motor ya indexa las FK de referencia en
  `pty_cs_canales` y `pty_mat_precios_branch`.
- **Consultar la vista sin filtro** (el GET paginado actual) calcula
  todas las direcciones × todos los productos. Sirve para verificar,
  pero **no** es el camino del pedido. Ver §4.

## 4. Brecha de plataforma: consumir la vista por dirección

Hoy el `GET /api/pty_sql_*` solo pagina (`pagina`, `por_pagina`), **no
filtra por columna**. Una Consulta Ecto sí acepta parámetros vía
Endpoint (SPEC-SYS-1009202602), pero solo sobre catálogos tipo 1, no
sobre una SQL View. Para que el pedido o la app pidan "los precios de
la dirección X" hace falta uno de estos dos cambios, ambos de
**plataforma (área SYS), en su propia spec**:

- **(a) Recomendado**: filtros de igualdad por columna en el GET de una
  SQL View (`?direccion_id=123`), limitados a columnas declaradas como
  filtrables. Es genérico y sirve para cualquier SQL View.
- **(b)** Permitir una SQL View como catálogo base de una Consulta Ecto,
  y exponerla como Endpoint con parámetro.

Esta spec entrega la cascada funcionando y verificable en la base. El
consumo por dirección queda bloqueado hasta cerrar esa spec SYS. El
pedido todavía no existe, así que no retrasa nada hoy.
