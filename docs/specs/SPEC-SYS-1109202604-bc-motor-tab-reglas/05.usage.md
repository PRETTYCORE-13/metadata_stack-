# SPEC-SYS-1109202604 — BC Motor: Tab Reglas

**Documento:** Guía de uso · Grupos A-D, 100% verificados (documentación
retroactiva, 2026-09-11).

## 1. Objetivo

Editar, guardar y compilar el código Elixir de las reglas de negocio
PRE (antes de aplicar una transición) y POST (después de aplicarla) de
un catálogo, en caliente, sin salir del Motor BC.

## 2. ¿Quién utiliza esta funcionalidad?

Gente de ADN o del equipo de plataforma, editando un catálogo desde el
Motor BC (`/sysadmin/bc-list` → abrir un catálogo → tab "Reglas").
Nunca el usuario final directamente.

## 3. Conceptos que debo conocer

- **PRE**: código que corre antes de aplicar una transición de estado
  — si el primer error frena, no se aplica nada.
- **POST**: código que corre después de aplicar la transición — si
  falla, se deshace todo lo que se había hecho.
- **Stub**: el esqueleto de código que se muestra cuando el catálogo
  todavía no tiene PRE o POST propio — ya compila, con el nombre de
  módulo correcto, pero con un marcador de "sin completar".
- **Compilar ≠ Guardar por separado**: no existen esas dos acciones
  como pasos distintos; "Compilar" ya incluye validar sintaxis y
  guardar, en un solo botón.

## 4. Flujo general

1. Abrir un catálogo en el Motor BC.
2. Entrar al tab "Reglas".
3. Elegir el sub-tab PRE o POST (cada uno con su propio textarea).
4. Editar el código.
5. Click en "Compilar" — procesa PRE y POST juntos, cada uno de forma
   independiente.

## 5. Guía paso a paso

### 5.1 Editar y compilar una regla

1. Entrar al tab "Reglas" del catálogo.
2. Elegir el sub-tab PRE o POST.
3. Si el catálogo no tiene código propio todavía, aparece un stub ya
   armado (no un textarea vacío) con un aviso de "sin completar" junto
   al textarea.
4. Editar el código en el textarea.
5. Click en "Compilar" (un solo botón para ambos bloques, PRE y POST
   se envían juntos en el mismo submit).
6. El sistema valida la sintaxis de cada bloque por separado:
   - Si un bloque tiene error de sintaxis: no se guarda nada de ese
     bloque, se muestra el error con su línea. El otro bloque se
     procesa igual, sin verse afectado.
   - Si un bloque es sintácticamente válido: se guarda siempre,
     aunque la compilación posterior falle por otro motivo (en ese
     caso el mensaje aclara "se guardó, pero no compiló").

### 5.2 Copiar el código de un bloque

1. Click en el botón "Copiar" junto al textarea de PRE o POST.
2. El código completo de ese bloque queda en el portapapeles.

### 5.3 Qué pasa si se intenta salir sin guardar

1. Si se editó un textarea y todavía no se guardó ese cambio, al
   intentar cerrar/recargar la pestaña del navegador o navegar a otra
   pantalla dentro de la app, el sistema pregunta antes de descartar
   el cambio.
2. Se puede cancelar esa navegación y seguir editando, o confirmar y
   perder el cambio no guardado.

## 6. Ejemplos prácticos

### Ejemplo: un bloque falla, el otro se guarda igual

Se edita PRE con un error de sintaxis y POST con código válido, y se
hace click en "Compilar": PRE muestra el error de sintaxis y no
persiste nada; POST se guarda y compila normalmente, sin verse
afectado por el error del otro bloque.

### Ejemplo: código válido que no compila

Se edita un bloque con sintaxis Elixir correcta pero que referencia
algo inexistente (error semántico): el sistema lo guarda igual, y
muestra "Se guardó, pero no compiló: <motivo>" — el texto no se pierde,
solo falta resolver el error para que quede corriendo.

## 7. Casos comunes

- **En producción no se puede editar** — es esperado: la edición en
  caliente solo está disponible en dev/test; en producción el código
  se muestra en solo lectura, con el texto de que se llega ahí por
  git + release, no desde esta pantalla.
- **El aviso de "sin completar" sigue apareciendo aunque ya escribí
  código real** — revisar que no haya quedado pegado el marcador de
  stub por error; el aviso se recalcula sobre cualquier código actual,
  no solo sobre el stub original.
- **"Guardado sin compilar — el motor corre la versión anterior"** — un
  guardado exitoso en base no implica que la lógica ya cambió en
  memoria; hay que volver a compilar para que el motor use la versión
  nueva.

## 8. Errores y situaciones especiales

- Un error de sintaxis nunca persiste nada de ese bloque — no hay
  guardado parcial de código roto.
- El aviso de cambios sin guardar (§5.3) es por bloque: guardar PRE no
  descarta el aviso de POST si POST todavía tiene cambios pendientes,
  y viceversa.
- "Publicar" (llevar las reglas a otros ambientes) NO es una acción de
  este tab — se hace con `mix motor.publicar <catalogo>` o el flujo
  normal de git + CI/CD.

## 9. Resultado esperado

Después de compilar un bloque sin errores, el mensaje confirma
"Guardado y compilado: <módulo>" y el aviso de "sin completar" (si
existía) desaparece una vez que el marcador de stub ya no está en el
texto. El motor de estados usa la lógica nueva en la siguiente
transición que dispare ese tipo (pre/post).
