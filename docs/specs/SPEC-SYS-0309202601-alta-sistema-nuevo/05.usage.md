# SPEC-SYS-0309202601 — Alta de Sistema Nuevo

**Documento:** Guía de uso · Grupos A-G ejecutados y cerrados en
producción real, incluido un cliente real de punta a punta ("ennova",
2026-09-07) — ver nota en §8 sobre el encabezado de `03.tasks.md`.

## 1. Objetivo

Dar de alta un sistema (cliente) nuevo en la infraestructura
compartida — base de datos propia, despliegue propio, dominio propio
con HTTPS — y a partir de ahí poder publicarle catálogos/actualizaciones
sin riesgo de afectar a otro sistema.

## 2. ¿Quién utiliza esta funcionalidad?

- **Equipo de Desarrollo (Dev)**: corre el mecanismo de alta desde su
  propia terminal (con acceso SSH directo al servidor) — nunca ADN.
- **ADN**: publica catálogos a un sistema ya dado de alta indicando
  siempre explícitamente a cuál apunta (por línea de comando o desde
  un selector en BC List) — no puede dar de alta un sistema nuevo por
  su cuenta.

## 3. Conceptos que debo conocer

- **Sistema / cliente**: un despliegue completo e independiente,
  identificado por un nombre corto (minúsculas, letras/dígitos/
  guiones).
- **Canal** (`unstable`/`testing`/`stable`): los tres escalones de
  confianza por los que pasa una mejora del núcleo compartido antes de
  llegar a un cliente real — se dan de alta con el mismo mecanismo que
  cualquier sistema, pero NUNCA entran al registro de clientes. El
  detalle de cómo se mueve una versión entre canales y hacia un
  cliente vive en `SPEC-SYS-1809202603-propagacion-extensiones` — no
  se repite acá.
- **`priv/sistemas.json`**: el registro de sistemas válidos — lo que
  valida si `--sistema=` apunta a algo real.
- **Servidor Postgres compartido**: una sola instancia con una base
  por sistema, pensada para poder apuntar a un servicio de nube real
  más adelante sin cambiar código, solo variables de entorno.

## 4. Flujo general

1. Dev corre el mecanismo de alta desde el devcontainer (Linux — no
   confiable desde una terminal Windows nativa).
2. Se valida que el nombre no exista ya, contra tres fuentes: el
   registro de sistemas, el clúster directo, y la configuración de
   ruteo del servidor — para no chocar ni siquiera con un dominio
   tomado por otra funcionalidad ajena a este mecanismo.
3. Se crea la base de datos, se aplica el despliegue, se migra, se
   expone el dominio con HTTPS, y se registra el sistema como último
   paso.
4. El usuario final de ese cliente completa el wizard de primer
   arranque desde el navegador (crea su Empresa, su sysadmin, y de
   paso una Sucursal/Almacén/Unidad de venta por default) — esto NO
   lo hace el mecanismo de alta, corre después, la primera vez que
   alguien entra al sistema nuevo.
5. ADN publica catálogos a ese sistema indicando siempre el sistema de
   destino explícito — se rechaza cualquier sistema no registrado.

## 5. Guía paso a paso

### 5.1 Dar de alta un sistema nuevo

```
mix motor.alta <ambiente> <sistema> <imagen>
```

Ejemplo real: `mix motor.alta Metadata ennova ghcr.io/prettycore-13/metadata_stack:latest`
— crea la base `db_ennova`, el despliegue `metadata-ennova`, expone
`ennova.ventaenruta.com.mx` con HTTPS válido, y registra `ennova` en
`priv/sistemas.json` (commit + push).

### 5.2 Completar el primer arranque

1. Entrar por navegador al dominio del sistema recién creado — redirige
   a `/primer-arranque`.
2. Completar el wizard con las credenciales reales de sysadmin — crea
   la Empresa y, de paso, una Sucursal/Almacén/Unidad de venta por
   default (editables después desde la UI).

### 5.3 Publicar un catálogo a ese sistema

```
mix motor.publicar <catalogo> --sistema=<sistema>
```

`--sistema=` es obligatorio, sin ningún valor por default — se
rechaza si `<sistema>` no está en `priv/sistemas.json`. También
disponible sin terminal: en BC List, los modales de publicar/
despublicar tienen un selector de sistema, con el botón de confirmar
deshabilitado hasta elegir uno.

Para probar un catálogo antes de mandarlo a cualquier cliente real,
`--sistema=unstable` está permitido (nunca `testing`/`stable`, que
solo reciben por promoción entre canales — ver
`SPEC-SYS-1809202603-propagacion-extensiones`).

### 5.4 Actualizar o promover una versión ya existente

No es parte de este mecanismo — ver la guía de uso de
`SPEC-SYS-1809202603-propagacion-extensiones` (§5) para mover una
versión entre canales o aplicarla a un cliente.

## 6. Ejemplos prácticos

### Ejemplo: intentar dar de alta un nombre ya tomado

Si `<sistema>` ya existe en `priv/sistemas.json`, o ya hay un
despliegue con ese nombre en el clúster, o ya hay un bloque de ruteo
para ese dominio (aunque pertenezca a otra funcionalidad, no a
metadata_stack), el mecanismo rechaza el alta antes de crear nada.

### Ejemplo: alta interrumpida a mitad de camino

Si el proceso corta antes de terminar (por ejemplo, falla la
aplicación de manifiestos), volver a correr el mismo comando con el
mismo nombre retoma donde cortó — cada paso es re-ejecutable sin
duplicar recursos ni fallar por "ya existe".

## 7. Casos comunes

- **"El comando se cuelga o vuelve sin salida"** — correrlo desde el
  devcontainer (Linux), no desde una terminal Windows nativa; es un
  problema conocido de cómo Windows maneja la conexión SSH del
  mecanismo, no del mecanismo en sí.
- **"`mix motor.publicar` rechaza mi sistema"** — confirmar que el
  nombre esté exactamente como aparece en `priv/sistemas.json`
  (sensible a mayúsculas/formato); un canal (`unstable`/`testing`/
  `stable`) nunca aparece ahí salvo `unstable`, que sí es un destino
  válido para publicar de prueba.

## 8. Errores y situaciones especiales

- **Nota sobre el estado de este documento**: al momento de escribir
  esta guía, el encabezado de `03.tasks.md` todavía dice "🚧 en
  construcción", pero el cuerpo del documento muestra los Grupos A-G
  cerrados, incluido un cierre de spec explícito (2026-09-07) con un
  cliente real de punta a punta. Esta guía se escribió a partir de esa
  evidencia de cierre real — vale la pena corregir el encabezado de
  `03.tasks.md` si el estado real es efectivamente "cerrado".
- **Alta parcial**: nunca queda a medio camino de forma silenciosa —
  un sistema con recursos creados pero sin registrar en
  `priv/sistemas.json` no es válido para publicar nada (el mismo
  chequeo de "¿está registrado?" ya lo bloquea), y el mecanismo es
  re-ejecutable para terminarlo.
- **Para el detalle operativo completo** (prerrequisitos de una sola
  vez, troubleshooting real encontrado en producción), ver
  `docs/onboarding-nuevo-sistema.md` — el runbook vivo de este
  mecanismo.

## 9. Resultado esperado

Después de dar de alta un sistema, confirmar: el dominio
`<sistema>.ventaenruta.com.mx` responde por HTTPS y muestra
`/primer-arranque`; el sistema aparece en `priv/sistemas.json`; y
`mix motor.publicar --sistema=<sistema>` deja de rechazarlo.
