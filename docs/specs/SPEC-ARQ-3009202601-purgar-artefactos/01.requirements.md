# SPEC-ARQ-3009202601 — Purgar artefactos

**Documento:** Requirements · **Fase:** ✅ aprobada (2026-09-30), incluido
el ajuste en R4 hecho al diseñar.

## 1. Propósito

Los 4 desarrolladores publican artefactos de negocio (catálogos `pty_*`)
a `unstable` para probarlos, y muchos se descartan después. Hoy, quitar
uno publicado (BC List → Eliminar + `mix motor.despublicar`) tiene tres
limitaciones:

1. **Depende de la máquina del autor.** `motor.despublicar` exige que el
   artefacto ya se haya borrado local, con su migración de `DROP` en
   `priv/repo/migrations/`. Un dev no puede quitar lo que publicó otro.
2. **Deja una lápida.** El release `bc-<catalogo>` se reemplaza por un
   paquete que solo trae la migración de `DROP`, y `ci.yml` lo vuelve a
   incluir en cada build para siempre. La lápida llega a `testing`,
   `stable` y los clientes, y registra en su `schema_migrations` dos
   migraciones de un artefacto que nunca existió ahí.
3. **No tiene pantalla ni registro** de quién quitó qué.

Además, una prueba que nadie identificó como tal puede avanzar hasta
los clientes, y hoy no hay forma de quitarla ambiente por ambiente.

Esta spec define un mecanismo para **purgar** un artefacto de cualquier
sistema destino, como si nunca hubiera existido, desde una pantalla
compartida por todo el equipo.

## 2. Alcance

**Incluye:**
- Pantalla **Configuración › Developer › Purgar** con las pestañas
  **Artefactos** y **Bitácora**.
- **Retirar** un artefacto: dejar de incluirlo en cualquier build
  futuro (acción global, una sola vez).
- **Purgar** un artefacto en un sistema destino puntual (canal
  `unstable`/`testing`/`stable` o cliente de `priv/sistemas.json`):
  tablas, metadata y registro de sus migraciones.
- Respaldo automático de las tablas antes de purgar en un cliente, con
  retención de 30 días.
- Bitácora de purgas, guardada en el sistema destino.
- Rol de sistema nuevo `acceso_sysadmin_purgar`.

**No incluye:**
- Restaurar un artefacto purgado. El respaldo sirve para una
  recuperación manual de datos, no es un "deshacer".
- Prevenir que una prueba avance entre canales (marca "en prueba" del
  autor + bloqueo de la propagación `unstable → testing`). Va en otra
  SPEC ARQ aparte.
- Purgar artefactos que no sean `pty_*` (catálogos core
  `meta_schema_*`).
- Reemplazar BC List → Eliminar, que sigue siendo para el trabajo local
  mientras un artefacto se construye.

## 3. Contexto real (2026-09-30)

- Los artefactos publicados viven en GitHub Releases `bc-<catalogo>`.
  `ci.yml` descarga **todos** los `bc-*` en cada build y los incluye en
  la imagen. Esa imagen es la que se propaga `unstable → testing →
  stable` y después a los clientes.
- El paquete de `bc-<catalogo>` incluye los archivos del catálogo **y
  de todos los que referencia** (cierre transitivo,
  `MetaSchemaContext.calcular_paquete_publicacion/1`). Un artefacto X
  puede viajar dentro del release de otro artefacto Y.
- En cada deploy corren las migraciones pendientes y después
  `import_meta`, que crea la metadata de cada `.meta.json` de la
  imagen. Si se borran las tablas, la metadata y las filas de
  `schema_migrations` de X en un sistema cuya imagen todavía trae X, el
  siguiente deploy o reinicio **lo vuelve a crear**. Es la misma familia
  de problema que tumbó tablas en `testing` el 2026-09-21
  (SPEC-ARQ-1809202603).

## 4. Requisitos funcionales (EARS)

### R1. Acceso por rol
EL SISTEMA DEBE mostrar la opción "Purgar" en el submenú "Developer", y
permitir entrar a su pantalla, solo a usuarios con el rol de sistema
`acceso_sysadmin_purgar` (tipo sysadmin, sembrado por migración, igual
que el resto de la familia `acceso_sysadmin_*`). El rol se otorga desde
la pestaña "Sysadmin" de usuarios, como las demás capacidades.

### R2. Lista de artefactos independiente de la máquina local
CUANDO un usuario abre la pestaña Artefactos, EL SISTEMA DEBE listar los
artefactos `pty_*` a partir de lo realmente publicado: los releases
`bc-*` y los catálogos presentes en cada sistema destino. Nunca debe
depender de la base ni de los archivos locales de quien la abre. Por
cada artefacto debe mostrar si está retirado y en qué sistemas destino
existe todavía.

### R3. Catálogos detalle como unidad
CUANDO se retira o purga un catálogo maestro, EL SISTEMA DEBE incluir
sus catálogos detalle en la misma operación. Un catálogo detalle no se
puede retirar ni purgar por separado de su maestro.

### R4. Retirar
CUANDO un usuario retira un artefacto X, EL SISTEMA DEBE sacarlo de los
releases que restaura cada build (`bc-*`) para que ningún build futuro
lo incluya. Su paquete se conserva como **inventario** del retiro (qué
tablas y qué migraciones tenía), porque las purgas en testing, stable y
los clientes pueden ocurrir días después, cuando ninguna imagen nueva
trae ya esos archivos.
SI X viaja además dentro del paquete de otro artefacto Y sin que Y
dependa de él (una carpeta que lo contiene, o un paquete viejo de Y),
ENTONCES EL SISTEMA DEBE sacar los archivos de X de ese paquete y volver
a subirlo sin ellos, sin tocar ningún otro archivo de Y, y registrar en
la bitácora qué paquetes modificó. Si Y sí depende de X, aplica R5
(bloquear).
SI al sacar X un paquete queda vacío, ENTONCES EL SISTEMA DEBE bloquear y
nombrar ese paquete.
CUANDO X ya no existe en ningún sistema destino, EL SISTEMA DEBE ofrecer
borrar su inventario de forma definitiva.
*(Ajuste 2026-09-30, a pedido explícito, al construir el Grupo D:
originalmente decía "bloquear y nombrar esos artefactos", pero los
paquetes reales se traslapan (una carpeta publicada trae todos sus
catálogos) y casi nada se habría podido retirar.)*
*(Ajuste 2026-09-30, al diseñar: originalmente decía "borrar el release
`bc-X`", pero sin inventario no se puede limpiar `schema_migrations` en
las purgas posteriores, ver `02.design.md` §4.)*

### R5. Bloqueo por dependencias
SI otro artefacto depende de X en el sistema destino (llave foránea
hacia sus tablas, o una Consulta SQL/Diccionario que lee de ellas),
ENTONCES EL SISTEMA DEBE bloquear el retiro o la purga sin tocar nada,
y sugerir qué dependencia retirar o purgar antes.

### R6. Purgar solo donde ya no puede revivir
SI la imagen que corre en el sistema destino todavía incluye X,
ENTONCES EL SISTEMA DEBE bloquear la purga y explicar que primero hay
que retirar X y llevar a ese sistema una imagen sin él.
- En `unstable`, EL SISTEMA DEBE ofrecer hacerlo en un solo paso:
  retirar, reconstruir y desplegar `unstable`, y después purgar.
- En `testing`, `stable` y los clientes, la imagen nueva llega por el
  camino normal (`mix motor.propagar_extension` /
  `mix motor.propagar_extension_a_sistema`). Esta spec no lo salta.

### R7. Purga completa, sin lápida
CUANDO se purga X en un sistema destino, EL SISTEMA DEBE borrar ahí sus
tablas físicas, toda su metadata (header, detalles, estados,
transiciones, permisos, navegación, plantillas y cualquier otro
registro ligado) y las filas de `schema_migrations` de sus migraciones.
No debe generar ninguna migración nueva ni dejar rastro que viaje a
otros sistemas.

### R8. Aviso cuando hay datos
SI las tablas de X tienen registros en el sistema destino, ENTONCES EL
SISTEMA DEBE mostrar cuántos tiene cada tabla y pedir confirmación
explícita antes de seguir.

### R9. Confirmación por nombre
CUANDO se va a retirar o purgar, EL SISTEMA DEBE exigir que el usuario
escriba el nombre exacto del artefacto. Si no coincide, no se ejecuta.

### R10. Respaldo en clientes
CUANDO se purga X en un cliente de `priv/sistemas.json`, EL SISTEMA DEBE
guardar antes un respaldo de las tablas de X en el servidor de ese
cliente. El respaldo nunca sale de ese servidor. SI el respaldo falla,
ENTONCES la purga no se ejecuta.
En los canales `unstable`, `testing` y `stable` no se respalda.

### R11. Retención del respaldo
EL SISTEMA DEBE borrar los respaldos de purga con más de 30 días.

### R12. Bitácora
CUANDO se ejecuta un retiro o una purga, termine bien o mal, EL SISTEMA
DEBE registrar: quién, qué artefacto, qué acción, en qué sistema
destino, cuándo, cuántos registros tenía cada tabla, la ruta del
respaldo (si aplica) y el resultado. La purga se registra en la base del
sistema destino. La pestaña Bitácora debe mostrar los registros de
todos los sistemas destino, sin importar quién los hizo.

### R13. Idempotencia
CUANDO se purga X en un sistema donde X ya no existe, o donde quedó
purgado a medias, EL SISTEMA DEBE terminar lo que falte sin fallar, y
avisar si no había nada que borrar. Lo mismo al retirar un artefacto ya
retirado.

### R14. Copia local de quien purga
CUANDO quien purga tiene X en su máquina, EL SISTEMA DEBE ofrecerle
(opcional) borrarlo también local: tablas, metadata, `.ex`, exports,
reglas **y sus migraciones**, sin generar migración de `DROP`. Las
copias locales de los demás desarrolladores no se tocan.

### R15. Consultas y Consultas SQL también se purgan
*(Agregado 2026-09-30, a pedido explícito, al cerrar el Grupo B.)*
EL SISTEMA DEBE tratar como artefacto, además de los catálogos, a las
Consultas (`schema_context_type` 3) y a las Consultas SQL /
Diccionarios / Servicios (`schema_context_type` 4), con las mismas
reglas de R2 a R14. Purgar una Consulta SQL borra su vista o función de
Postgres, su registro de Consulta SQL y su metadata. Purgar una
Consulta borra su metadata.
SI la Consulta o Consulta SQL está en uso (un campo que usa el
Diccionario, un Endpoint publicado o reglas que usan el Servicio),
ENTONCES EL SISTEMA DEBE bloquear y decir qué la usa.
Las carpetas de navegación (`schema_context_type` 2) **no** se purgan:
son estructura del menú, no pruebas.

## 5. Requisitos no funcionales

- **NF1.** Ninguna operación usa `Ecto.Migrator` con `:to`/`:step`
  sobre un sistema remoto (lección de SPEC-ARQ-1809202603). Todo se
  hace con nombres exactos de tablas y versiones.
- **NF2.** Las consultas remotas de la lista (R2) no deben bloquear la
  pantalla. Un sistema destino caído se muestra como error en su fila,
  sin ocultar los demás.
- **NF3.** La purga en un sistema destino es atómica a nivel base:
  tablas, metadata y `schema_migrations` se borran en una sola
  transacción. El respaldo (R10) ocurre antes y fuera de ella.

## 6. Decisiones (2026-09-30)

1. **R14** (limpieza local opcional) se queda en esta spec.
2. **`mix motor.despublicar`** se conserva por ahora, sin cambios, como
   alternativa de borrado por migración. Esta spec no lo toca. Su retiro
   queda para una decisión posterior.
