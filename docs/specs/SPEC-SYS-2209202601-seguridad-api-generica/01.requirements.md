# Requirements — Seguridad real en la API genérica (`/api`)

## Contexto

Hallazgo real (2026-09-22, a partir de una duda del usuario sobre el tab
"Contrato" de BC Motor): el scope `/api` (`router.ex:103-138`) corre bajo
el pipeline `:api` (`fetch_session` + `fetch_current_scope_for_usuario`,
sin ningún plug que EXIJA sesión) — un request sin login llega igual, con
`current_scope` vacío, y nada lo detiene después.

**Estado real, verificado directo contra el código (no supuesto):**

| Ruta | Controller | Protección hoy |
|---|---|---|
| `roles`, `permisos`, `usuarios/:id/roles` | Rol/Permiso/UsuarioRolController | Ya tiene `RequierePermiso` — fuera de alcance |
| `meta_schema_header` (crear/editar catálogo) | MetaSchemaHeaderController | Ninguna |
| `meta_schema_estados`, `meta_schema_transiciones` (definir autómata) | MetaEstadoController / MetaTransicionAdminController | Ninguna |
| `catalogos/:tabla/{impacto,validar_motor,completitud}` + `DELETE catalogos/:tabla` | CatalogoAdminController | Ninguna — borra el catálogo entero sin login |
| `:tabla` CRUD (leer/crear/editar/borrar registros) | CatalogoController | Ninguna |
| `:tabla/:id/transiciones` (ejecutar transición) | MetaTransicionController | "Accidental" — el motor de estados deniega si `contexto["usuario_id"]` es `nil`, pero no hay ningún plug; si el `contexto` no trae esa llave, se trata como llamada interna confiable y NO se chequea nada |

**Pieza reusable, ya existente, verificada:**
`MetadataAppWeb.Plugs.RequierePermiso` (`plugs/requiere_permiso.ex`) ya
soporta recurso dinámico — sin `recurso:` en las opciones, lo toma de
`conn.params["tabla"]`. Internamente llama a `MetadataApp.Permissions.
can?/3` (`permissions.ex:37`), la MISMA función que ya usa toda la UI web
(`recurso` = `schema_context_name` del catálogo, `accion` ∈ `leer/crear/
editar/eliminar`, `administrador?/2` como bypass total). No hace falta
ninguna lógica de permisos nueva — solo conectar el plug donde falta.

Sin ningún consumidor real conocido de esta API hoy (verificado: la app
móvil usa `/api/movil/*`, un sistema de token completamente separado) —
exigir login/permiso no rompe ninguna integración existente.

## Requisitos

### Autenticación (toda ruta de `/api` sin protección hoy)

R1. CUANDO un request llega a cualquier ruta de `/api` listada arriba como
"Ninguna" o "Accidental" sin una sesión de Usuario válida, EL SISTEMA DEBE
rechazarlo con `401` antes de tocar cualquier dato — nunca ejecutar la
acción y filtrar después.

### Permisos por catálogo (rutas con `:tabla` en la URL)

R2. CUANDO un Usuario con sesión válida pide `GET /api/:tabla` o
`GET /api/:tabla/:id`, EL SISTEMA DEBE exigir el permiso `{recurso:
tabla, accion: "leer"}` (vía `Permissions.can?/3`) — `403` si no lo
tiene.

R3. CUANDO un Usuario con sesión válida pide `POST /api/:tabla`, EL
SISTEMA DEBE exigir `{recurso: tabla, accion: "crear"}`.

R4. CUANDO un Usuario con sesión válida pide `PUT`/`PATCH
/api/:tabla/:id`, EL SISTEMA DEBE exigir `{recurso: tabla, accion:
"editar"}`.

R5. CUANDO un Usuario con sesión válida pide `DELETE /api/:tabla/:id`, EL
SISTEMA DEBE exigir `{recurso: tabla, accion: "eliminar"}`.

### Transiciones de estado (ejecutar, no definir)

R6. CUANDO un Usuario con sesión válida pide `GET
/api/:tabla/:id/transiciones` (listar las disponibles) o `POST
/api/:tabla/:id/transiciones/:accion` (ejecutar una), EL SISTEMA DEBE
exigir el MISMO permiso que ya evalúa `MetaStateEngine.
verificar_permiso_transicion/3` para esa transición puntual — nunca dejar
que la falta de `usuario_id` en el contexto se interprete como "llamada
interna confiable" cuando el origen es HTTP externo (R1 ya lo bloquea
antes de llegar acá, pero el chequeo interno queda alineado con R1, no
contradictorio).

### Administración de catálogos (crear/definir/borrar la estructura)

R7. CUANDO un Usuario con sesión válida pide crear o editar un header
(`POST`/`PUT /api/meta_schema_header`), agregar un estado o una
transición al autómata (`POST /api/meta_schema_estados`,
`POST /api/meta_schema_transiciones`), o consultar impacto/validar
motor/completitud de un catálogo (`GET
/api/catalogos/:tabla/{impacto,validar_motor,completitud}`), EL SISTEMA
DEBE exigir el mismo permiso de plataforma que ya protege las pantallas
equivalentes de BC Motor/BC List (`recurso: "sysadmin_bc"`, `accion:
"editar"` para escritura, `"leer"` para las 3 rutas de solo consulta).

R8. CUANDO un Usuario con sesión válida pide `DELETE
/api/catalogos/:tabla` (borrar un catálogo completo), EL SISTEMA DEBE
exigir `{recurso: "sysadmin_bc", accion: "editar"}` — mismo criterio que
R7, ninguna acción destructiva de esta magnitud queda con un permiso más
débil que "editar la estructura".

### Sin regresión para quien ya tiene acceso legítimo

R9. Un Usuario con el rol "administrador" (bypass total, `Permissions.
administrador?/2`) DEBE seguir teniendo acceso completo a TODA esta API,
sin ningún cambio de comportamiento — esta spec agrega una puerta, no le
quita la llave maestra a quien ya la tenía.

R10. Los endpoints ya protegidos hoy (`roles`, `permisos`,
`usuarios/:id/roles`) NO DEBEN modificarse — fuera de alcance, ya
correctos.

## Fuera de alcance (explícito)

- `/api/consultas/*` (Endpoints por Consulta, `SPEC-SYS-1009202602`) — ya
  tiene su propio mecanismo de API key, no relacionado con sesión de
  Usuario.
- `/api/movil/*` — sistema de token separado (`SPEC-API-0409202601`), sin
  cambios acá.
- Cambiar el modelo de permisos en sí (qué roles/permisos existen, cómo
  se conceden desde `CatalogoPermisosLive`) — se reusa tal cual está.
