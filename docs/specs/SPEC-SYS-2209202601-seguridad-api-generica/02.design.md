# Design — Seguridad real en la API genérica (`/api`)

## 1. Pieza que ya existe, sin tocar

`MetadataAppWeb.Plugs.RequierePermiso` (`plugs/requiere_permiso.ex`) ya
hace exactamente lo que R1-R9 piden: 401 sin sesión, 403 sin el permiso,
`recurso` dinámico desde `conn.params["tabla"]` si no se pasa fijo,
`Permissions.can?/3` (con bypass de administrador ya adentro) como único
motor de decisión. **No se toca su lógica de 401/403/recurso** — mismo
patrón exacto que ya usa `RolController` (`plug ... [recurso: ...,
accion: ...] when action in [...]`).

## 2. Único cambio al plug: `accion` también dinámica (R6)

Hoy `accion = Keyword.fetch!(opts, :accion)` — siempre fija. Para
`MetaTransicionController.ejecutar/2` (R6), el permiso a chequear es el
NOMBRE de la transición pedida (`conn.params["accion"]`, ej. "alta",
"baja"), no un string fijo — exactamente la misma pareja
`{recurso: tabla, accion: transicion.accion}` que ya evalúa
`MetaStateEngine.verificar_permiso_transicion/3` más adentro.

```elixir
accion =
  Keyword.get(opts, :accion) ||
    conn.params["accion"] ||
    raise "RequierePermiso: falta :accion (ni fijo en el plug ni conn.params[\"accion\"])"
```

Mismo criterio simétrico que ya existe para `recurso`/`"tabla"` — no es
una pieza nueva de diseño, es la misma idea aplicada al otro lado del
par recurso/acción.

## 3. Plugs nuevos, por controller (R1-R8)

**`CatalogoController`** (CRUD genérico, recurso dinámico = `:tabla`):

```elixir
plug MetadataAppWeb.Plugs.RequierePermiso, [accion: "leer"] when action in [:index, :show]
plug MetadataAppWeb.Plugs.RequierePermiso, [accion: "crear"] when action in [:create]
plug MetadataAppWeb.Plugs.RequierePermiso, [accion: "editar"] when action in [:update]
plug MetadataAppWeb.Plugs.RequierePermiso, [accion: "eliminar"] when action in [:delete]
```

**`MetaTransicionController`** (recurso dinámico = `:tabla`, acción fija
para listar / dinámica para ejecutar):

```elixir
plug MetadataAppWeb.Plugs.RequierePermiso, [accion: "leer"] when action in [:index]
plug MetadataAppWeb.Plugs.RequierePermiso, [] when action in [:ejecutar]
```

La segunda línea no pasa `accion:` a propósito — la toma de
`conn.params["accion"]` (pieza 2).

**`MetaSchemaHeaderController`**, **`MetaEstadoController`**,
**`MetaTransicionAdminController`** (definir la estructura — recurso
FIJO `"sysadmin_bc"`, R7, mismo recurso que ya usa BC Motor/BC List en
la web):

```elixir
plug MetadataAppWeb.Plugs.RequierePermiso, [recurso: "sysadmin_bc", accion: "leer"] when action in [:index, :show]
plug MetadataAppWeb.Plugs.RequierePermiso, [recurso: "sysadmin_bc", accion: "editar"] when action in [:create, :update]
```

(`MetaEstadoController`/`MetaTransicionAdminController` solo tienen
`:index`/`:create` — se omite la línea de `:show`/`:update` donde la
acción no existe.)

**`CatalogoAdminController`** (impacto/validar_motor/completitud = solo
consulta; `delete` = acción destructiva, R8):

```elixir
plug MetadataAppWeb.Plugs.RequierePermiso, [recurso: "sysadmin_bc", accion: "leer"] when action in [:impacto, :validar_motor, :completitud]
plug MetadataAppWeb.Plugs.RequierePermiso, [recurso: "sysadmin_bc", accion: "editar"] when action in [:delete]
```

## 4. Por qué ningún controller necesita lógica propia

Los 6 controllers de arriba hoy no tienen ningún `plug`/chequeo de auth
(confirmado, ver `01.requirements.md`) — el cambio completo por
controller es agregar 1-2 líneas de `plug`, nunca tocar las funciones de
acción (`index/2`, `create/2`, etc.) en sí. `MetaTransicionController.
ejecutar/2` sigue llamando a `MetaStateEngine.
verificar_permiso_transicion/3` exactamente igual que hoy — ese chequeo
interno queda como segunda capa (defensa en profundidad), no se
elimina; con el plug ya filtrando antes, nunca debería llegar a negar
ahí salvo un bug — si eso pasa, es señal de que las dos capas
divergieron y hay que investigar, no motivo para sacar ninguna de las
dos.

## 5. Riesgo conocido y cómo se cubre

Un permiso `recurso: "<catalogo>"` que hoy NO existe para ningún rol
(catálogo nuevo, nunca se le asignó explícitamente a nadie en
`CatalogoPermisosLive`) deniega a TODOS excepto administrador — mismo
comportamiento que ya tiene la UI web hoy (`Permissions.can?/3` es la
misma función), así que no es una regresión nueva, es coherencia con lo
que ya pasa si alguien intenta entrar a ese catálogo desde la pantalla
web sin permiso. Se verifica en Grupo B (tasks.md) contra un catálogo
real sin ningún permiso concedido.

## 6. Cómo quedan resueltos R1-R10

R1 (401 sin sesión) y R2-R8 (403 por permiso, por ruta) — ambos salen
gratis del mismo `RequierePermiso`, ya sea con `recurso`/`accion` fijos
(R7-R8) o dinámicos (R2-R6). R9 (administrador sin regresión) — bypass
ya integrado en `Permissions.can?/3`, sin tocar. R10 (roles/permisos
intactos) — ningún archivo de esos 3 controllers se toca en esta spec.
