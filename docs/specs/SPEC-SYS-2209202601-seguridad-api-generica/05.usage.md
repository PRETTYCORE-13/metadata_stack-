# Uso — Seguridad real en la API genérica (`/api`)

## Qué cambia para quien ya consume esta API

Si un sistema externo o interno ya le pega a `/api/<catalogo>` (o a
`/api/meta_schema_header`, `/api/catalogos/<tabla>/...`, ejecutar
transiciones, etc.) con una sesión de Usuario válida y los permisos
correctos, **no nota ningún cambio** — sigue funcionando exactamente
igual que antes.

Lo que cambia es para quien NO cumplía eso, que antes entraba igual:

- **Sin sesión iniciada** → `401`:
  ```json
  {"errors": {"detail": "no autenticado"}}
  ```
- **Con sesión, pero sin el permiso que esa acción puntual exige** →
  `403`:
  ```json
  {"errors": {"detail": "sin permiso"}}
  ```

Ninguno de los dos casos llega a tocar ningún dato — el rechazo pasa
ANTES de ejecutar la acción pedida.

## Qué permiso exige cada cosa

| Qué se pide | Permiso exigido |
|---|---|
| `GET /api/<catalogo>`, `GET /api/<catalogo>/:id` | `<catalogo>` / **leer** |
| `POST /api/<catalogo>` | `<catalogo>` / **crear** |
| `PUT`/`PATCH /api/<catalogo>/:id` | `<catalogo>` / **editar** |
| `DELETE /api/<catalogo>/:id` | `<catalogo>` / **eliminar** |
| `GET /api/<catalogo>/:id/transiciones` (ver disponibles) | `<catalogo>` / **leer** |
| `POST /api/<catalogo>/:id/transiciones/<accion>` (ejecutar) | `<catalogo>` / **`<accion>`** (el nombre de la transición en sí) |
| Crear/editar un catálogo (`meta_schema_header`, `meta_schema_estados`, `meta_schema_transiciones`) | `sysadmin_bc` / **editar** |
| Consultar impacto/validar motor/completitud de un catálogo | `sysadmin_bc` / **leer** |
| Borrar un catálogo completo (`DELETE /api/catalogos/<tabla>`) | `sysadmin_bc` / **editar** |

Un usuario con el rol **"administrador"** siempre pasa, sin importar
qué le hayan concedido explícitamente — igual que ya pasaba en la web.

## Cómo desbloquear una integración real que empezó a recibir 401/403

1. **401 ("no autenticado")** — la integración necesita mandar la
   cookie de sesión de un Usuario real logueado (esta API nunca usó
   API key ni token — si necesitás eso, es el caso de
   `SPEC-SYS-1009202602-endpoint-desde-consulta`, un mecanismo
   separado y ya pensado para integraciones externas).

2. **403 ("sin permiso")** — a ese Usuario le falta el permiso puntual
   de la tabla de arriba. Se concede desde:
   - **Permiso sobre un catálogo** (leer/crear/editar/eliminar, o el
     nombre de una transición): `/sysadmin/catalogos/permisos` —
     elegí el rol del usuario, buscá el catálogo, tildá la acción que
     necesita.
   - **Permiso `sysadmin_bc`** (crear/editar catálogos, borrar uno
     completo): `/sysadmin/roles` — mismo permiso que ya usan BC Motor
     y BC List en la web, se concede desde ahí igual que cualquier
     otro.

No hace falta reiniciar nada ni tocar código — el chequeo lee el
permiso en el momento (con cache corto, `Permissions.invalidar_cache/2`
se dispara solo al conceder/revocar un rol).
