# SPEC-SYS-0710202601 — Tepache (bundles de previsualización entre desarrolladores)

**Documento:** Requirements · **Fase:** ✅ cerrada (2026-10-08,
R23 y R24 implementados y verificados; R9, R14.1, R20, R21 y R22 el
2026-10-07) · Spec de **documentación retroactiva**
(2026-10-07) de una funcionalidad ya construida y en uso, más **un
requisito nuevo** (R9, validación de dependencias al exportar — a
pedido explícito del usuario, mismo día). Los requisitos retroactivos
(todos salvo R9) describen el comportamiento tal como YA funciona hoy,
sin proponer cambios — si algo de ahí se quiere cambiar en el futuro,
va en una spec nueva y separada.

## 1. Contexto y decisión de alcance

Tepache se construyó en una sesión sin spec propia (ver
`docs/roadmap.md #14`). Esta spec lo documenta de punta a punta y, de
paso, agrega la primera mejora real sobre el comportamiento existente.

**Decisión confirmada por el usuario (2026-10-07):** el requisito R9
(rechazar el export si faltan dependencias por seleccionar) queda
DENTRO de esta misma spec, no en una aparte — por eso esta spec sí
lleva `03.tasks.md`, a diferencia del patrón 100% retroactivo de
`SPEC-SYS-2509202602`/`SPEC-SYS-2509202603`.

## 2. Vocabulario

- **Tepache**: nombre interno del bundle de previsualización — un
  `.tar.gz` con schema, migraciones, metadata y autómata de uno o más
  catálogos, distribuido como release de GitHub.
- **Catálogo seleccionado**: el que quien exporta eligió a mano (UI o
  argumento de `mix motor.tepache`).
- **Dependencia** / **cierre de dependencias**: un catálogo que un
  seleccionado necesita para funcionar completo (un detalle suyo, o un
  catálogo al que apunta un campo tipo "referencia") — calculado por
  `MetaSchemaContext.calcular_paquete_publicacion/1`, la misma función
  que usa la publicación real.
- **Paquete completo**: el resultado de ese cierre — seleccionados +
  sus dependencias.
- **Tag**: identificador del release de GitHub, formato
  `TEPACHE-NNNNNN` (consecutivo global, 6 dígitos).
- **Servicio/Diccionario/Consulta (SQL View)**: catálogo tipo 4
  (`SPEC-SYS-2509202601`) — Tepache también puede empaquetarlos,
  siempre que ya tengan SQL guardado.

## 3. Requisitos

### Exportar

**R1.** CUANDO alguien exporta uno o más catálogos (pantalla "Tepache
Exp/Imp" o `mix motor.tepache <catálogo> [<catálogo2> ...]`), EL
SISTEMA DEBE validar cada uno con el mismo chequeo estructural que usa
la publicación real (`MetaPublicador.validar/1`): si es un catálogo
normal, que su motor de estados sea válido; si es una SQL View, que ya
tenga SQL guardado.

**R2.** Si algún catálogo no existe o no pasa esa validación, EL
SISTEMA DEBE rechazar el export completo con un mensaje, sin crear
ningún release ni subir nada.

**R3.** EL SISTEMA DEBE calcular el cierre de dependencias (paquete
completo) de los catálogos seleccionados.

**R4.** Antes de re-sincronizar o exportar nada, EL SISTEMA DEBE
regenerar el schema `.ex` de **todos** los catálogos existentes
localmente (no solo los del paquete) contra su metadata actual, y
exportar a `priv/repo/catalogos/` la metadata, el autómata y las
plantillas de **todos** los catálogos existentes localmente — mismo
efecto de lado que `mix gen.catalogos` + `mix meta.export` +
`mix motor.export`. Esto deja el checkout local consistente de punta a
punta, aunque el bundle final solo incluya los archivos del paquete.

**R5.** EL SISTEMA DEBE armar un `.tar.gz` con el contenido exportado
de, exclusivamente, los catálogos del paquete completo —
`MetaPublicador.armar_bundle/1`, el mismo mecanismo que usa la
publicación real.

**R6.** EL SISTEMA DEBE calcular el próximo tag `TEPACHE-NNNNNN` como
el consecutivo siguiente al mayor ya existente entre los releases de
GitHub, consultando hasta 1000 releases.

**R6.1.** Con un límite de consulta menor a la cantidad real de
releases del repo, el cálculo puede ignorar tags `TEPACHE-*` viejos
(quedan fuera de los más recientes) y proponer un tag que ya existe
(bug real, corregido 2026-09-29) — R6 exige explícitamente un límite
igual o mayor a la cantidad de releases esperable.

**R7.** EL SISTEMA DEBE crear el release de GitHub con ese tag, notas
en Markdown (descripción libre de quien exporta primero si la escribió,
después catálogos incluidos, catálogos agregados automáticamente y
advertencias del validador), y subir el bundle como asset de nombre
fijo `tepache.tar.gz` — nunca el nombre temporal interno con el que se
armó.

**R7.1.** El tag de un tepache NUNCA DEBE coincidir ni reutilizar el
tag `bc-<catálogo>` que usa la publicación real — son namespaces
separados.

**R8.** Al terminar de exportar (éxito o error), EL SISTEMA DEBE
borrar el archivo `.tar.gz` temporal local — nunca dejarlo residual en
el filesystem de quien publica.

**R9 (NUEVO, 2026-10-07, a pedido explícito).** Si el cierre de
dependencias (R3) incluye algún catálogo que NO fue seleccionado
explícitamente por quien exporta, EL SISTEMA DEBE **rechazar el
export** con un mensaje que liste, por nombre, cada catálogo faltante
— sin regenerar schemas, sin exportar metadata, sin armar ni subir
ningún bundle. El sistema NUNCA DEBE agregar esas dependencias a la
selección de forma automática o silenciosa; quien exporta tiene que
agregarlas a mano (a la selección de la pantalla, o como argumento
extra de `mix motor.tepache`) y reintentar. Reemplaza el
comportamiento anterior (la dependencia se sumaba sola, documentada
después del hecho en las notas del release como "incluidos
automáticamente").

**R23 (NUEVO, 2026-10-08, a pedido explícito).** Al exportar, EL
SISTEMA DEBE incluir en el paquete, de forma automática, cada carpeta
real (`schema_context_type` 2) que esté en la ruta del menú de un
catálogo del paquete. Por ejemplo, un catálogo con ruta `/liz/reporte`
arrastra la carpeta cuya ruta es `/liz`, y si hay carpetas anidadas,
arrastra todas las de arriba. Así, el ícono, la etiqueta, la
visibilidad y el orden de esas carpetas le llegan a quien importa.

**R23.1.** Agregar una carpeta de esta forma NO DEBE disparar el
rechazo de R9: una carpeta no es una dependencia funcional, solo es
presentación del menú. Las carpetas incluidas DEBEN listarse en las
notas del release con el título "Carpetas incluidas".

**R23.2.** Una carpeta implícita (sin registro propio, que solo se
deduce de la ruta) no tiene ícono ni datos que mandar, así que no
viaja.

**R23.3.** Motivo: caso real del 2026-10-08. El ícono de una carpeta
cambiado en el origen nunca llegaba a quien importa, porque el
buscador de la pantalla excluye carpetas y el cálculo de dependencias
(R3) no las agrega. El import ya sabía actualizarlas
(`cambios_de_directorio/2`), pero nunca le llegaban.

**R23.4.** Solo aplica al tepache: `mix motor.publicar` no cambia,
aunque comparte el cálculo de dependencias (R3). La carpeta se agrega
por fuera de ese cálculo.

**R20 (NUEVO, 2026-10-07, a pedido explícito).** CUANDO alguien
exporta desde la pantalla "Tepache Exp/Imp", EL SISTEMA DEBE mostrar
una barra de progreso por etapas mientras el export corre, con el
nombre de la etapa en curso: (1) validando catálogos y dependencias,
(2) regenerando schemas, (3) exportando metadata y autómata, (4)
armando el paquete, (5) publicando en GitHub. Cada etapa iniciada
avanza la barra en partes iguales (20%) — indica en qué paso va, NUNCA
una estimación de tiempo restante.

**R20.1.** Mientras el export corre, la pantalla DEBE seguir
respondiendo y el botón "Exportar tepache" DEBE quedar deshabilitado
(sin poder lanzar un segundo export en paralelo).

**R20.2.** Si el export falla (incluido el rechazo de R9), la barra
DEBE desaparecer y mostrarse el error igual que hoy (caja roja). Al
terminar con éxito, la barra DEBE desaparecer y mostrarse el
resultado igual que hoy.

**R20.3.** El avance solo se muestra en la pantalla; `mix
motor.tepache` NO cambia su salida (decisión del usuario, 2026-10-07).

### Importar

**R10.** CUANDO alguien importa un tag (pantalla "Tepache Exp/Imp" o
`mix motor.tepache.importar <TEPACHE-NNNNNN>`), EL SISTEMA DEBE bajar
el asset `.tar.gz` del release correspondiente sin tocar la base de
datos local todavía.

**R11.** EL SISTEMA DEBE determinar qué catálogos trae el bundle
leyendo el índice del `.tar.gz` (nombres de archivo `.meta.json`), sin
necesidad de extraerlo completo.

**R12.** Para cada catálogo del bundle que YA exista localmente, EL
SISTEMA DEBE comparar sus campos actuales (`meta_schema_detail`
local) contra los que trae el `.meta.json` entrante, y detectar
cuáles existen localmente pero NO vienen en el bundle entrante.

**R13.** Si R12 detecta campos candidatos a eliminar, EL SISTEMA DEBE
detenerse ANTES de aplicar cualquier cambio (ni migrar, ni extraer, ni
importar metadata) y pedir confirmación explícita, listando catálogo y
campos — nunca debe eliminar un campo con datos reales sin que un
humano lo confirme.

**R14.** Una vez confirmado (o si R12 no detectó nada), EL SISTEMA
DEBE extraer el bundle sobre el proyecto de quien importa, migrar la
base de datos local (mismo mecanismo que
`MetadataApp.Release.migrate/0`, sin pasar por Mix) e importar
metadata, autómata y plantillas de los catálogos del bundle.

**R14.1.** El import de metadata, autómata y plantillas NO DEBE
procesar ningún catálogo fuera del bundle, aunque sus archivos estén
en la carpeta local `priv/repo/catalogos/` de quien importa (bug real,
encontrado 2026-10-07: el import re-importaba toda esa carpeta, y con
eso podía aplicar a la base cambios locales que no venían en el
tepache; además el resultado listaba como "ya existía, sin cambios"
todos los catálogos del checkout).

**R15.** Si se confirmaron campos a eliminar (R13), EL SISTEMA DEBE
aplicar un soft-delete local sobre esos campos — nunca un `DROP`
físico adicional fuera del que ya haya traído la migración del
bundle.

**R16.** EL SISTEMA DEBE registrar los permisos (leer, crear, editar,
eliminar, y cada transición real del catálogo) de cada catálogo
importado — SIN concedérselos a ningún rol. Conceder el acceso a un
rol puntual queda siempre a criterio de quien importa: nunca se hereda
del bundle sin que quien importa lo pida con la casilla de R24.

**R24 (CORREGIDO, 2026-10-08, a pedido explícito — reemplaza la
primera versión del mismo día, "conceder todos los permisos a un rol
elegido al importar", que no era lo pedido).** Al exportar desde la
pantalla "Tepache Exp/Imp", EL SISTEMA DEBE guardar en el paquete los
permisos que tienen sobre los catálogos del paquete:
- los roles de **todas las empresas a las que pertenece quien
  exporta**, cada uno identificado por **nombre de empresa + nombre de
  rol**;
- los roles de sistema, identificados solo por nombre.

El "administrador" de sistema no se guarda (ya ve todo).

**R24.1.** Al importar, la pantalla DEBE ofrecer **una sola
casilla**: "Aplicar los permisos que trae el tepache". **Solo si está
marcada**, EL SISTEMA DEBE conceder las acciones que trae el paquete:
- a cada rol de empresa, en el rol con el mismo nombre dentro de la
  empresa con el mismo nombre del destino (cualquier empresa de esa
  base, pertenezca o no a ella quien importa);
- a cada rol de sistema, en el rol de sistema con el mismo nombre.

Sin la casilla no se concede nada: el comportamiento es el de R16
(solo se registran los permisos).

**R24.2.** EL SISTEMA NO DEBE crear empresas ni roles. Omite el rol y
lo lista en el resultado del import, con el motivo, cuando: la empresa
no existe en el destino; el rol no existe en esa empresa; o hay más de
una empresa con ese nombre (el nombre de empresa no es único; no se
adivina cuál es).

**R24.3.** Aplicar los permisos solo suma: NUNCA DEBE quitar un
permiso que el rol ya tenga en el destino.

**R24.4.** Es parte de la etapa 6 de R22 ("registrando permisos") y
del todo o nada de R21.3: si falla, no queda ningún permiso ni otro
cambio de esos pasos en la base.

**R24.5.** La casilla DEBE conservarse si el import se detiene para
confirmar campos a eliminar (R13/R22.1).

**R24.6.** Si el tepache no trae permisos (ej. `TEPACHE-000013` o
`TEPACHE-000014`, exportados antes de este cambio), la casilla no tiene
efecto y el resultado lo dice.

**R24.7.** `mix motor.tepache` exporta sin permisos (no sabe quién
exporta) y `mix motor.tepache.importar` nunca los aplica — mismo
criterio que R20.3 y R22.4.

**R24.8.** Las notas del release DEBEN decir de cuántos roles y
empresas trae permisos (ej. "**Permisos incluidos:** 5 roles de 2
empresas"), sin listarlos.

**R17.** Al terminar de importar (éxito o error), EL SISTEMA DEBE
borrar el bundle temporal local.

**R22 (NUEVO, 2026-10-07, a pedido explícito).** CUANDO alguien
importa desde la pantalla "Tepache Exp/Imp", EL SISTEMA DEBE mostrar
una barra de progreso por etapas con el nombre de la etapa en curso:
(1) descargando el tepache, (2) revisando qué catálogos trae y si
faltan campos, (3) extrayendo archivos, (4) migrando la base, (5)
importando metadata, autómata y plantillas, (6) registrando permisos.
Cada etapa iniciada avanza la barra en partes iguales — indica en qué
paso va, NUNCA una estimación de tiempo restante (mismo criterio que
R20).

**R22.1.** Si después de la etapa 2 hace falta confirmar campos a
eliminar (R13), la barra DEBE quitarse mientras se muestra el aviso de
confirmación; al confirmar, DEBE reaparecer y continuar desde la etapa
3. Al cancelar, no se toca nada (igual que hoy).

**R22.2.** Mientras el import corre, la pantalla DEBE seguir
respondiendo y el botón "Importar" (y "Confirmar y eliminar esos
campos") DEBE quedar deshabilitado, sin poder lanzar un segundo import
en paralelo.

**R22.3.** Si el import falla en cualquier etapa — incluida una
excepción no controlada, como una migración que truena (caso real
`TEPACHE-000010`, 2026-10-07) — la barra DEBE desaparecer y mostrarse
el error en la caja roja de resultado; la pantalla NUNCA DEBE caerse.
Al terminar con éxito, la barra DEBE desaparecer y mostrarse el
resultado igual que hoy. (Qué dice exactamente el mensaje y qué pasa
con lo que quedó a medias lo define R21.)

**R22.4.** El avance solo se muestra en la pantalla; `mix
motor.tepache.importar` NO cambia su salida (mismo criterio que R20.3).

### Disponibilidad y resiliencia

**R18.** La pantalla "Tepache Exp/Imp" y los mix tasks
`motor.tepache`/`motor.tepache.importar` SOLO DEBEN estar disponibles
donde `bpb_habilitado` esté activo (ambiente de desarrollo, con
compilador) — nunca en un ambiente de producción.

**R19.** Si una ejecución externa (`gh`, `tar`) falla porque el
binario no está instalado o no está en el PATH de quien corre el
proceso, EL SISTEMA NO DEBE tumbar el proceso que la invoca (LiveView
o Mix task) — debe devolver un error manejable y mostrarlo.

**R21 (NUEVO, 2026-10-07, a pedido explícito — "opción B").** Si el
import falla en cualquier paso posterior a confirmar (extraer, migrar,
importar metadata/autómata/plantillas, soft-delete de R15 o registrar
permisos), EL SISTEMA DEBE deshacer lo que ESE intento hizo, para que
la máquina de quien importa quede como estaba antes del intento, y
devolver un error (nunca tumbar el proceso — pantalla ni mix task) que
diga en qué paso falló, la causa real y el resultado de la reversión.
Motivo: caso real `TEPACHE-000010` (2026-10-07), donde una migración
que tronó dejó 238 archivos extraídos y 12 tablas creadas sin metadata.

**R21.1 — Archivos.** Antes de extraer, EL SISTEMA DEBE guardar una
copia de cada archivo local que el bundle va a sobrescribir. Si hay
que revertir, DEBE restaurar esas copias y borrar SOLO los archivos que
el bundle creó (los que no existían antes de extraer). NUNCA DEBE tocar
un archivo que el bundle no trae. Las copias DEBEN conservarse hasta
que la restauración termine bien; si falla, el mensaje DEBE decir
dónde quedaron.

**R21.2 — Migraciones.** EL SISTEMA DEBE revertir SOLO las migraciones
que estaban pendientes justo antes de migrar y que este intento
aplicó, en orden inverso. NUNCA DEBE revertir una migración que ya
estaba aplicada antes del intento.

**R21.3 — Metadata y permisos.** Importar metadata/autómata/plantillas,
el soft-delete de R15 y registrar permisos DEBEN ser todo o nada: si
cualquiera falla, no queda ningún cambio de esos pasos en la base.

**R21.4 — Ante la duda, no revertir.** EL SISTEMA NO DEBE revertir
nada de forma automática (ni migraciones ni archivos) y DEBE reportar
el estado exacto en el mensaje, si alguna migración a revertir:
(a) usa un patrón de "crear si no existe" (`create_if_not_exists`,
`IF NOT EXISTS`) — revertirla podría borrar una tabla que ya existía
con datos; o (b) su reversión falla (ej. una migración sin `down`
reversible). En el caso (b), lo ya revertido antes de la falla se
reporta como tal.

**R21.5 — Límite conocido.** Si una migración del bundle quita una
columna, los datos de esa columna se pierden al migrar; revertir la
vuelve a crear vacía. R21 no lo evita (lo previene la confirmación de
R13) y el mensaje lo DEBE mencionar si aplica.

**R21.6.** Aplica igual a la pantalla y a `mix
motor.tepache.importar` (la lógica vive en `MetaTepache`, no en la
interfaz). Una falla ANTES de extraer (descargar, revisar el bundle)
no requiere reversión: ahí todavía no se tocó nada (R10-R12).

## 4. Límites actuales (informativo, sin propuesta)

- No hay forma de "despublicar" o borrar un tepache ya creado desde la
  app — solo se puede hacer manualmente desde GitHub.
- La detección de campos removidos (R12) compara solo por nombre: si
  alguien creó de forma independiente, en otra máquina, un catálogo
  con el mismo nombre pero sin relación real con el origen del bundle,
  puede dar un falso positivo. Se acepta como diseño ("mejor preguntar
  de más que borrar de menos").
- Solo cubre catálogos normales (tipo 1/detalle) y SQL Views (tipo 4)
  que ya tengan SQL guardado — una SQL View sin SQL guardado bloquea
  el export completo si está entre los seleccionados o entre sus
  dependencias (R2).
