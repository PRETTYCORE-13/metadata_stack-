# SPEC-SYS-1109202601 — BC Motor: Tab Configuración

**Documento:** Explicación general · **Fase:** ✅ aprobada (2026-09-11).

## ¿Qué problema resuelve?

Cuando alguien arma o edita un catálogo con el Motor BC, necesita definir
todo lo que hace que ese catálogo funcione: su nombre y dónde aparece en
el menú, qué información guarda (los campos), y — si ese catálogo maneja
un flujo de estados (por ejemplo "Borrador → Aprobado → Cerrado") — en
qué estados puede estar un registro y qué acciones lo mueven de uno a
otro. El tab "Configuración" es la pantalla central donde se arma todo
eso, en un solo lugar, de punta a punta.

## ¿Cómo funciona, a grandes rasgos?

Al entrar a este tab aparecen cuatro bloques, en el orden real en que
conviene completarlos:

1. **Encabezado**: el nombre visible del catálogo, dónde aparece en el
   árbol de navegación, su ícono, y si está visible o no.
2. **Campos**: la lista de toda la información que guarda cada registro
   del catálogo — qué campos tiene, de qué tipo, si son obligatorios, si
   aparecen como columna en la ficha detallada, y configuraciones extra
   según el tipo (formato de captura, formato de fecha, o — si el campo
   apunta a otro catálogo — cómo se relaciona con él).
   Para esos campos que apuntan a otro catálogo también se puede limitar
   qué registros se pueden elegir: que dependan de lo que se eligió antes
   en otro campo (por ejemplo, Municipio según el Estado), que solo
   muestren registros con un valor fijo (por ejemplo, en Repartos, solo
   los almacenes de tipo "COMPROMETIDA"), o que solo ofrezcan lo que
   entrega un Diccionario de datos (una SQL View con condiciones que
   cruzan varios catálogos, como "empleados de ventas que no deben
   dinero").
3. **Estados**: la lista de "fotografías" posibles en las que puede
   estar un registro (por ejemplo, "Pendiente", "Aprobado"), con un
   color e ícono para identificarlas de un vistazo. El primer estado que
   se crea queda marcado automáticamente como el punto de partida.
4. **Transiciones**: las acciones que mueven un registro de un estado a
   otro (por ejemplo, "aprobar" mueve de "Pendiente" a "Aprobado"). Cada
   transición define también qué campos se pueden editar en ese
   momento, y si el permiso para ejecutarla ya existe o hay que
   crearlo.

Un catálogo puede no tener flujo de estados en absoluto. Y un catálogo
"detalle" (uno que vive siempre colgado de otro, como los renglones de
un pedido) ni siquiera muestra los bloques de Estados y Transiciones:
comparte el flujo de estados de su catálogo maestro.

Arriba de todo, una barra de pasos muestra de un vistazo qué partes ya
están armadas y cuáles faltan, para guiar el orden lógico de
construcción de un catálogo nuevo.

## ¿Quién usa esta funcionalidad?

Gente de ADN o del equipo de plataforma que construye o mantiene
catálogos con el Motor BC — nunca el usuario final del catálogo (él ve
el resultado ya armado, no esta pantalla).

## Lo que esta spec NO hace

No documenta el tab "Diagrama" (la representación visual del flujo de
estados ya armado acá, ver `SPEC-SYS-1109202602-bc-motor-tab-diagrama`),
ni el tab "Contrato" (la documentación de API que se genera
automáticamente a partir de lo configurado acá, ver
`SPEC-SYS-1109202603-bc-motor-tab-contrato`), ni el tab "Reglas"
(condiciones antes/después de cada transición), ni los tabs Relaciones,
Get Config, Post Config o Permisos, que tienen (o pueden tener) sus
propias specs. Tampoco explica cómo el sistema, por dentro, crea o borra
columnas reales cuando se agrega o elimina un campo desde acá.
