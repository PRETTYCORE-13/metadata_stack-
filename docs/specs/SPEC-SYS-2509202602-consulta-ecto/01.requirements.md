# SPEC-SYS-2509202602 — Consulta Ecto (Reportes)

**Documento:** Requirements · Spec de **documentación retroactiva**
(a pedido explícito, 2026-09-25): describe la Consulta Ecto tal como YA
funciona hoy, sin cambiar comportamiento del sistema ni proponer
mejoras.

## 1. Contexto y decisión de alcance

**Decisión confirmada por el usuario (2026-09-25):** esta spec solo
documenta lo existente. Nada de lo que sigue implica trabajo de
implementación. Los límites del comportamiento actual se registran en
§4 tal como son, sin propuesta. Si alguno se decide cambiar, se hace en
una spec nueva y separada.

La Consulta Ecto se construyó por partes, en varias sesiones, sin una
spec propia. Otras specs ya documentan piezas que se montaron sobre
ella; aquí se referencian, no se repiten:

- `SPEC-SYS-0209202601` — Parámetros y totales (compartidos con los
  catálogos normales).
- `SPEC-SYS-0909202605` — Resumen de selección.
- `SPEC-SYS-1009202602` — Endpoint API a partir de una Consulta.
- `SPEC-SYS-0809202601` — Publicar la definición de una Consulta a otro
  ambiente (solo requirements, sin construir).

## 2. Vocabulario

- **Consulta Ecto**: Business Context de tipo Consulta, de solo lectura.
  En el menú y ante el usuario final se muestra como "Consulta" o
  "Reporte".
- **Catálogo principal**: el catálogo del que parte la consulta. Siempre
  hay exactamente uno.
- **Tabla relacionada**: otro catálogo que se suma a la consulta, unido
  con una tabla que ya está en ella.
- **Unión**: el par de campos por el que se enlaza una tabla relacionada
  con otra que ya está en la consulta.
- **Campo de control**: un dato del catálogo principal que no es un campo
  de negocio configurado: ID, Estado, TRN, Sucursal, Almacén o Unidad de
  venta.
- **Registro eliminado**: un registro borrado de forma lógica. No es lo
  mismo que un registro en estado "Baja", que sigue existiendo.

## 3. Requisitos

### Alta

**R1.** CUANDO quien construye catálogos pulsa "Nueva consulta" en BC
List, EL SISTEMA DEBE pedir etiqueta, carpeta y ruta en el menú, y el
catálogo principal. El catálogo principal se elige de la lista de
catálogos que pueden ser referenciados.

**R2.** CUANDO se intenta guardar una consulta sin catálogo principal,
sin etiqueta, o sin ruta, EL SISTEMA DEBE rechazar el guardado con un
mensaje, sin crear nada.

**R3.** CUANDO la ruta elegida ya la usa otro catálogo o carpeta, EL
SISTEMA DEBE avisarlo mientras se escribe y rechazar el guardado.

**R4.** CUANDO se guarda una consulta nueva, EL SISTEMA DEBE crearla
visible en el menú, con un nombre interno derivado de su ruta (prefijo
`consulta_`, nunca `pty_`) y con todos los campos de negocio de sus
tablas ya incluidos como columnas visibles.

### Tablas relacionadas

**R5.** MIENTRAS se da de alta una consulta, EL SISTEMA DEBE permitir
sumar tablas relacionadas una a una, y DEBE mostrar en ese momento la
unión que va a usar con cada una.

**R6.** CUANDO se suma una tabla relacionada, EL SISTEMA DEBE detectar
sola la unión, en este orden de preferencia:
1. Maestro-detalle: la tabla nueva es detalle de una que ya está en la
   consulta, o al revés.
2. La tabla nueva tiene un campo que apunta a una que ya está.
3. Una tabla que ya está tiene un campo que apunta a la nueva.

**R7.** CUANDO no se encuentra ninguna unión, o quien construye quiere
otra, EL SISTEMA DEBE permitir definirla a mano: un campo de la tabla
nueva contra un campo de cualquier tabla anterior.

**R8.** CUANDO la tabla que se suma es detalle de algún maestro, EL
SISTEMA DEBE avisar que la consulta devolverá una fila por cada renglón
del detalle, no una por cada maestro.

**R9.** CUANDO alguna tabla relacionada todavía no tiene unión definida,
EL SISTEMA DEBE impedir guardar la consulta.

**R10.** EL SISTEMA DEBE permitir quitar solo la última tabla
relacionada que se sumó, para no dejar una unión apuntando a una tabla
que ya no está.

**R11.** CUANDO una tabla relacionada no tiene registro que coincida con
la unión, EL SISTEMA DEBE conservar la fila del catálogo principal y
dejar vacías las columnas de esa tabla.

### Editor de la consulta

**R12.** CUANDO quien construye abre una consulta desde BC List, EL
SISTEMA DEBE mostrar su editor con cinco pestañas: Configuración,
Contrato, Permisos, Get Config y SQL. El editor muestra sobre qué tablas
está construida la consulta y un acceso directo al reporte.

**R13.** EN la pestaña Configuración, EL SISTEMA DEBE permitir editar el
encabezado (etiqueta, carpeta y ruta, ícono, visible) y la etiqueta de
cada columna. No debe permitir cambiar tipo, longitud ni ninguna otra
propiedad que venga del catálogo original.

**R14.** EL SISTEMA DEBE permitir agregar o quitar como columnas los
campos de control del catálogo principal, pero solo los que ese
catálogo realmente tiene:
- ID, siempre.
- Estado, si tiene motor de estados.
- TRN, si es transaccional.
- Sucursal, Almacén y Unidad de venta, si tiene alcance de datos
  habilitado y la columna correspondiente.

**R15.** CUANDO se muestra una columna de Estado, Sucursal, Almacén o
Unidad de venta, EL SISTEMA DEBE mostrar su nombre, no su número
interno. Lo mismo DEBE hacer con cualquier campo que apunte a otro
catálogo: mostrar la descripción configurada en ese campo.

**R16.** EN la pestaña Get Config, EL SISTEMA DEBE permitir elegir qué
columnas son visibles y reordenarlas arrastrando. El nuevo orden se
guarda al soltar la columna, sin botón aparte.

**R17.** EN la pestaña Get Config, EL SISTEMA DEBE permitir definir el
orden de los resultados:
- una lista de columnas con prioridad y dirección (ascendente o
  descendente);
- se puede ordenar por cualquier columna de la consulta, visible o no;
- cada cambio se guarda al momento.

**R18.** EN la pestaña Get Config, EL SISTEMA DEBE permitir marcar una
columna visible como parámetro del reporte, con sus valores iniciales,
y configurar totales, formato y resumen de selección por columna. Los
detalles de estas funciones están en `SPEC-SYS-0209202601` y
`SPEC-SYS-0909202605`.

**R19.** EN la pestaña SQL, EL SISTEMA DEBE mostrar, solo para leer, la
consulta que se manda a la base de datos, con sus uniones, columnas y
parámetros. Muestra ejemplos de valores donde un parámetro todavía no
tiene valor inicial. Debe hacerlo en dos vistas: el SQL y la consulta
Ecto de la que sale.

**R20.** EN la pestaña Contrato, EL SISTEMA DEBE documentar cómo leer la
consulta por la API.

### Permisos y alcance de datos

**R21.** EN la pestaña Permisos, y en la administración de permisos por
catálogo, EL SISTEMA DEBE ofrecer para una consulta únicamente el
permiso de leer.

**R22.** CUANDO un usuario sin permiso de leer intenta abrir una
consulta, desde el menú o por la API, EL SISTEMA DEBE negarle el
acceso.

**R23.** EL SISTEMA DEBE aplicar a la consulta el alcance de datos del
usuario sobre el catálogo principal, tal como está configurado en ese
catálogo. El alcance no se aplica a las tablas relacionadas.

**R24.** EL SISTEMA DEBE excluir de los resultados los registros
eliminados, tanto del catálogo principal como de las tablas
relacionadas.

### Uso por el usuario final

**R25.** CUANDO un usuario con permiso abre la consulta desde el menú,
EL SISTEMA DEBE mostrar una tabla de solo lectura con las columnas
visibles, en su orden, y un contador del tipo "1-25 de N". No debe haber
ninguna acción para crear, editar ni borrar.

**R26.** MIENTRAS la consulta no tenga ningún parámetro de fecha y el
usuario no haya llenado ningún otro parámetro, EL SISTEMA DEBE mostrar
la tabla vacía y pedirle elegir un filtro. Nunca carga todos los
registros por defecto.

**R27.** CUANDO el usuario llena o cambia un parámetro, EL SISTEMA DEBE
volver a calcular filas, contador y totales con ese valor, solo para su
sesión. La configuración guardada de la consulta no cambia.

**R28.** CUANDO el usuario pulsa el encabezado de una columna, EL
SISTEMA DEBE ordenar por esa columna, solo para su sesión. Ese orden
reemplaza al configurado en Get Config.

**R29.** EL SISTEMA DEBE permitir al usuario mostrar u ocultar columnas
en su vista y seleccionar filas para ver el resumen de selección.

**R30.** CUANDO el usuario descarga Excel, EL SISTEMA DEBE exportar las
columnas visibles de una de dos formas:
- **todas** las filas que cumplen los parámetros y el alcance, no solo
  las que se ven en pantalla;
- **solo las filas seleccionadas**, respetando el alcance.

### API

**R31.** CUANDO se pide una consulta por la ruta general de lectura de
la API (la misma que usa cualquier catálogo), EL SISTEMA DEBE responder
con:
- la descripción de las columnas visibles;
- las filas de la página pedida;
- los totales configurados;
- la paginación (página, tamaño, total de filas y total de páginas).

**R32.** EL SISTEMA DEBE paginar siempre la respuesta de la API: 25
filas por página si no se indica otro tamaño, y un máximo de 100.

**R33.** CUANDO la petición a la API trae como parámetro el nombre de
una columna de la consulta, EL SISTEMA DEBE filtrar por igualdad exacta
con ese valor.

**R34.** EL SISTEMA DEBE nombrar cada valor de la API con el catálogo y
el campo de donde sale, para que no se confundan dos columnas con el
mismo nombre que vienen de tablas distintas.

**R35.** EL SISTEMA NO DEBE aceptar altas, cambios ni bajas de registros
a través de una consulta.

### Eliminación

**R36.** CUANDO quien construye elimina una consulta desde BC List, EL
SISTEMA DEBE:
- pedir solo una confirmación simple, porque la consulta no tiene datos
  propios que perder;
- borrar la consulta junto con toda su configuración;
- no tocar ningún registro de los catálogos que consultaba.

## 4. Comportamiento actual observado (sin propuesta)

Límites del sistema tal como está hoy, verificados en el código el
2026-09-25. Se registran para que nadie los tome como un error nuevo ni
como algo que la spec promete:

- **Pantalla sin paginación ni búsqueda:** la vista del usuario final
  muestra solo las primeras 25 filas. El contador sí indica el total
  real, pero no hay botones de página ni caja de búsqueda general. El
  Excel ("todas") y la API sí llegan a todas las filas.
- **Tablas fijas después del alta:** las tablas relacionadas y sus
  uniones solo se eligen al crear la consulta. El editor no permite
  agregarlas, quitarlas ni corregir su unión después.
- **Filtro ambiguo por nombre:** si dos tablas de la misma consulta
  tienen un campo con el mismo nombre, un filtro por ese nombre (API o
  filtros internos) se aplica solo a la primera coincidencia. Los
  parámetros de Get Config no tienen este problema, porque se resuelven
  por catálogo y campo.
- **Totales elegidos por el usuario sin alcance:** el valor que el
  usuario elige calcular por columna (suma, promedio, mínimo, máximo,
  conteo) no aplica el alcance de datos. El total general y el resumen
  de selección sí lo aplican.
- **Campos de control solo del principal** (ver R14).
- **Publicación incompleta:** al publicar a otro ambiente viaja la
  entrada del menú de la consulta, pero no su definición (tablas,
  columnas, orden). Esto lo cubre `SPEC-SYS-0809202601`, que todavía no
  se construye.

## 5. Fuera de alcance

- Consultas con condiciones que no sean uniones (por ejemplo "que no
  exista", o agregados con condición): `SPEC-SYS-2509202601`
  (Consulta SQL).
- Diagnóstico sin alcance de datos: `SPEC-SYS-0909202603` (Consulta
  Directa).
- Endpoint API propio y trabajos asíncronos: `SPEC-SYS-1009202602`.
