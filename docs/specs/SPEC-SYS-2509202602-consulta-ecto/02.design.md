# SPEC-SYS-2509202602 — Consulta Ecto (Reportes)

**Documento:** Design · Spec de **documentación retroactiva**
(2026-09-25): describe CÓMO está construida hoy la Consulta Ecto. Sin
`03.tasks.md` a propósito: no hay nada que construir. Verificado contra
el código el 2026-09-25. Si el código cambia, esto se actualiza primero.

## 1. Mapa de piezas

| Pieza | Módulo | Rol |
|---|---|---|
| Encabezado | `MetaSchema.Header` (`meta_schema_header`) | Nombre, etiqueta, ruta, ícono, visible. `schema_context_type: 3` identifica una Consulta. |
| Definición | `MetadataApp.MetaSchema.Consulta` (`meta_schema_consulta`) | Catálogo principal, columnas, uniones y orden. Una fila por encabezado. |
| Motor | `MetadataApp.MetaConsultas` | Arma la query, filtra, aplica el alcance, pagina, totaliza y resuelve etiquetas. |
| Parámetros | `MetadataApp.ParametrosCatalogo` | Motor de parámetros compartido con los catálogos BC (`SPEC-SYS-0209202601`). |
| Alta y eliminación | `MetadataAppWeb.Sysadmin.BcListLive` | Modal "Nueva consulta", tablas relacionadas, borrado. |
| Editor | `MetadataAppWeb.Sysadmin.ConsultaEditorLive` | `/sysadmin/bc-list/:nombre/consulta`, 5 pestañas. |
| Vista del usuario final | `MetadataAppWeb.CatalogoLive` (`montar_consulta/2`, `render/1` con `es_consulta?: true`) | Mismo LiveView que un catálogo, con otra rama de render. |
| API | `CatalogoController.index/2` → `ConsultaController.index/2` | `GET /api/:tabla`, la misma ruta que un catálogo. |
| Permisos | `CatalogoPermisosLive`, `Permissions` | Solo `~w(leer)` para una consulta. |

Una Consulta **no tiene** tabla física, módulo Ecto generado, motor de
estados ni TRN. Por eso `MetaSchemaContext.modulo_por_nombre/1` nunca
resuelve su nombre y los datos siempre se leen de los catálogos que
combina.

## 2. Modelo de datos

`meta_schema_consulta`:

| Columna | Tipo | Contenido |
|---|---|---|
| `meta_schema_header_id` | FK, única, `on_delete: :delete_all` | Encabezado dueño (R36: borrar el header borra la definición). |
| `catalogo_base` | string | Catálogo principal. |
| `campos` | `{:array, :map}` | Columnas; forma completa en el moduledoc de `MetaSchema.Consulta`. |
| `joins` | `{:array, :map}` | Uniones, en el orden en que se agregaron. |
| `orden_por` | `{:array, :map}` | `%{"catalogo", "campo", "direccion"}`, en orden de prioridad. |
| `insert_guid` / `update_guid` / `delete_guid` | string | Auditoría estándar. |

Claves relevantes de cada entrada de `campos`:

- Identidad: `catalogo`, `campo`, `etiqueta`, `tipo`, `orden`, `visible`.
- `control: true` marca un campo de control (R14). Su `campo` es la
  clave lógica (`estado`, `branch`, …) y `tipo` va en `nil`.
- Parámetros (`es_parametro`, `acotado`, `tipo_filtro`, `origen`,
  `catalogo_referenciado`, `defaults`): ver `SPEC-SYS-0209202601`.
- Totales, formato y resumen de selección (`agregacion_activa`,
  `total_general_activo`, `mascara_*`, `formato_*`, `resumen_seleccion_*`):
  ver `SPEC-SYS-0209202601` y `SPEC-SYS-0909202605`.

Cada entrada de `joins` tiene esta forma:
`%{"catalogo", "catalogo_destino", "campo_en_nuevo", "campo_en_destino", "tipo" => "left"}`.

## 3. Alta (R1-R4)

`BcListLive`:

- `"validar_consulta"` avisa en vivo si la ruta ya existe (R3).
- `"guardar_consulta"` valida en este orden: catálogo principal, luego
  etiqueta y ruta, luego ruta duplicada, luego tablas sin unión (R2, R3,
  R9).
- El nombre interno sale de `nombre_desde_nav_consulta/1`: prefijo
  `consulta_` más la ruta normalizada, con tope de 50 caracteres. No
  lleva `pty_` a propósito, porque una consulta sí se versiona en git.

Al guardar, dentro del mismo `with`:

1. `MetaSchemaContext.crear_header_con_detalles/1` con
   `schema_context_type: 3`, `schema_visible: true` y sin detalles.
2. `MetaConsultas.crear/2` llena `campos` con todos los
   `meta_schema_detail` del catálogo principal, visibles.
3. `agregar_tablas_relacionadas/2` aplica cada unión con
   `MetaConsultas.agregar_tabla_manual/5`. No vuelve a correr la
   detección: guarda exactamente lo que el admin vio en el modal. Cada
   tabla suma sus campos al final (`offset` = número de campos que ya
   había).

## 4. Detección de unión (R5-R10)

`MetaConsultas.detectar_union/2` es una función pura: no escribe en la
base. El modal la usa para mostrar en vivo la unión detectada. Prueba en
este orden:

1. **Maestro-detalle** (`detectar_union_maestro_detalle/2`) por
   `schema_encabezado_id`:
   - si la tabla nueva es detalle de una que ya está, la unión es
     `encabezado_id → id`;
   - si es maestro de una que ya está, la unión es `id → encabezado_id`.

   Va primero porque `encabezado_id` es una columna del framework que
   `listar_detalles/1` no ve.
2. **Dirección A:** la tabla nueva tiene un campo `referencia` hacia una
   presente. La unión es `<campo> → id`.
3. **Dirección B** (`detectar_union_desde_existentes/2`): una tabla
   presente tiene un campo `referencia` hacia la nueva. La unión es
   `id → <campo>`.

Si ninguna coincide, devuelve `:sin_union`. El editor manual (R7) ofrece:

- del lado de la tabla nueva, `campos_disponibles_para_union/1`: `id`,
  más `encabezado_id` si es detalle, más sus detalles;
- del lado destino, los mismos campos de cada tabla anterior.

El aviso de "una fila por renglón" (R8) sale de
`maestro_de_detalle/1`. `quitar_ultima_tabla/1` y el evento del modal
solo quitan la última tabla (R10).

`corregir_union/4` existe en el motor pero no tiene ninguna pantalla que
la use (ver §4 de requirements, "Tablas fijas después del alta").

## 5. Armado de la query (R11, R24)

`construir_query_base/1`:

- Da un binding nombrado a cada tabla: `:t0` al catálogo principal,
  luego `:t1`, `:t2`… en el orden de `joins`.
- Devuelve también el mapa `catalogo => alias`, que usan los filtros, el
  select y los totales.
- Base: `from r in <modulo>, as: :t0, where: is_nil(r.delete_guid)`.
- Cada unión es `LEFT JOIN` con `is_nil(delete_guid)` dentro del `ON`,
  así se excluyen los registros eliminados sin perder la fila principal
  (R11, R24).

Cada columna se expone con la clave compuesta
`ParametrosCatalogo.clave_campo/1`, que produce `:"<catalogo>__<campo>"`.
Así se distinguen dos campos con el mismo nombre en tablas distintas
(R34). Los campos de control se leen de su columna física
(`@campo_real_control`: `estado → estado_id`, `branch → branch_id`,
`inventory_location → inventory_id`, `sales_unit → sales_unit_id`).

## 6. Ejecución (`MetaConsultas.ejecutar/6`)

Pasos, en orden:

1. `construir_query_base/1`.
2. `aplicar_filtros/4`: filtros por nombre crudo. Se resuelven contra la
   **primera** coincidencia en `campos` (limitación de §4).
3. `aplicar_busqueda/4`: `ILIKE` sobre `::text`, unido con `OR` sobre
   los campos pedidos. La API no lo usa y la pantalla de la consulta no
   tiene caja de búsqueda.
4. `ParametrosCatalogo.aplicar_filtros_parametro_estandar/4`:
   parámetros resueltos por catálogo y campo, con los overrides de la
   sesión.
5. `aplicar_alcance_de_datos/4` (§7).
6. `total_filas` = `Repo.aggregate(:count)`. Se omite en modo cursor.
7. Filas: orden (`aplicar_orden/3` según `orden_por`, que ignora en
   silencio las entradas que ya no existen) o cursor, luego select de
   las visibles más `:id` del principal (lo necesita la selección),
   `aplicar_paginacion/2`, y al final la resolución de etiquetas (§8).
8. `totales/3`: `SUM` de los campos con `agregacion_activa` sobre toda la
   query filtrada, con `exclude(:order_by)`.

`contar/5` repite los pasos 1-5 más el conteo. Las opciones `:timeout` y
`:despues_de_id` (cursor) vienen de `SPEC-SYS-1009202602` y solo las usa
el endpoint.

Otras variantes:

- `agregar/6`: el valor que el usuario elige por columna
  (sum/avg/min/max/count). Aplica filtros, búsqueda y parámetros, pero
  **no el alcance** (limitación de §4, ya anotada en el código).
- `agregar_seleccionados/5` y `listar_seleccionados/3`: acotan solo por
  los ids seleccionados del principal, **con** alcance, e ignoran
  filtros y parámetros de la vista.

## 7. Permisos y alcance de datos (R21-R23)

- **Permiso:** `CatalogoPermisosLive` ofrece `~w(leer)` cuando
  `catalogo.es_consulta`. `Permissions.buscar_catalogos/2` deja pasar el
  tipo 3 sin exigir transiciones.
- **Menú:** `CatalogoLive.mount` verifica
  `Permissions.can?(scope, "leer", nombre)` antes de `montar_consulta/2`.
- **API:** el plug `RequierePermiso, accion: "leer"` de
  `CatalogoController` corre antes de delegar. Crear, editar o eliminar
  sobre una consulta no pasa, porque nunca se puede otorgar ese permiso
  (R35).
- **Alcance:** se aplica solo sobre `catalogo_base` y usa
  `alcance_habilitado` del header **del catálogo principal**, no de la
  consulta:
  - `Permissions.alcance_tipo_efectivo/2` decide el filtro: `:global`,
    `:empresa`, `:branch`, `:sales_unit`, `:inventory_location` o
    `:propio`;
  - `con_columna_alcance/5` no filtra nada si la columna no existe;
  - cada filtro deja pasar los registros con la columna en `NULL`;
  - con scope `nil` y alcance habilitado: `where false`;
  - con `:sistema`: sin filtro;
  - con `{:empresa_fija, id}` (endpoint): filtra siempre por `empresa_id`.

## 8. Resolución de etiquetas (R15)

Se resuelve por lotes, con una consulta por columna y por página, nunca
una por fila:

- `resolver_campos_control/3`: Estado sale de
  `MetaStateEngine.mapa_nombres_estados/1`; Sucursal, Almacén y Unidad
  de venta salen de `Autenticacion.obtener_*`.
- `resolver_campos_referencia/3`: los campos `tipo: "referencia"`
  reutilizan `CatalogoGenerico.etiqueta_para_referencia/2` y
  `modulo_destino_de/1`, igual que un catálogo normal.

## 9. Editor (R12-R20)

`ConsultaEditorLive` requiere `on_mount {Hooks.Autorizacion,
{"sysadmin_bc", "editar"}}`. Si el nombre no es de tipo 3, regresa a BC
List.

| Pestaña | Eventos / funciones | Persistencia |
|---|---|---|
| Configuración | `guardar_header` (`EncabezadoBcComponents`), `guardar_etiquetas`, `guardar_campos_control` → `sincronizar_campos_control/2` | Botón guardar. |
| Contrato | Documentación del `GET /api/:tabla` | Solo lectura. |
| Permisos | Incrusta `CatalogoPermisosLive` | La de permisos. |
| Get Config | `mover_a` (hook `ListaOrdenable`), `guardar_columnas`, `*_orden`, `cambiar_es_parametro` y demás toggles de parámetro, totales y formato | Inmediata por acción, salvo "Guardar columnas". |
| SQL | `query_representativa_con_filtros/1` → `Ecto.Adapters.SQL.to_sql/3` (subpestaña SQL) e `inspect/2` (subpestaña Ecto) | Solo lectura; nunca se ejecuta. |

Detalles:

- `claves_control_disponibles/1` filtra las claves de control según lo
  que el principal realmente tiene (R14).
- La identidad de una fila en el editor es `"<catalogo>::<campo>"`
  (`identificador/1`).
- `cambiar_es_parametro` solo permite prender el parámetro en una
  columna visible.
- `query_representativa_con_filtros/1` rellena con valores de ejemplo
  (`overrides_dummy/1`) los parámetros que todavía no tienen valor
  inicial, sin reemplazar uno real (R19).

## 10. Vista del usuario final (R25-R30)

`CatalogoLive.montar_consulta/2` traduce `consulta.campos` a la misma
forma de columna que un catálogo (`columna_desde_campo_consulta/2`).
Toma tipo y propiedades reales de `meta_schema_detail` en cada montaje;
no se guardan en la consulta.

- `cargar_todos_por_default?` siempre es `false` en una consulta. Por
  eso `datos_solicitados?/1` exige alguna de estas condiciones (R26):
  - un parámetro de fecha, que siempre acota;
  - un override de sesión;
  - una búsqueda.
- `cargar_filas_consulta/1` calcula `contar/5` + `ejecutar/6` con
  `@por_pagina 25` y el `offset` de `@pagina`. El render de consulta no
  tiene controles de paginación ni búsqueda (límite de §4), así que en
  la práctica siempre se ve la página 1.
- `ordenar_por_columna` guarda `orden_usuario`, que reemplaza a
  `orden_por` como una sola columna solo en la sesión (R28).
- Excel:
  - todas las filas: `filas_export/1` → `ejecutar/6` con `opciones = []`,
    sin límite;
  - seleccionadas: `listar_seleccionados/3` (R30).
- `panel_parametros`, `panel_campos` (columnas del usuario),
  `resumen_seleccion` y `celdas_resumen` son los mismos componentes que
  usa un catálogo BC.

## 11. API (R31-R35)

`ConsultaController.index/2`:

- `resolver_paginacion/1`: `pagina ≥ 1`, `por_pagina` default 25 y
  limitado a 1-100 (R32).
- `filtros_desde_params/2`: todo param que coincida con el nombre crudo
  de un campo de la consulta se convierte según su tipo (integer,
  referencia, decimal, boolean) y se filtra por igualdad (R33). Los de
  control son integer, salvo `trn`, que es string.
- Respuesta (`Jason.OrderedObject`): `meta_campos` (visibles, con
  `clave`, `catalogo`, `campo`, `etiqueta` y `tipo`), `data`, `totales`
  y `paginacion`.
- No tiene `show`, `create`, `update` ni `delete` para una consulta. El
  controlador genérico no resuelve módulo para el tipo 3 y el permiso
  tampoco se puede otorgar (R35).

## 12. Eliminación (R36)

`BcListLive` `"pedir_eliminar_consulta"` / `"confirmar_eliminar_consulta"`:
confirmación simple, sin `CatalogoGenerador.impacto/1`, porque no hay
tabla física. Luego `MetaSchemaContext.eliminar_header/1` → `Repo.delete`,
y el `ON DELETE CASCADE` (migración `20260728194748`) borra la fila de
`meta_schema_consulta`.
