## 1. Objetivo

Exponer una Consulta como una API HTTP propia y autocontenida —con su
propia ruta, sus propias credenciales y, opcionalmente, la capacidad de
dar de alta registros— para que un sistema externo consuma o cargue
datos sin pasar por la plataforma ni por un Usuario real.

## 2. ¿Quién utiliza esta funcionalidad?

- **Quien configura un endpoint** (ADN o plataforma): sección
  "Endpoints" (`/sysadmin/endpoints`), una capacidad de Sysadmin propia
  e independiente de "Business Process Builder" (se concede con su
  propio switch en la pestaña "Sysadmin" de un usuario).
- **Quien lo consume**: un sistema externo, con una credencial propia
  (API key) — nunca una persona logueada en la plataforma.

## 3. Conceptos que debo conocer

- **Endpoint**: la configuración publicable (nombre, método, ruta,
  parámetros, campos visibles, y opcionalmente alta) sobre una Consulta
  interna que se crea de forma transparente — nunca se administra esa
  Consulta como tal.
- **Borrador vs. publicado**: un endpoint guardado no responde llamadas
  externas hasta que se publica. Probarlo con datos reales NO requiere
  publicarlo antes.
- **Credencial**: una API key propia, generada por endpoint (puede
  haber varias). Cada una puede ver solo un subconjunto de los campos
  visibles del endpoint — el caller nunca puede pedir más de lo que su
  credencial ya tiene permitido.
- **Alcance por empresa**: los datos que devuelve un endpoint siempre
  son de la empresa donde se publicó — nunca hay filtro por usuario ni
  por permisos individuales, porque no hay un Usuario real detrás de una
  llamada externa.
- **Paginación por página vs. por cursor**: la forma normal es
  `pagina`/`por_pagina` (con tope máximo). Para resultados muy grandes,
  existe además un modo por cursor (bloques sucesivos sin repetir ni
  perder registros) y un modo asíncrono por Job (para traer TODO el
  resultado de una consulta enorme en segundo plano).
- **Alta vía POST**: opcional, exclusiva por endpoint — si está
  habilitada, un POST deja de interpretarse como filtro de búsqueda y
  pasa a insertar un registro nuevo (con sus renglones de detalle, si
  aplica).

## 4. Flujo general

1. Crear el endpoint desde la sección "Endpoints" (catálogo base +
   tabla detalle opcional).
2. Configurar campos visibles/parámetros, sin salir de esa pantalla.
3. Probar contra datos reales (opcional, no bloquea publicar).
4. Publicar — el endpoint empieza a responder llamadas externas.
5. Generar una credencial por cada sistema externo que vaya a
   consumirlo, con el subconjunto de campos que le corresponde.
6. (Opcional) Habilitar alta vía POST, si el endpoint necesita insertar
   registros en vez de (o además de) consultarlos.
7. (Opcional, con las salvedades del §7 de esta guía) Llevar el
   endpoint a otro ambiente.

## 5. Guía paso a paso

### 5.1 Crear un endpoint nuevo

1. Entrar a "Endpoints" (menú "Plataforma", capacidad `sysadmin_endpoints`
   — requiere además que Business Process Builder esté habilitado en
   ESE ambiente, ver §7).
2. "+ Nuevo endpoint": elegir el catálogo base y, si corresponde, una
   tabla detalle relacionada — la unión entre ambas se detecta sola. Si
   no se detecta ninguna relación válida, no se crea nada; hay que
   elegir otra tabla o dejarlo sin detalle.
3. Al confirmar, el endpoint queda creado de una en estado "borrador",
   con nombre/ruta autogenerados y método GET — aparece de inmediato en
   el listado, listo para configurar o para eliminar si se abandona a
   mitad de camino.

### 5.2 Configurar campos, parámetros y datos generales

1. Dentro de "Configurar" el endpoint: sección **Campos** — marcar
   Visible/Parámetro/Acotado/Tipo de filtro/Default por campo, sin
   salir de la pantalla (mismos controles que ya usa "Get Config").
2. Sección **Configuración del endpoint**: nombre, método (GET/POST),
   ruta (el prefijo fijo `/api/consultas/` se muestra fijo delante del
   input), descripción.
3. De los campos marcados como Parámetro en el paso 1, elegir cuáles
   participan como entrada del endpoint, y marcar cada uno como
   obligatorio u opcional. Cada parámetro puede tener su propia
   descripción de texto libre (se usa en la Documentación).
4. Guardar. Si algún parámetro configurado dejó de ser válido (el campo
   ya no es Parámetro, o se eliminó), el guardado se bloquea con un
   error señalando cuál — nunca queda un endpoint guardado apuntando a
   algo que ya no existe.

### 5.3 Probar el endpoint

1. Con el endpoint guardado (publicado o no), botón **Probar**: un
   mini-formulario pide un valor por cada parámetro configurado.
2. Ejecuta contra datos reales y muestra la respuesta JSON real,
   incluido el bloque `"meta"` de paginación.

### 5.4 Publicar y gestionar credenciales

1. Botón **Publicar** — el endpoint empieza a responder llamadas
   externas; aparecen el método y la ruta completa (con botón para
   copiarla).
2. Sección **Credenciales** → "+ Nueva credencial": nombre + qué
   campos visibles puede exponer esa credencial en particular.
3. Al crear (o regenerar) una credencial, la API key completa se
   muestra UNA sola vez — copiarla en ese momento, no se vuelve a
   mostrar completa nunca más (solo el sufijo, enmascarado).
4. Regenerar invalida de inmediato la key anterior de ESA credencial,
   sin afectar a las demás del mismo endpoint. Revocar la inutiliza
   para siempre (también sin afectar a las demás) — sigue apareciendo
   en la lista, marcada como revocada, para trazabilidad.
5. Crear o revocar una credencial no exige que el endpoint esté
   publicado — se pueden preparar de antemano.
6. **Despublicar** vuelve el endpoint a borrador — ninguna credencial,
   sin importar cuál, sigue funcionando mientras esté en ese estado.

### 5.5 Consultar la documentación

La sección **Documentación** (dentro de "Configurar") arma su
contenido leyendo el endpoint guardado: método, ruta, esquema de
autenticación (`Bearer`), cada parámetro con su clave/tipo/etiqueta/
descripción/obligatoriedad, la forma de la paginación, un ejemplo real
de lo que se puede enviar (query string para GET, body JSON para POST)
y un ejemplo de respuesta — nunca incluye una API key real, ni
enmascarada.

### 5.6 Invocar el endpoint (lado del sistema externo)

1. Header `Authorization: Bearer <api_key>` — nunca por query string ni
   por body.
2. GET: parámetros por query string. POST (modo consulta): parámetros
   en el body JSON.
3. Paginar con `pagina`/`por_pagina` (hay un tope máximo — un pedido
   por encima se recorta solo, nunca se rechaza), o con `cursor` para
   bloques sucesivos en consultas grandes (sin `"total"` en la
   respuesta en este modo, solo `"cursor_siguiente"`/`"tiene_mas"`).
4. Para una extracción completa de una consulta muy grande: encolar un
   Job (`POST .../jobs`, responde `202` con un `job_id` de inmediato) y
   consultar su estado (`GET .../jobs/:job_id`) hasta `"completado"`,
   momento en el que se puede descargar el resultado completo.

### 5.7 Habilitar alta de registros vía POST (opcional)

1. Solo disponible si el endpoint es método POST. Tarjeta "Alta de
   registros": activar el interruptor y marcar qué campos reales del
   catálogo puede mandar el caller externo.
2. Si el catálogo base tiene catálogos detalle reales, aparece además
   una sub-sección "Renglones" por cada uno, con su propia lista de
   campos habilitados.
3. Un campo tipo "referencia" habilitado se identifica del lado del
   caller por su descripción (nunca por un id interno) — la UI y la
   Documentación lo dejan explícito.
4. Con alta habilitada, un POST a ese endpoint deja de interpretarse
   como filtros: crea un encabezado (y sus renglones, si corresponden)
   con las mismas reglas que un alta manual (motor de estados, folio si
   el catálogo es transaccional). Responde `201` con el id del registro
   nuevo, o `422` con un mensaje si algo no pasó validación.

## 6. Ejemplos prácticos

### Ejemplo: consultar con paginación normal

```
GET /api/consultas/ventas-producto?pagina=1&por_pagina=50
Authorization: Bearer <api_key>
```

Devuelve `{"data": [...], "meta": {"pagina": 1, "por_pagina": 50, "total": N, "total_paginas": M}}`.

### Ejemplo: dar de alta un encabezado con renglones

```
POST /api/consultas/lista-precios
Authorization: Bearer <api_key>
Content-Type: application/json

{
  "descripcion": "Lista mayorista",
  "pty_lista_precios_det": [
    {"pty_lista_precios_det_productos": "Tornillo 3/4", "precio": 12.50}
  ]
}
```

`pty_lista_precios_det_productos` es un campo referencia — se manda su
descripción (el código/nombre que el sistema le da al producto), no un
id. Si esa descripción no coincide con exactamente un producto, el alta
completa se rechaza con `422` (sin insertar nada), distinguiendo "no
encontrado" de "ambiguo" (más de un producto con esa misma
descripción).

### Ejemplo: body con Content-Type incorrecto

Un caller que manda `Content-Type: text/plain` en vez de
`application/json` sobre un endpoint de alta ya no crea una fila vacía
en silencio — el sistema detecta que ninguna clave del body coincide
con los campos habilitados y responde `422` con la lista de campos que
sí acepta, para que el caller pueda comparar contra lo que mandó.

## 8. Casos comunes

- **Un pedido externo trae `empresa_id`** — se ignora siempre; la
  empresa sale únicamente de la configuración del endpoint.
- **Un pedido de `por_pagina` por encima del tope** — se recorta al
  tope, nunca se rechaza.
- **Dos endpoints con el mismo método y ruta** — no se puede guardar el
  segundo; el error aparece al guardar, no recién al publicar.
- **Más de un endpoint sobre la misma Consulta** — no está permitido,
  el modelo es uno como máximo.
- **Necesito acotar por sucursal/almacén, no solo por empresa** — no
  está soportado; el endpoint se publica igual, acotado solo por
  empresa (ver `00.doc_human.md`, "Lo que esta spec NO hace").

## 9. Errores y situaciones especiales

- **401** — falta el header `Authorization`, no trae el esquema
  `Bearer`, la key no matchea ninguna credencial activa, o la
  credencial fue revocada.
- **404** — ruta inexistente, o el endpoint existe pero está en
  borrador (ninguna credencial funciona mientras no esté publicado).
- **400** — falta un parámetro marcado como obligatorio.
- **422** (modo alta) — validación de campos, catálogo sin motor de
  estados configurado, referencia ambigua/no encontrada, o body sin
  ninguna coincidencia contra los campos habilitados.
- **504** — la consulta subyacente superó el tiempo máximo de
  ejecución configurado; se cancela y se responde el error, nunca se
  deja la conexión colgada.
- **Cada llamada (éxito o error, desde que el endpoint se resolvió)
  queda auditada** — fecha/hora, endpoint, empresa, IP, método,
  resultado HTTP, duración y cantidad de registros — nunca la API key
  ni los valores de los parámetros.

## 10. Resultado esperado

Un endpoint publicado, con al menos una credencial activa, responde
llamadas externas con exactamente los campos permitidos de esa
credencial, acotados a la empresa donde se publicó, paginados,
auditados, y rechazando cualquier intento de escribir por fuera de lo
explícitamente habilitado (alta) o de leer más allá de lo configurado.
