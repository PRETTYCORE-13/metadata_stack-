# SPEC-SYS-1009202602 — Endpoint a partir de una Consulta

**Documento:** Explicación general · **Fase:** ✅ aprobada (2026-09-10,
extendida en vivo hasta 2026-09-18).

## ¿Qué problema resuelve?

Hoy una Consulta (un Reporte armado en la plataforma) solo se puede ver
desde adentro de la propia aplicación — alguien tiene que entrar,
abrirla y mirarla en pantalla. Esta spec agrega una forma de exponer
esa misma Consulta como una API propia, con su propia dirección web y
su propia credencial de acceso, para que un sistema externo (un ERP, una
tienda online, cualquier programa ajeno) pueda pedirle datos
directamente, sin que nadie tenga que copiar información a mano ni
darle a ese sistema externo una cuenta de usuario real de la
plataforma.

## ¿Cómo funciona, a grandes rasgos?

Desde una sección propia llamada "Endpoints" (independiente de
cualquier Reporte que ya exista), se elige un catálogo base y,
opcionalmente, una tabla de detalle relacionada, y con eso se arma un
endpoint nuevo: un nombre, si responde a pedidos GET o POST, una
dirección fija bajo un prefijo reservado, qué campos se pueden ver y
cuáles sirven como filtro de entrada. El endpoint nace en "borrador",
se puede probar con datos reales sin exponerlo a nadie todavía, y
recién cuando está listo se "publica" — a partir de ahí responde
pedidos externos de verdad.

Para que un sistema externo pueda llamarlo, hace falta generarle una
credencial propia (una especie de contraseña larga) — se pueden emitir
varias credenciales distintas para el mismo endpoint, una por cada
sistema externo que lo use, y cada una puede tener acceso a un
subconjunto distinto de campos. Cualquier respuesta viene siempre
acotada a los datos de la empresa donde se publicó el endpoint, nunca
mezclada con otra, y siempre paginada (nunca todo de una vez). Además
del uso de solo lectura, un endpoint se puede configurar para que un
pedido POST, en vez de consultar, dé de alta un registro nuevo — con
las mismas reglas que si alguien lo cargara a mano desde la pantalla
(estado inicial, folio, validaciones), nunca escribiendo directo a la
base. Cada llamada, exitosa o rechazada, queda registrada (quién, a
qué hora, con qué resultado) — pero nunca se guarda la credencial usada
en ese registro.

## Historia

Esta spec se extendió varias veces en vivo, a pedido explícito, después
de su primera versión (que ya cubría lo esencial: configurar, publicar,
llamar, paginar, una sola credencial por endpoint). Entre los cambios
más importantes: pasó de una credencial única por endpoint a poder
tener varias, cada una viendo solo un subconjunto de campos; se agregó
soporte para consultas con cientos de miles de registros (por bloques,
o en segundo plano con seguimiento); se separó por completo de "crear
una Consulta primero" — ahora un endpoint se arma directo desde su
propia sección, eligiendo el catálogo, sin pasar por un Reporte; se
sumó la posibilidad de dar de alta registros (no solo consultar),
incluyendo sus renglones de detalle si el catálogo los tiene; y se
resolvió cómo identificar un campo de referencia (por su descripción,
no por un número interno — tras probar primero con otro criterio y
revertirlo a pedido explícito). Por último, se resolvió cómo llevar un
endpoint ya armado en desarrollo hacia otros ambientes (pruebas,
producción, un cliente puntual) — este último tramo, al cierre de esta
fase, todavía tiene partes pendientes de terminar (ver
`05.usage.md` para el detalle exacto de qué está disponible hoy).

## ¿Quién usa esta funcionalidad?

Dos perfiles distintos. Quien CONFIGURA un endpoint (elige el catálogo,
los campos, publica, genera credenciales) es del equipo de plataforma o
ADN, desde la sección "Endpoints" — una capacidad propia que se
concede por separado de cualquier otra. Quien CONSUME el endpoint es
un sistema externo (no una persona navegando la plataforma): con su
credencial, hace pedidos HTTP normales y recibe JSON de vuelta.

## Lo que esta spec NO hace

No agrega ningún control de acceso por usuario o por permiso individual
en la llamada externa — el único filtro es la empresa donde se publicó
el endpoint, igual para cualquier credencial válida de ese endpoint. No
limita cuántos pedidos por minuto puede hacer una credencial (esa
protección queda definida en el papel, pero no construida). No permite
acotar los datos por sucursal, almacén, unidad de venta o "solo lo
propio" — solo por empresa. No ofrece un editor de uniones manuales
entre más de dos tablas al armar un endpoint desde su sección propia
(para eso existe el camino ya existente de armar una Consulta completa
desde BC List). Y no toca ni modifica la ruta genérica que ya existía
antes de esta spec para exponer cualquier Consulta sin credencial
(`GET /api/<nombre_consulta>`) — se documenta como un hallazgo de
seguridad preexistente, pero queda fuera de esta spec a propósito.
