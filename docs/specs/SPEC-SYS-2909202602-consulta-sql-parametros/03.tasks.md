# SPEC-SYS-2909202602 — Consulta SQL con parámetros

**Documento:** Tasks · **Fase:** en definición, sin tareas iniciadas.

Cada tarea es chica y verificable. Es código del núcleo: va con tests
(`mix test` del archivo tocado) y, cuando toca la base, con verificación
real contra Postgres de dev en una transacción con rollback y sin
residuo. No correr `mix format` ni `mix precommit` completos (ver
memoria `feedback_mix_precommit_format`): formatear solo los archivos
tocados.

## Grupo A — Modelo, parámetros y traducción (§2, §3 pasos 1-2)

- [ ] A1. Migración del núcleo: `meta_schema_consulta_sql` + `parametros`
  (`jsonb`, default `[]`) y `tope_renglones` (entero, default 1000).
  Actualizar el schema `ConsultaSql` y su changeset: `uso` acepta
  `"servicio"`, y `tope_renglones` va de 1 a 5000.
- [ ] A2. `ConsultasSql.validar_parametros/1`: nombres con
  `^[a-z][a-z0-9_]{0,40}$`, tipos de la tabla de §2, sin repetidos, y
  default compatible con su tipo. Tests por cada rechazo.
- [ ] A3. Traductor de referencias (D3): del SQL con `:nombre` saca la
  versión de validación (`(NULL::tipo_pg)`) y la de función
  (`p_nombre`). Salta textos entre `'...'` y `"..."`, comentarios `--` y
  `/* */`, y los casts `::tipo`. Rechaza un `:nombre` no declarado y un
  parámetro obligatorio que no aparece (R3). Tests con casts, textos con
  `:` adentro y comentarios.
- [ ] A4. Verificar contra Postgres real, en una transacción con
  rollback, que una función `LANGUAGE sql STABLE` con `BEGIN ATOMIC` que
  contiene `INSERT`, `UPDATE` o `DELETE` se rechaza **al crearla**. Si
  no se rechaza, volver a `02.design.md` §3 antes de seguir y agregar
  una validación propia.
- [ ] A5. R6: `cambiar_uso` rechaza cambiar de o hacia `"servicio"`.
  Test.

## Grupo C — Ejecutar (§4)

- [ ] C1. Conversión de valores por tipo (R7): enteros, decimales,
  fechas ISO, sí/no, y listas de enteros a partir de una lista JSON o de
  un texto `"1,2,3"`. Completa defaults, exige obligatorios y el error
  nombra el parámetro. Tests.
- [ ] C2. `ejecutar_servicio/3`: `SELECT * FROM fn($1..$n) AS r
  [WHERE alcance] LIMIT tope+1`, con los valores siempre como
  parámetros (R8). Test con un valor malicioso como texto (no tiene
  efecto) y como entero (se rechaza).
- [ ] C3. Condición de alcance como SQL con parámetros, con el mismo
  criterio que `alcance_por_columnas/3` para `%Scope{}`,
  `{:credencial, _}` y `:sistema` (R11). Tests por tipo de alcance.
- [ ] C4. Aislamiento (D5): sin transacción, `READ ONLY` + timeout; con
  transacción, `SAVEPOINT` → timeout → consulta → `ROLLBACK TO
  SAVEPOINT`, siempre. Verificar en dev:
  - Un error dentro de una transacción abierta no la aborta: una
    consulta posterior de la misma transacción funciona.
  - Después de la llamada, el `statement_timeout` es el de antes.
  - El Servicio ve una fila insertada en esa misma transacción y
    todavía no confirmada (R14).
- [ ] C5. Tope (R10): con `tope_renglones` = 2 y 3 filas de resultado,
  la llamada da error y no regresa filas. Test.
- [ ] C6. Tiempo máximo (R9): un Servicio con `pg_sleep` que supera el
  límite regresa `{:error, :tiempo_excedido}`. Test.
