# SPEC-SYS-2909202602 — Consulta SQL con parámetros

**Documento:** Design · **Fase:** en definición.

## 1. Decisiones de fondo

| # | Decisión | Por qué |
|---|---|---|
| D1 | Un Servicio es una **función SQL de Postgres** (`LANGUAGE sql STABLE`, cuerpo `BEGIN ATOMIC`), generada por migración como hoy la vista | Es el mismo modelo que la SQL View (SPEC-SYS-2509202601 R10): Postgres valida tablas y columnas al crearla, registra sus dependencias en `pg_depend` y viaja por migración con `motor.publicar`. Los servidores usan Postgres 16/17, y `BEGIN ATOMIC` existe desde la 14 |
| D2 | Descartado: guardar el SQL como texto y ejecutarlo con valores en cada llamada | Sin `pg_depend`, R21 no se podría cumplir; se reinterpreta el texto en cada llamada, y va contra el criterio de R10 de 2509 |
| D3 | En el SQL, quien lo escribe se refiere a un parámetro como **`:nombre`**; la plataforma lo traduce | Es legible y no choca con los casts `::tipo` de Postgres. La traducción la hace un analizador que salta textos entre comillas, comentarios y `::` |
| D4 | Obligatoriedad y default los resuelve **la plataforma antes de llamar**; la función siempre recibe todos sus argumentos (`NULL` si es opcional sin default) | Los `DEFAULT` de Postgres solo sirven al final de la firma y complican cambiar la lista. Así R7 se valida en un solo lugar, con mensajes propios |
| D5 | Ejecución dentro de un **SAVEPOINT** cuando ya hay una transacción abierta | `SET LOCAL statement_timeout` y cualquier error se revierten con `ROLLBACK TO SAVEPOINT`, sin abortar la transacción de la regla (R13). Además ve los datos todavía no confirmados de esa transacción (R14) |
| D6 | La API reutiliza **`ConsultaEndpoint`**, que ahora puede colgar de una Consulta Ecto **o** de un Servicio | Credenciales, alcance por credencial, auditoría, documentación y publicación ya existen (SPEC-SYS-1009202602); R16 pide no duplicarlos |

## 2. Modelo de datos (tablas del núcleo, migración normal en el repo)

**`meta_schema_consulta_sql`**:
- `uso`: se agrega el valor `"servicio"` (R1).
- `parametros` (nuevo, `{:array, :map}`, default `[]`): cada uno
  `%{"nombre", "tipo", "obligatorio", "default"}` (R2).
- `tope_renglones` (nuevo, entero, default 1000, máximo 5000) (R10).

Tipos de parámetro y su tipo en Postgres:

| Tipo (R2) | Postgres | Valor Elixir |
|---|---|---|
| entero | `bigint` | `integer` |
| decimal | `numeric` | `Decimal` |
| texto | `text` | `String` |
| fecha | `date` | `Date` |
| sí/no | `boolean` | `boolean` |
| lista de enteros | `bigint[]` | lista de `integer` |

Nombre de parámetro: `^[a-z][a-z0-9_]{0,40}$`. En la función se llama
`p_<nombre>`; el prefijo evita choques con columnas de las tablas.

**`meta_schema_consulta_endpoint`**:
- `meta_schema_consulta_sql_id` (nuevo, FK opcional).
- `meta_schema_consulta_id` pasa a opcional.
- Constraint de base: exactamente uno de los dos (D6).
- Para un Servicio, `parametros` del endpoint se **deriva** del Servicio
  y no se edita a mano (R16).

## 3. Guardar un Servicio (`ConsultasSql.guardar_sql/2`, rama `"servicio"`)

1. **Validar los parámetros declarados**: nombres, tipos, sin
   repetidos, y que un default corresponda a su tipo.
2. **Traducir referencias** (D3): cada `:nombre` se convierte en dos
   versiones del SQL:
   - **De validación**: `:nombre` → `(NULL::tipo_pg)`.
   - **De la función**: `:nombre` → `p_nombre`.
   Un `:nombre` no declarado se rechaza (R3). Un parámetro obligatorio
   que no aparece en el SQL también se rechaza (R3).
3. **Validar contra la base** con la versión de validación, usando el
   camino de hoy: `CREATE TEMP VIEW` en una transacción que siempre se
   revierte. Eso rechaza varias sentencias y lo que no sea lectura (R4),
   y `leer_columnas/1` da las columnas de salida (R5), que se guardan en
   `columnas`.
4. **Generar la migración** `<ts>_funcion_<nombre>_<ts>.exs`
   (`ruta_migracion("funcion", ...)`, con el mismo sufijo de timestamp
   que la vista):

   ```sql
   DROP FUNCTION IF EXISTS pty_sql_x;
   CREATE FUNCTION pty_sql_x(p_direccion_id bigint, p_productos bigint[], p_fecha date)
   RETURNS TABLE (material_id bigint, precio_caja numeric, ...)
   LANGUAGE sql STABLE
   BEGIN ATOMIC
     <SQL de la función>;
   END
   ```

   `DROP` + `CREATE` y no `CREATE OR REPLACE`, porque este último no
   permite cambiar las columnas de salida (mismo criterio que la vista).
   El SQL entra al archivo como literal con `inspect/1`, como hoy. Si la
   migración falla, se borra el archivo y no se toca la metadata.
5. **Guardar** `sql`, `parametros`, `columnas` y `tope_renglones`.

`STABLE` hace que Postgres rechace un `INSERT`/`UPDATE`/`DELETE` dentro
de la función. Se verifica en tasks A, junto con el paso 3.

**R6**: `cambiar_uso/…` rechaza cambiar de o hacia `"servicio"`.

## 4. Ejecutar (`ConsultasSql.ejecutar_servicio/3`)

```elixir
ejecutar_servicio(nombre, valores, alcance)
# alcance: %Scope{} | :sistema | {:credencial, credencial}
# -> {:ok, %{columnas: [...], filas: [map]}} | {:error, motivo}
```

1. **Parámetros** (R7): se completan defaults, se exigen obligatorios y
   se convierte cada valor a su tipo. Si falla, error que nombra el
   parámetro, sin tocar la base.
2. **SQL de la llamada**, con valores **siempre** como `$n` (R8):

   ```sql
   SELECT * FROM pty_sql_x($1, $2, $3) AS r
   WHERE <condición de alcance sobre r.branch_id / r.sales_unit_id / r.inventory_id>
   LIMIT <tope + 1>
   ```

   La condición de alcance (R11) se arma con el mismo criterio de
   `alcance_por_columnas/3`, pero como SQL con parámetros, porque
   `fragment` de Ecto no admite un número variable de argumentos. Solo
   aplica si `columnas` tiene columnas de control; `:sistema` no acota.
3. **Tiempo máximo y aislamiento** (R9, D5):
   - Sin transacción abierta: transacción `READ ONLY` +
     `SET LOCAL statement_timeout`, igual que hoy.
   - Con transacción abierta (una regla): `SAVEPOINT svc` →
     `SET LOCAL statement_timeout` → consulta → `ROLLBACK TO SAVEPOINT
     svc`, siempre, haya éxito o error. Se revierte el timeout y, si
     falló, la transacción de la regla sigue sana.
4. **Tope** (R10): si regresa más de `tope_renglones` filas, error "el
   resultado excede N renglones"; nunca se recorta.

## 5. Desde un BC (R13-R15)

`MetadataApp.MetaBcApi.ejecutar_servicio(nombre, valores, contexto)` es
la ayuda que usan las reglas `Pre`/`Post`:
- Con `contexto["usuario_id"]`: alcance de ese usuario.
- Sin usuario (llamada de sistema): `:sistema`, mismo criterio que el
  resto de `MetaBcApi`.
- Servicio inexistente: `{:error, "No existe el servicio <nombre> en
  este ambiente."}` (R15).

## 6. Por API (R16-R18)

- **Alta**: desde el Servicio (tab Contrato o `/sysadmin/endpoints` →
  "Nuevo desde Servicio"), con el mismo flujo que desde una Consulta.
- **Controller** (`ConsultaEndpointController`): si el endpoint tiene
  `meta_schema_consulta_sql_id`, delega en `ejecutar_servicio/3` con
  `{:credencial, credencial}`. Credencial, auditoría y rechazo de
  `empresa_id` externo son los mismos de hoy.
- **Lista de enteros por `GET`**: `?productos=1,2,3` o
  `?productos[]=1&productos[]=2`. Por `POST`: arreglo JSON.
- **Respuesta**: `{"data": [...], "meta_campos": [...]}`, sin
  paginación (R18). Los Jobs no aplican.

## 7. Dependencias (R21, R22)

- `catalogos_que_usa/1` y `vistas_que_dependen/2` suman una rama para
  funciones: `pg_depend d JOIN pg_proc p ON p.oid = d.objid AND
  d.classid = 'pg_proc'::regclass`. Con `BEGIN ATOMIC`, Postgres
  registra las tablas y columnas que usa el cuerpo, así que borrar una
  columna usada se rechaza con el mismo mensaje de hoy.
- **Eliminar un Servicio** se rechaza si:
  - Un `ConsultaEndpoint` lo referencia (FK).
  - Su nombre aparece en el código de reglas de algún catálogo
    (`meta_schema_reglas_codigo.codigo_fuente`). Es una búsqueda por
    texto: puede dar un falso positivo con un comentario, pero nunca un
    falso negativo con una llamada real.

## 8. Pantalla (R19, R20)

`ConsultaSqlEditorLive` con uso Servicio:
- **Parámetros**: tabla editable (nombre, tipo, obligatorio, default).
- **Tope de renglones**.
- **Probar**: un formulario generado a partir de los parámetros que
  llama a `ejecutar_servicio/3` con el alcance del usuario y muestra las
  filas o el error.
- **Contrato**: parámetros, columnas de salida y ejemplo de llamada
  desde una regla (`MetaBcApi.ejecutar_servicio/3`) y, si tiene
  Endpoint, su ruta.

## 9. Publicación (R23)

`exportar_definicion/1` e `importar_definicion/2` agregan `parametros` y
`tope_renglones`. La migración `*_funcion_pty_sql_*` entra al paquete
igual que `*_vista_pty_sql_*`; su nombre contiene `pty_sql_`, así que
cumple la regla de CI para migraciones sobre objetos `pty_`. Los
catálogos que usa se agregan con la rama de funciones de §7.
