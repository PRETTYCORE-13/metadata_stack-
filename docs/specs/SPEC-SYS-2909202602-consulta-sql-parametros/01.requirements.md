# SPEC-SYS-2909202602 — Consulta SQL con parámetros

**Documento:** Requirements · **Fase:** en definición.

## Contexto

Pedido explícito (2026-09-29): un módulo al que se le den unos pocos
datos (por ejemplo, dirección, productos y fecha) y resuelva una
respuesta de negocio, como el precio de venta, que se pueda usar desde
cualquier BC y por API. El primer caso real es SPEC-ADN-2909202602.

Hallazgos de la revisión del código (2026-09-29) que acotan esta spec:

- La Consulta SQL (SPEC-SYS-2509202601) no admite parámetros (su R6).
  El SQL se convierte en una vista fija, y su API (`GET`) solo pagina:
  no filtra ni recibe valores.
- Los Endpoints (SPEC-SYS-1009202602) ya resuelven llave de acceso,
  auditoría, documentación y publicación entre ambientes, pero solo
  sobre una Consulta Ecto, que no puede partir de una Consulta SQL.
- Las reglas de un BC ya son código por catálogo (`Pre`/`Post`) y pueden
  llamar funciones de ayuda de la plataforma. Falta una ayuda para
  ejecutar una consulta de negocio con valores.
- La lógica de negocio de cada cliente vive en catálogos `pty_`, que no
  viajan en el repo. Por eso un resolvedor no puede ser código del
  núcleo: tiene que ser un artefacto de negocio que se publica con
  `motor.publicar`.

## 1. Uso "Servicio" y sus parámetros

R1. EL SISTEMA DEBE ofrecer un tercer uso de la Consulta SQL,
**Servicio**, además de Diccionario y Consulta. Un Servicio no aparece
en el menú ni alimenta combos: solo se ejecuta cuando alguien lo llama
con sus parámetros (§3 y §4).

R2. UN Servicio DEBE poder declarar uno o más **parámetros**, cada uno
con: nombre, tipo, si es obligatorio y, opcionalmente, un valor por
default. Tipos admitidos: entero, decimal, texto, fecha, sí/no y
**lista de enteros** (por ejemplo, varios productos en una sola
llamada).

R3. EL SQL de un Servicio DEBE referirse a cada parámetro por su
nombre. CUANDO se guarda, EL SISTEMA DEBE rechazarlo si el SQL usa un
parámetro que no está declarado, o si hay un parámetro obligatorio
declarado que el SQL no usa.

R4. CUANDO se guarda el SQL de un Servicio, EL SISTEMA DEBE aplicar las
mismas validaciones que a cualquier Consulta SQL (SPEC-SYS-2509202601
R7 y R8): una sola sentencia de lectura, validada contra la base real y
con el error de la base mostrado de forma legible. Todo esto sin
ejecutarlo con datos reales.

R5. CUANDO se guarda un Servicio válido, EL SISTEMA DEBE registrar las
columnas que regresa (nombre y tipo), que forman su contrato de salida.

R6. EL SISTEMA NO DEBE permitir cambiar el uso de un Servicio a
Diccionario o Consulta, ni al revés: sus reglas de validación y de
ejecución son distintas.

## 2. Ejecución

R7. CUANDO se ejecuta un Servicio, EL SISTEMA DEBE validar los valores
recibidos antes de correr el SQL. Si falta un parámetro obligatorio sin
default, o un valor no corresponde a su tipo, DEBE rechazar la llamada
con un error claro que nombre el parámetro, sin ejecutar nada.

R8. LOS valores de los parámetros DEBEN tratarse siempre como datos,
nunca como parte del texto del SQL. Un valor como `1; DROP TABLE x` es
simplemente un valor inválido para un entero o un texto sin efecto.

R9. TODA ejecución de un Servicio DEBE ser de solo lectura y tener un
tiempo máximo, igual que cualquier Consulta SQL (SPEC-SYS-2509202601
R13). Si lo excede, se corta y regresa un error claro.

R10. UN Servicio DEBE tener un **tope de renglones por llamada**. CUANDO
el resultado lo excede, EL SISTEMA DEBE rechazar la llamada con un error
claro y NO DEBE regresar un resultado recortado en silencio. Un
resolvedor con datos incompletos, como una lista de precios a la que le
faltan productos, es peor que un error.

R11. CUANDO el resultado de un Servicio expone las columnas de control
de alcance (`branch_id`, `sales_unit_id`, `inventory_id`), EL SISTEMA
DEBE acotarlo al alcance de quien llama: al del usuario si lo llama una
regla de un BC, y al de la credencial si lo llaman por API (igual que
SPEC-SYS-1009202602 R22). CUANDO no las expone, NO DEBE acotar, y el
tab Configuración DEBE avisarlo.

R12. UNA misma llamada, con los mismos parámetros y el mismo alcance,
DEBE regresar el mismo resultado sin importar si llega desde un BC o
por API.

## 3. Desde un BC

R13. LAS reglas de cualquier BC (`Pre` y `Post`) DEBEN poder ejecutar
un Servicio por su nombre, pasándole sus parámetros, y recibir los
renglones resultantes o un error estructurado. Nunca una excepción que
tumbe la operación.

R14. CUANDO una regla ejecuta un Servicio durante una transición, el
Servicio DEBE ver los datos de esa misma operación en curso, incluidos
los cambios todavía no confirmados (por ejemplo, los renglones que se
están agregando a un pedido en esa misma transición).

R15. CUANDO el Servicio que llama una regla no existe en el ambiente
(por ejemplo, porque no se publicó junto con el BC), EL SISTEMA DEBE
regresar un error claro que lo nombre, para que la regla decida qué
hacer.

## 4. Por API

R16. EL SISTEMA DEBE permitir crear un **Endpoint** (SPEC-SYS-1009202602)
sobre un Servicio, con todo lo que ya ofrece un Endpoint:
- Prefijo de ruta reservado.
- Credenciales propias, con su alcance.
- Auditoría de cada llamada.
- Documentación, publicación y despublicación.

Los parámetros del Endpoint son los del Servicio, con su mismo tipo y
obligatoriedad (R2). No se pueden elegir otros.

R17. UN Endpoint sobre un Servicio DEBE aceptar tanto `GET` (parámetros
en la dirección, con varios valores para una lista) como `POST`
(parámetros en el cuerpo JSON), con el mismo resultado. `POST` existe
porque una lista larga de productos no cabe cómodamente en una
dirección.

R18. LA respuesta de un Endpoint sobre un Servicio DEBE ser JSON con el
resultado completo (no paginado, porque ya está acotado por R10) y las
columnas del contrato de salida (R5).

## 5. Pantalla

R19. EL tab Configuración de un Servicio DEBE permitir declarar, editar
y quitar sus parámetros (R2), y **probarlo**: capturar valores de
prueba, ejecutarlo y ver el resultado, con las mismas reglas de R7-R11.

R20. EL tab Contrato de un Servicio DEBE documentar sus parámetros
(nombre, tipo, obligatorio, default) y sus columnas de salida, y cómo
llamarlo desde una regla de BC.

## 6. Dependencias y publicación

R21. CUANDO se intenta eliminar un campo o un catálogo que usa el SQL de
un Servicio, EL SISTEMA DEBE avisarlo y rechazarlo, igual que con
cualquier Consulta SQL (SPEC-SYS-2509202601 R29).

R22. CUANDO se intenta eliminar un Servicio que usa un Endpoint o que
aparece en las reglas de algún BC, EL SISTEMA DEBE avisarlo y
rechazarlo.

R23. `mix motor.publicar` DEBE llevar un Servicio completo (encabezado,
SQL, parámetros y contrato de salida) junto con los catálogos que su SQL
usa, de forma que en el destino funcione igual.

## 7. Seguridad y compatibilidad

R24. SOLO un usuario con el permiso de administración de catálogos
(`sysadmin_bc`) DEBE poder crear o editar un Servicio. Ejecutarlo desde
un BC no requiere ese permiso: lo decide la regla del BC.

R25. LAS Consultas SQL que ya existen (usos Diccionario y Consulta)
DEBEN seguir funcionando exactamente igual. Esta spec no les agrega
parámetros.

## 8. Fuera de alcance

- SQL que modifique datos: un Servicio solo lee (R9).
- Parámetros de tipo tabla o de estructura libre (por ejemplo, una
  lista de pares producto-cantidad). Si hace falta, se agrega un tipo
  nuevo en esta spec.
- Guardar resultados en caché: cada llamada consulta la base. Si hace
  falta por volumen, se evalúa aparte con mediciones reales.
- Llamadas asíncronas o por lotes grandes (Jobs de SPEC-SYS-1009202602):
  un Servicio es de respuesta inmediata y acotada (R10).
- Resolvedores de negocio concretos: cada uno va en su propia spec ADN
  (el primero, SPEC-ADN-2909202602).
