# SPEC-SYS-2909202602 — Consulta SQL con parámetros

**Documento:** Explicación general · **Fase:** en definición.

## ¿Qué problema resuelve?

Hoy la plataforma tiene la **Consulta SQL**: alguien escribe un SQL de
solo lectura y la plataforma lo convierte en una vista que se puede
consultar como una tabla más. Su límite es que el SQL es fijo, no recibe
datos de quien pregunta. Sirve para listas del tipo "los clientes
activos", pero no para preguntas que dependen de algo que llega en el
momento, como "¿qué precio tiene este producto, para este cliente, en
esta fecha?".

Ese tipo de pregunta aparece cada vez más en el negocio: el precio de
un producto, el crédito disponible de un cliente, qué promociones le
aplican, a qué ruta le toca una dirección. Son "resolvedores": reciben
unos pocos datos y regresan una respuesta calculada. Hoy no hay forma
de construirlos dentro de la plataforma. La alternativa sería
programarlos en el núcleo, pero el núcleo es el mismo para todos los
clientes y cada cliente resuelve estas preguntas a su manera.

## ¿Cómo funciona, a grandes rasgos?

Se agrega a la Consulta SQL la posibilidad de declarar **parámetros**:
valores con nombre y tipo que quien pregunta manda en cada llamada. Por
ejemplo, una dirección de entrega, una lista de productos y una fecha.
El SQL los usa donde los necesita y la plataforma lo ejecuta con esos
valores, siempre en modo de solo lectura y con un tiempo máximo.

Una misma Consulta SQL con parámetros se puede usar de dos formas, y
en las dos da exactamente el mismo resultado:

- **Desde un BC:** la regla de un catálogo (por ejemplo, al agregar un
  renglón a un pedido) la llama para obtener un dato y guardarlo.
- **Por API:** un sistema externo, una integración o la app móvil la
  llama por internet con su propia llave de acceso, igual que los
  Endpoints que ya existen.

Como la lógica vive una sola vez, en la Consulta, nunca hay dos formas
de calcular lo mismo que puedan dar resultados distintos.

Igual que la Consulta SQL de hoy, la plataforma revisa que el SQL sea
válido y que solo lea datos, nunca que los modifique. Además se publica
a otros ambientes junto con los catálogos de negocio. Así, cada cliente
puede tener sus propios resolvedores sin tocar el núcleo.

## ¿Quién usa esta funcionalidad?

- **Quien construye catálogos** (equipo de plataforma o ADN con
  conocimiento de SQL): escribe la Consulta, declara sus parámetros y la
  conecta a las reglas de sus BC.
- **Quien integra otros sistemas** (app móvil, ERP externo): la llama por
  API con los parámetros que pide.
- **El usuario final** no la ve. Ve el resultado: un precio que se llena
  solo en el pedido, un aviso de crédito agotado, etc.

## Lo que esta spec NO hace

No construye ningún resolvedor de negocio en particular. El primero, el
precio de venta, vive en su propia spec (SPEC-ADN-2909202602). No
permite SQL que modifique datos. No cambia las Consultas SQL sin
parámetros que ya existen, que siguen funcionando igual. Tampoco
reemplaza a las Consultas (reportes) ni a sus Endpoints.
