# SPEC-SYS-2509202601 — Consulta SQL (Diccionario, Consulta y Servicio)

**Documento:** Guía de uso · Grupos A-J verificados (2026-09-25) · Uso Servicio, grupos K-P verificados (2026-09-30; su publicación a otros ambientes, grupo Q, todavía no).

## 1. Objetivo

Armar listas de datos con condiciones que cruzan varios catálogos (por
ejemplo, "almacenes de tipo COMPROMETIDA", "empleados de ventas que no
deben dinero") escribiendo un SQL de lectura. La plataforma lo convierte
en una vista y la usa como una tabla más: para los combos de los campos
referencia (uso **Diccionario**) o como reporte de solo lectura (uso
**Consulta**).

## 2. ¿Quién utiliza esta funcionalidad?

Quien construye catálogos en el BPB (equipo de plataforma o ADN que sabe
SQL), desde BC List. El usuario final solo ve el resultado: combos que
ofrecen lo que corresponde y, si la SQL View es visible, un listado en el
menú.

## 3. Conceptos que debo conocer

- **SQL View:** un BC tipo 4. Su nombre técnico siempre empieza con
  `pty_sql_` y es también el nombre de la vista en la base.
- **Diccionario:** su SQL debe regresar una columna `id` entera (lo que
  se guarda en el campo) y al menos una columna de descripción.
- **Consulta:** reporte de solo lectura. Basta con una columna.
- **BC autorizados:** los catálogos que pueden elegir un Diccionario en
  sus campos. Solo ellos lo ven.
- **Alcance automático:** si el SQL regresa `branch_id`, `sales_unit_id`
  o `inventory_id`, las filas se acotan a lo que el usuario puede ver. El
  administrador ve todo.

## 4. Flujo general

1. BC List → **"+ SQL View"**: etiqueta, navegación y uso.
2. En su editor → Configuración: pegar el SQL → **Validar y guardar**.
3. Si es Diccionario: en "BC que pueden usarla", autorizar los catálogos.
4. En el Motor BC del catálogo autorizado → campo referencia →
   **Filtros** → "Filtrar por diccionario".

## 5. Guía paso a paso

### 5.1 Crear la SQL View

1. `/sysadmin/bc-list` → **"+ SQL View"**.
2. Etiqueta, carpeta y nombre en el menú (la vista previa muestra la ruta
   y el nombre técnico `pty_sql_…`), y el uso: Diccionario o Consulta.
3. **Crear**: abre su editor. Nace sin SQL y **no visible**.

### 5.2 Escribir el SQL (tab Configuración)

1. Pega una sola consulta de lectura (`SELECT` o `WITH … SELECT`), sin
   parámetros. Si necesitas parámetros, el uso es **Servicio** (§11).
2. **Validar y guardar.** La base de datos revisa el SQL; si algo está
   mal, se muestra su mensaje y no se guarda nada.
3. Al guardar se ven las **columnas detectadas**, una **vista previa de 5
   filas** y el aviso de **alcance** (qué columna de control acota, o que
   no se acota).
4. Cada vez que guardas se genera una migración nueva
   (`<fecha>_vista_pty_sql_….exs`). Esa migración queda fuera de git y
   viaja al publicar.

Nombres de columna: solo minúsculas, números y guion bajo. Si una
columna sale con otro nombre, renómbrala con `AS`.

### 5.3 Autorizar BC (solo Diccionario)

1. En "BC que pueden usarla", busca el catálogo y **+ Autorizar**.
2. La tabla muestra, por BC, qué campos lo usan ("Sin uso todavía" si
   ninguno).
3. **Quitar** no deja retirar un BC que tiene campos usándolo.

### 5.4 Usarlo en un campo referencia

1. Motor BC del catálogo autorizado → fila del campo referencia →
   **Filtros**.
2. Sección **"Filtrar por diccionario"**: elige el Diccionario y marca
   las columnas que forman la descripción del combo.
3. Opcional: en cada filtro fijo o dependencia, **"Aplicar sobre"** →
   "Columnas del Diccionario" para filtrar por una columna de la vista
   (por ejemplo, la unidad de venta elegida en el formulario contra
   `sales_unit_id`).
4. **Guardar.** Se verifica que todos los `id` del Diccionario existan en
   el catálogo destino del campo.

Desde ahí, el combo solo ofrece los registros del Diccionario, y al
guardar un registro (pantalla o API) se rechaza un valor que no esté en
él: "el valor seleccionado no está en el diccionario de este campo".

### 5.5 Contrato y Permisos

- **Contrato:** `GET /api/pty_sql_…` con `pagina` y `por_pagina` (25 por
  defecto, máximo 100). Responde `meta_campos`, `data` y `paginacion`.
- **Permisos:** solo la acción `leer`. Se registra sola al crear la SQL
  View; se concede a roles como cualquier otro catálogo.

## 6. Ejemplos prácticos

### Almacenes de reparto (verificado en dev el 2026-09-25)

```sql
SELECT il.id, il.inventory_name AS nombre, il.branch_id
FROM meta_schema_inventory_location il
WHERE il.delete_guid IS NULL AND upper(il.inventory_type) = 'COMPROMETIDA'
```

Uso Diccionario, descripción `nombre`, acotado por `branch_id`. Usado en
un campo Almacén, el combo solo ofrece los almacenes COMPROMETIDA de las
sucursales del usuario.

## 7. Casos comunes

- **"Mi Diccionario no aparece en Filtros"**: revisa que el BC esté
  autorizado, que la SQL View **no** sea visible, que su uso sea
  Diccionario y que ya tenga SQL guardado.
- **"El combo sale vacío"**: el Diccionario se combina con los filtros
  fijos y la cascada del campo; un filtro fijo sobre otra columna puede
  estar dejando fuera todo.
- **"No me deja eliminar un campo de un catálogo"**: si una SQL View lo
  usa, el mensaje la nombra. Ajusta su SQL primero.
- **"No puedo cambiar el Diccionario a Consulta o volverlo visible"**:
  algún campo lo usa; aparecen en el mensaje.

## 8. Errores y situaciones especiales

- Toda ejecución tiene un máximo de 5 segundos. Si se excede, se cancela
  con un mensaje claro.
- Solo se aceptan consultas de lectura; varias sentencias, `INSERT`,
  `UPDATE`, `DELETE` o cambios de estructura se rechazan.
- La validación al guardar un registro no aplica el alcance (el
  changeset no conoce la sesión); el combo sí lo aplica.
- Una SQL View solo se edita en desarrollo; a otros ambientes llega con
  `mix motor.publicar`, junto con los catálogos que usa su SQL.

## 9. Resultado esperado

Una SQL View guardada existe como vista en la base, aparece en BC List
con la etiqueta "SQL View", tiene su permiso `leer` y, si es un
Diccionario autorizado, puede elegirse en los filtros de los campos
referencia de sus BC autorizados.

## 11. Uso Servicio: una consulta con parámetros

### 11.1 Para qué sirve

Un **Servicio** responde una pregunta de negocio que depende de datos que
llegan en el momento: "¿qué precio tiene este producto para este cliente
en esta fecha?", "¿cuánto crédito le queda?". Se escribe una sola vez, en
SQL, y lo usan:

- **Las reglas de cualquier BC**, por ejemplo para llenar el precio de un
  renglón de pedido.
- **Otros sistemas por API** (la app, un ERP), con su propia llave.

Las dos formas dan el mismo resultado. Un Servicio no aparece en el menú
ni en combos, y su uso no se puede cambiar a Diccionario o Consulta ni al
revés.

### 11.2 Crear el Servicio y sus parámetros

1. `/sysadmin/bc-list` → **"+ SQL View"** → uso **Servicio** → **Crear**.
2. En su editor, tab **Configuración** → **"+ Agregar parámetro"** por
   cada dato que va a recibir:
   - **Nombre:** minúsculas, números y guion bajo, empezando con letra
     (por ejemplo, `direccion_id`).
   - **Tipo:** Entero, Decimal, Texto, Fecha, Sí/No o **Lista de
     enteros** (para mandar varios valores a la vez, como varios
     productos).
   - **Obligatorio** y, si quieres, un **Default**.
   - **Cuidado:** un parámetro nuevo nace como **Entero**. Si es una
     lista, cambia el tipo antes de guardar.
3. En el SQL, usa cada parámetro como `:nombre`:
   ```sql
   SELECT t.id, t.nombre
   FROM (VALUES (1,'uno'),(2,'dos'),(3,'tres')) AS t(id, nombre)
   WHERE t.id = ANY(:ids)
   ```
   Una lista se usa con `= ANY(:parametro)`. Dentro de textos entre
   comillas o comentarios, `:nombre` no se toca, y `x::date` sigue siendo
   un cast normal.
4. **Tope de renglones por llamada** (1,000 por default, máximo 5,000):
   si un resultado lo pasa, la llamada se rechaza completa. Nunca regresa
   un resultado recortado.
5. **Validar y guardar.** La base revisa el SQL y crea la función
   `pty_sql_…`. Se ven las **columnas detectadas** y el aviso de
   **alcance**.

### 11.3 Probar

En el panel **Probar**, a la derecha de las columnas, captura un valor
por parámetro (una lista como `1,3`, una fecha como `AAAA-MM-DD`) →
**Probar**. Muestra las filas, o el error: por ejemplo, *"Falta el
parámetro obligatorio «ids»."*. Se ejecuta con tu alcance de datos.

### 11.4 Llamarlo desde una regla de BC

El tab **Contrato** trae el ejemplo armado con sus parámetros:

```elixir
MetaBcApi.ejecutar_servicio("pty_sql_…", %{"ids" => [101, 102]})
```

Regresa `{:ok, %{columnas: [...], filas: [%{"columna" => valor}]}}` o
`{:error, motivo}`. Corre como sistema (sin acotar al usuario), dentro de
la transacción de la regla: ve lo que la regla ya cambió, y un error no
la aborta. Verificado en dev con una regla `Post` real que guardó el
resultado en su registro.

### 11.5 Exponerlo por API

En el tab **Contrato** → **"Por API"**. Crear, publicar y eliminar solo
se puede en local; las credenciales, en cualquier ambiente.

1. **Nombre** y **Ruta** → **Crear endpoint**. Nace en **BORRADOR** y
   así **no responde** (quien lo llame recibe 404).
2. **Publicar** para activarlo.
3. **Credenciales:** una por cada sistema que lo va a usar. Nombre y
   columnas que puede recibir → **"+ Credencial"**. La llave se muestra
   **una sola vez**: cópiala en ese momento. Si se pierde o se filtra,
   revócala y crea otra.

Llamada, por ejemplo desde Postman (verificado el 2026-09-30):

- `GET http://<servidor>/api/consultas/<ruta>?ids=1,3`, o
  `POST` a la misma ruta con cuerpo JSON `{"ids": [1, 3]}`. Responde por
  los dos métodos, sin importar cuál se configuró.
- **Authorization:** `Bearer <llave>`.
- Respuesta: `{"data": [...], "meta_campos": [...]}`, sin paginar, solo
  con las columnas que permite la credencial.

| Respuesta | Cuándo |
|---|---|
| 200 | Correcto |
| 400 | Parámetro faltante o inválido (el mensaje lo nombra) |
| 401 | Sin llave, llave inválida o revocada |
| 404 | La ruta no existe o el Endpoint está en borrador |
| 422 | El resultado pasa el tope |
| 504 | Tardó más del tiempo máximo |

Cada llamada queda en la auditoría del Endpoint. `/sysadmin/endpoints` lo
lista con la etiqueta **SERVICIO**, y "Configurar" lleva a su tab
Contrato.

### 11.6 Casos comunes

- **"op ANY/ALL (array) requires array on right side"** al guardar: usas
  `= ANY(:x)` y `:x` no es **Lista de enteros**. El mensaje trae la
  ayuda con el parámetro a corregir.
- **"El SQL usa parámetros que no están declarados"**: falta agregarlo en
  la tabla, o el nombre no coincide.
- **"Hay parámetros obligatorios que el SQL no usa"**: quítalo o úsalo en
  el SQL.
- **Postman responde 404:** el Endpoint sigue en borrador, o la ruta no
  coincide.
- **Postman responde 401:** la llave es de una credencial revocada, o se
  copió incompleta.
- **"No se puede eliminar: lo usa el Endpoint…" / "…lo usan las reglas
  de…"**: primero elimina el Endpoint o quita la llamada en esas reglas.
- **"No puedo borrar un campo de un catálogo"**: si un Servicio lo usa,
  el mensaje lo nombra, igual que con una SQL View.
