# SPEC-SYS-2509202601 — Consulta SQL (Diccionario, Consulta y Servicio)

**Documento:** Requirements · **Fase:** ✅ §1-§10 aprobadas (2026-09-25) · §11 uso Servicio aprobada (2026-09-29).

## Contexto

Pedido explícito (2026-09-25): hay listas para combos que no salen de un
solo catálogo, sino de condiciones que cruzan varios (empleados de
ventas que no deben dinero, rutas de preventa de la sucursal actual con
perfil activo, clientes activos de la unidad de venta elegida sin
venta). Antes se resolvían con un SQL escrito a mano que regresaba la
llave y un campo de acompañamiento.

**Hallazgos de la revisión del código (2026-09-25) que acotan esta spec:**

- Un campo `referencia` solo puede apuntar a catálogos tipo 1 y a
  tablas de sistema (`MetaSchemaContext.listar_catalogos_referenciables/0`).
  Sus combos se filtran por cascada, filtros fijos (SPEC-SYS-1109202601
  §2.1) y alcance de datos, pero nada de eso expresa "que no exista" ni
  "suma mayor a".
- La Consulta Ecto (`schema_context_type: 3`, `MetaConsultas`) solo une
  tablas que existen (inner join) y no tiene condiciones fijas: sus
  condiciones son parámetros con valor por default. A pedido explícito,
  **esta spec no toca la Consulta Ecto**: el caso se resuelve con un
  tipo de catálogo nuevo.
- Se descartó traducir el SQL a una query Ecto: no hay un traductor
  confiable y se perdería todo lo que no sea trivial (`NOT EXISTS`,
  subconsultas, `CASE`). El SQL se guarda tal cual y la base de datos lo
  convierte en una vista, que la plataforma consulta como una tabla más
  (detalle en `02.design.md`).

## 1. Alta y encabezado

R1. EL SISTEMA DEBE ofrecer en BC List el alta de una **Consulta SQL**,
con el mismo encabezado que una Consulta Ecto (`EncabezadoBcComponents`):
Etiqueta, Navegación (carpeta + slug, con vista previa de la ruta),
Ícono (selector visual) y "Es visible".

R2. EL encabezado de una Consulta SQL DEBE incluir un selector de
**uso**, con tres opciones: **Diccionario** (lista para alimentar combos
de campos referencia), **Consulta** (reporte de solo lectura) o
**Servicio** (consulta con parámetros para reglas de BC y API; §11,
agregado el 2026-09-29).

R3. CUANDO una Consulta SQL (de cualquier uso) está marcada como
visible, EL SISTEMA DEBE mostrarla en el menú en su ruta como un listado
de solo lectura, paginado, con las columnas y el orden que entrega su
SQL. CUANDO no es visible, NO DEBE aparecer en el menú.

R4. CUANDO se intenta cambiar el uso de un Diccionario a Consulta, o
marcarlo como visible, mientras algún campo referencia lo usa (§7), EL
SISTEMA DEBE rechazarlo y mostrar qué BC y campos lo usan.

R5. UNA Consulta SQL DEBE poder publicarse a otros ambientes como
cualquier catálogo de negocio (§9).

## 2. Configuración: el SQL

R6. EL tab Configuración DEBE tener, además del encabezado, una sección
para pegar el SQL. En los usos Diccionario y Consulta, la Consulta SQL
NO DEBE tener parámetros ni filtros propios: el SQL queda fijo, y lo
variable se aplica desde afuera sobre sus columnas (§4 y §7). El uso
Servicio (§11, agregado el 2026-09-29) es la excepción: sí declara
parámetros.

R7. CUANDO se guarda el SQL, EL SISTEMA DEBE rechazarlo si no es una
sola sentencia de lectura (`SELECT`, o `WITH ... SELECT`): nada de
varias sentencias, ni altas, cambios, bajas o cambios de estructura.

R8. CUANDO se guarda el SQL, EL SISTEMA DEBE validarlo contra la base
de datos real (sintaxis, tablas y columnas existentes) y, si falla,
mostrar el error de la base de forma legible, sin guardar nada.

R9. CUANDO el uso es Diccionario, EL SISTEMA DEBE exigir que el
resultado del SQL tenga una columna llamada `id`, de tipo entero, y al
menos una columna más (la descripción o acompañamiento). Si falta,
rechaza el guardado.

R10. CUANDO se guarda un SQL válido, EL SISTEMA DEBE convertirlo en una
vista de la base de datos, de modo que al usarla (combo, reporte, API)
la plataforma la consulte como una tabla, sin volver a ejecutar SQL como
texto.

R11. CUANDO se edita el SQL de un Diccionario que algún campo usa, EL
SISTEMA DEBE rechazar la nueva versión si pierde la columna `id` o
alguna columna que esos campos usen (descripción, cascada, filtros).

R12. EL tab Configuración DEBE mostrar, después de guardar, las
columnas detectadas (nombre y tipo) y una vista previa de las primeras
5 filas.

R13. TODA ejecución de una Consulta SQL (vista previa, combo, reporte,
API) DEBE tener un tiempo máximo. Si lo excede, se corta y se muestra un
mensaje claro, sin bloquear la pantalla ni la base.

## 3. BC que pueden usar el Diccionario

Pedido explícito (2026-09-25): evita que al configurar un campo
referencia aparezcan todos los Diccionarios del sistema, y deja a la
vista qué BC dependen de cada Consulta SQL.

R14. CUANDO el uso es Diccionario, EL tab Configuración DEBE tener una
sección **"BC que pueden usarla"**, donde se agregan y quitan los BC de
negocio (catálogos tipo 1) autorizados a usar ese Diccionario, eligiendo
de una lista con búsqueda.

R15. LA sección de R14 DEBE mostrar, por cada BC autorizado, qué campos
de ese BC usan el Diccionario hoy (o "sin uso todavía"). Es la vista de
dependencias de la Consulta SQL.

R16. SOLO un BC autorizado en R14 DEBE poder elegir el Diccionario en el
formulario "Filtros" de sus campos referencia (§7).

R17. CUANDO se intenta quitar de la lista de R14 un BC que tiene campos
usando el Diccionario, EL SISTEMA DEBE rechazarlo y mostrar esos campos.

R18. LA lista de BC autorizados DEBE viajar con la Consulta SQL al
publicarla (§9).

## 4. Uso como reporte (Consulta)

R19. CUANDO el uso es Consulta, EL SISTEMA NO DEBE exigir la columna
`id`: basta con al menos una columna.

## 5. Alcance de datos

R20. CUANDO el resultado del SQL expone las columnas de control de
alcance (`branch_id`, `sales_unit_id`, `inventory_id`, con la misma
convención que los catálogos), EL SISTEMA DEBE acotar el resultado al
alcance de datos del usuario, igual que en cualquier catálogo. CUANDO
no las expone, NO DEBE acotar, y el tab Configuración DEBE avisarlo.

## 6. Contrato, Permisos y tabs

R21. EL tab Contrato DEBE documentar únicamente el endpoint de lectura
(`GET`): ruta, paginación, formato de respuesta y columnas. Nunca
`POST`/`PUT`/`DELETE`. Aplica la misma seguridad de API que una Consulta
Ecto (ver SPEC-SYS-2209202601).

R22. EL tab Permisos DEBE comportarse igual que en una Consulta Ecto:
solo la acción `leer`, y el alcance de datos mostrado como referencia de
solo lectura.

R23. LOS tabs de una Consulta SQL DEBEN ser, en este orden:
Configuración, Contrato y Permisos.

## 7. Diccionario en un campo referencia

Complementa SPEC-SYS-1109202601 (formulario "Filtros" de un campo
referencia), que se actualiza aparte.

R24. EL formulario "Filtros" de un campo referencia DEBE ofrecer una
sección **"Filtrar por diccionario"** que solo lista Consultas SQL con
uso Diccionario, **no visibles** y que tengan autorizado el BC del
campo (R16).

R25. CUANDO se elige un Diccionario, EL SISTEMA DEBE pedir qué columnas
del Diccionario forman la descripción del combo (al menos una) y
verificar que todos los `id` que entrega el Diccionario existen en el
catálogo destino del campo. Si alguno no existe, rechaza la
configuración (así la llave foránea del campo nunca recibe un id
inválido).

R26. CUANDO un campo referencia tiene Diccionario, EL SISTEMA DEBE
ofrecer en el combo solo los `id` del Diccionario, sin repetidos, con la
descripción elegida en R25, y aplicando además el alcance de datos
(R20), la cascada y los filtros fijos del campo.

R27. LA cascada y los filtros fijos de un campo con Diccionario DEBEN
poder aplicarse sobre columnas del Diccionario (por ejemplo, la unidad
de venta elegida en el formulario contra la columna `sales_unit_id` del
Diccionario), no solo sobre columnas del catálogo destino.

R28. CUANDO se guarda un registro (por pantalla o por API) y el valor de
un campo con Diccionario CAMBIÓ, EL SISTEMA DEBE confirmar del lado del
servidor que el id está en el Diccionario, con el mismo alcance,
cascada y filtros del momento. Si no, rechaza el guardado con un error
legible en ese campo. Mismo criterio que SPEC-SYS-1109202601 R27.

## 8. Dependencias

R29. CUANDO se intenta eliminar un campo o un catálogo que el SQL de
una Consulta SQL usa, EL SISTEMA DEBE rechazarlo con un mensaje que
nombre la Consulta SQL que lo usa, en vez de un error técnico de la base.

R30. CUANDO se intenta eliminar una Consulta SQL con uso Diccionario
que algún campo referencia usa, EL SISTEMA DEBE rechazarlo y mostrar qué
BC y campos lo usan (R15).

## 9. Publicación

R31. `mix motor.publicar` DEBE llevar una Consulta SQL completa: su
encabezado, su SQL, la creación de su vista y su lista de BC autorizados
(R18), de forma que en el destino quede funcionando igual.

R32. CUANDO se publica una Consulta SQL, EL SISTEMA DEBE incluir en el
paquete los catálogos que su SQL usa. CUANDO se publica un catálogo con
un campo que usa un Diccionario, DEBE incluir ese Diccionario.

## 10. Seguridad

R33. SOLO un usuario con el permiso de administración de catálogos
(`sysadmin_bc`, el mismo del Motor BC) DEBE poder crear o editar una
Consulta SQL. Su ejecución DEBE ser siempre de solo lectura.

## 11. Uso Servicio: Consulta SQL con parámetros (ampliación 2026-09-29)

**Contexto.** Pedido explícito (2026-09-29): un módulo al que se le den
unos pocos datos (por ejemplo, dirección, productos y fecha) y resuelva
una respuesta de negocio, como el precio de venta, que se pueda usar
desde cualquier BC y por API. El primer caso real es SPEC-ADN-2909202602.
Se integra a esta spec como tercer uso de la Consulta SQL, en lugar de
una spec aparte, para que la Consulta SQL quede documentada en un solo
lugar.

Hallazgos de la revisión del código (2026-09-29):

- Los usos Diccionario y Consulta no admiten parámetros (R6). El SQL se
  convierte en una vista fija, y su API (`GET`) solo pagina.
- Los Endpoints (SPEC-SYS-1009202602) ya resuelven llave de acceso,
  auditoría, documentación y publicación entre ambientes, pero solo
  sobre una Consulta Ecto, que no puede partir de una Consulta SQL.
- Las reglas de un BC ya son código por catálogo (`Pre`/`Post`) y pueden
  llamar funciones de ayuda de la plataforma. Falta una ayuda para
  ejecutar una consulta de negocio con valores.
- La lógica de negocio de cada cliente vive en catálogos `pty_`, que no
  viajan en el repo. Por eso un resolvedor no puede ser código del
  núcleo: tiene que ser un artefacto de negocio que se publica con
  `motor.publicar`.

### 11.1 El uso y sus parámetros

R34. EL SISTEMA DEBE ofrecer un tercer uso de la Consulta SQL,
**Servicio**, además de Diccionario y Consulta. Un Servicio no aparece
en el menú ni alimenta combos: solo se ejecuta cuando alguien lo llama
con sus parámetros (§11.3 y §11.4).

R35. UN Servicio DEBE poder declarar uno o más **parámetros**, cada uno
con: nombre, tipo, si es obligatorio y, opcionalmente, un valor por
default. Tipos admitidos: entero, decimal, texto, fecha, sí/no y
**lista de enteros** (por ejemplo, varios productos en una sola
llamada).

R36. EL SQL de un Servicio DEBE referirse a cada parámetro por su
nombre. CUANDO se guarda, EL SISTEMA DEBE rechazarlo si el SQL usa un
parámetro que no está declarado, o si hay un parámetro obligatorio
declarado que el SQL no usa.

R37. CUANDO se guarda el SQL de un Servicio, EL SISTEMA DEBE aplicar
las mismas validaciones que a cualquier Consulta SQL (R7 y R8): una sola
sentencia de lectura, validada contra la base real y con el error de la
base mostrado de forma legible. Todo esto sin ejecutarlo con datos
reales.

R38. CUANDO se guarda un Servicio válido, EL SISTEMA DEBE registrar las
columnas que regresa (nombre y tipo), que forman su contrato de salida.

R39. EL SISTEMA NO DEBE permitir cambiar el uso de un Servicio a
Diccionario o Consulta, ni al revés: sus reglas de validación y de
ejecución son distintas.

### 11.2 Ejecución

R40. CUANDO se ejecuta un Servicio, EL SISTEMA DEBE validar los valores
recibidos antes de correr el SQL. Si falta un parámetro obligatorio sin
default, o un valor no corresponde a su tipo, DEBE rechazar la llamada
con un error claro que nombre el parámetro, sin ejecutar nada.

R41. LOS valores de los parámetros DEBEN tratarse siempre como datos,
nunca como parte del texto del SQL. Un valor como `1; DROP TABLE x` es
simplemente un valor inválido para un entero o un texto sin efecto.

R42. TODA ejecución de un Servicio DEBE ser de solo lectura y tener un
tiempo máximo, igual que cualquier Consulta SQL (R13). Si lo excede, se
corta y regresa un error claro.

R43. UN Servicio DEBE tener un **tope de renglones por llamada**. CUANDO
el resultado lo excede, EL SISTEMA DEBE rechazar la llamada con un error
claro y NO DEBE regresar un resultado recortado en silencio. Un
resolvedor con datos incompletos, como una lista de precios a la que le
faltan productos, es peor que un error.

R44. CUANDO el resultado de un Servicio expone las columnas de control
de alcance (`branch_id`, `sales_unit_id`, `inventory_id`), EL SISTEMA
DEBE acotarlo al alcance de quien llama: al del usuario si lo llama una
regla de un BC, y al de la credencial si lo llaman por API (igual que
SPEC-SYS-1009202602 R22). CUANDO no las expone, NO DEBE acotar, y el
tab Configuración DEBE avisarlo (igual que R20).

R45. UNA misma llamada, con los mismos parámetros y el mismo alcance,
DEBE regresar el mismo resultado sin importar si llega desde un BC o
por API.

### 11.3 Desde un BC

R46. LAS reglas de cualquier BC (`Pre` y `Post`) DEBEN poder ejecutar
un Servicio por su nombre, pasándole sus parámetros, y recibir los
renglones resultantes o un error estructurado. Nunca una excepción que
tumbe la operación.

R47. CUANDO una regla ejecuta un Servicio durante una transición, el
Servicio DEBE ver los datos de esa misma operación en curso, incluidos
los cambios todavía no confirmados (por ejemplo, los renglones que se
están agregando a un pedido en esa misma transición).

R48. CUANDO el Servicio que llama una regla no existe en el ambiente
(por ejemplo, porque no se publicó junto con el BC), EL SISTEMA DEBE
regresar un error claro que lo nombre, para que la regla decida qué
hacer.

### 11.4 Por API

R49. EL SISTEMA DEBE permitir crear un **Endpoint** (SPEC-SYS-1009202602)
sobre un Servicio, con todo lo que ya ofrece un Endpoint:
- Prefijo de ruta reservado.
- Credenciales propias, con su alcance.
- Auditoría de cada llamada.
- Documentación, publicación y despublicación.

Los parámetros del Endpoint son los del Servicio, con su mismo tipo y
obligatoriedad (R35). No se pueden elegir otros.

R50. UN Endpoint sobre un Servicio DEBE aceptar tanto `GET` (parámetros
en la dirección, con varios valores para una lista) como `POST`
(parámetros en el cuerpo JSON), con el mismo resultado. `POST` existe
porque una lista larga de productos no cabe cómodamente en una
dirección.

R51. LA respuesta de un Endpoint sobre un Servicio DEBE ser JSON con el
resultado completo (no paginado, porque ya está acotado por R43) y las
columnas del contrato de salida (R38).

### 11.5 Pantalla

R52. EL tab Configuración de un Servicio DEBE permitir declarar, editar
y quitar sus parámetros (R35), y **probarlo**: capturar valores de
prueba, ejecutarlo y ver el resultado, con las mismas reglas de
R40-R44.

R53. EL tab Contrato de un Servicio DEBE documentar sus parámetros
(nombre, tipo, obligatorio, default) y sus columnas de salida, y cómo
llamarlo desde una regla de BC.

### 11.6 Dependencias y publicación

R54. CUANDO se intenta eliminar un campo o un catálogo que usa el SQL de
un Servicio, EL SISTEMA DEBE avisarlo y rechazarlo, igual que con
cualquier Consulta SQL (R29).

R55. CUANDO se intenta eliminar un Servicio que usa un Endpoint o que
aparece en las reglas de algún BC, EL SISTEMA DEBE avisarlo y
rechazarlo.

R56. `mix motor.publicar` DEBE llevar un Servicio completo (encabezado,
SQL, parámetros y contrato de salida) junto con los catálogos que su SQL
usa, de forma que en el destino funcione igual (como R31 y R32).

### 11.7 Seguridad y compatibilidad

R57. SOLO un usuario con el permiso de administración de catálogos
(`sysadmin_bc`) DEBE poder crear o editar un Servicio (como R33).
Ejecutarlo desde un BC no requiere ese permiso: lo decide la regla del
BC.

R58. LOS usos Diccionario y Consulta DEBEN seguir funcionando
exactamente igual. El uso Servicio no les agrega parámetros.

## 12. Fuera de alcance

- Parámetros o filtros dentro del SQL en los usos Diccionario y Consulta
  (R6). Solo el uso Servicio los tiene (§11).
- SQL que modifique datos, en cualquier uso: un Servicio solo lee (R42).
- Parámetros de tipo tabla o de estructura libre (por ejemplo, una
  lista de pares producto-cantidad). Si hace falta, se agrega un tipo
  nuevo en §11.
- Guardar resultados de un Servicio en caché: cada llamada consulta la
  base. Si hace falta por volumen, se evalúa aparte con mediciones
  reales.
- Llamadas asíncronas o por lotes grandes (Jobs de SPEC-SYS-1009202602):
  un Servicio es de respuesta inmediata y acotada (R43).
- Resolvedores de negocio concretos: cada uno va en su propia spec ADN
  (el primero, SPEC-ADN-2909202602).
- La Consulta Ecto y su motor (`MetaConsultas`): no se modifican.
- Reportes de usuario complejos con más funciones (totales, exportar,
  parámetros de usuario): el uso Consulta deja la base; se amplía en una
  spec futura.
- Búsqueda en el servidor mientras se escribe en el combo: se mantiene
  el mismo límite de 500 opciones que el resto de los combos. Si un
  Diccionario crece más, se atiende en una spec aparte.
- Traducir el SQL a Ecto (descartado, ver Contexto).
