# SPEC-SYS-2509202601 — Consulta SQL (Diccionario de datos y Consulta)

**Documento:** Design · **Fase:** ✅ aprobada (2026-09-25).

Idea central: el SQL se guarda tal cual y se convierte en una **vista de
Postgres** mediante una migración generada. En tiempo de uso, la
plataforma consulta la vista con **Ecto sin schema** (`from v in
"pty_sql_x"`), igual que a una tabla, así que nunca vuelve a ejecutar
SQL como texto. No se genera un módulo `.ex` por Consulta SQL: no hay
código compilado que desplegar, solo metadata más la migración de la
vista.

## 1. Tipo, nombre y almacenamiento (R1-R5)

- **Tipo de BC:** `schema_context_type: 4` ("Consulta SQL"). Hoy existen
  1 (catálogo), 2 (carpeta) y 3 (Consulta Ecto). El árbol del menú ya
  incluye cualquier tipo distinto de 2, así que un tipo 4 visible
  aparece solo (R3).
- **Nombre técnico:** `pty_sql_<slug de la navegación>`, máximo 50
  caracteres (mismo cálculo que `nombre_desde_nav_consulta/1`, con otro
  prefijo). El prefijo `pty_` es obligatorio: la migración de la vista
  queda fuera del repo compartido (`.gitignore`
  `priv/repo/migrations/*pty_*.exs`) y entra al paquete de
  `mix motor.publicar` por el comodín `*<catalogo>*.exs` de
  `MetaPublicador` (lección del CI roto el 2026-09-24). El nombre de la
  vista en Postgres es el mismo `schema_context_name`.
- **Tabla nueva `meta_schema_consulta_sql`** (core, migración `meta_*`
  que sí va al repo):

| Columna | Tipo | Nota |
|---|---|---|
| `meta_schema_header_id` | FK → `meta_schema_header`, único | 1 a 1 con el encabezado |
| `uso` | string: `"diccionario"` \| `"consulta"` | R2 |
| `sql` | text | el SQL tal cual lo pegó el usuario |
| `columnas` | jsonb `[%{"nombre", "tipo"}]` | detectadas al guardar (R12); fuente para selects y validaciones |
| `bcs_autorizados` | `{:array, :string}` | **nombres** de catálogo, no ids: los ids cambian entre ambientes y esto se publica (R14, R18) |
| `insert_guid`/`update_guid`/`delete_guid`, timestamps | | convención de siempre |

- **Cambio de uso o de visible (R4):** `EncabezadoBcComponents.guardar/2`
  recibe una validación extra para el tipo 4. Si hay campos que usan el
  Diccionario (§5), rechaza pasar a "consulta" o a `schema_visible: true`.

## 2. Guardar el SQL (R6-R13)

Módulo nuevo `MetadataApp.ConsultasSql`. Guardar es un flujo en dos
pasos:

**Paso 1: validar en una transacción que siempre se revierte.**

1. Una sola sentencia (R7): la consulta se manda por el protocolo
   extendido de Postgrex (`Repo.query/3` con parámetros), que rechaza
   varias sentencias ("cannot insert multiple commands into a prepared
   statement"). No hace falta parsear el texto.
2. `SET LOCAL statement_timeout` (R13) y luego
   `CREATE TEMP VIEW _validacion_sql AS <sql>`. Postgres rechaza todo lo
   que no sea una consulta de lectura: un `INSERT`/`UPDATE`/`DELETE`
   suelto no es un `SELECT`, y una vista no admite sentencias que
   modifican datos dentro de un `WITH` (R7). También valida la sintaxis
   y que las tablas y columnas existan (R8); su mensaje de error se
   muestra tal cual, sin la parte técnica del driver.
3. Leer las columnas de la vista temporal (`pg_attribute` +
   `format_type`) → `columnas` (R12).
4. Si es Diccionario: exigir la columna `id` de tipo entero y al menos
   otra (R9). Si ya hay campos que lo usan, exigir que sigan existiendo
   `id` y cada columna que esos campos usan (R11).
5. `ROLLBACK`.

**Paso 2: generar y correr la migración de la vista** (R10), con el
mismo patrón que `CatalogoGenerador` (archivo con timestamp en
`priv/repo/migrations/`, que se corre en el acto):

```elixir
# <ts>_vista_pty_sql_<slug>_<ts>.exs  (el <ts> repetido hace único el nombre; ver la nota final de 03.tasks.md)
def up do
  execute "DROP VIEW IF EXISTS pty_sql_<slug>"
  execute "CREATE VIEW pty_sql_<slug> AS <sql>"
end

def down, do: execute("DROP VIEW IF EXISTS pty_sql_<slug>")
```

`DROP` + `CREATE`, y no `CREATE OR REPLACE`: este último no permite
quitar ni renombrar columnas. Cada edición del SQL genera **una
migración nueva**, así que el historial viaja completo y en orden al
publicar.

**Ajuste al implementar (2026-09-25):** la migración **no** corre dentro
de la transacción que guarda la metadata. Correr `Ecto.Migrator` anidado
en una transacción es frágil (bug real 2026-09-07, ver
`BcMotorLive.transaccion_con_generador/2`): pide su propia conexión y
commitea por su cuenta de todos modos. `guardar_sql/2` lo hace en
secuencia: validar → escribir y correr la migración (si falla, se borra
el archivo y no se toca la metadata) → guardar la fila. Se reusan
`CatalogoGenerador.timestamp_migracion/0` y
`CatalogoGenerador.correr_migraciones_pendientes/0`, expuestos para esto.
Igual que los catálogos, solo se permite donde está activo
`generar_catalogos_en_caliente` (dev/test); en producción la vista llega
por `motor.publicar`. El SQL entra al archivo con `inspect/1`, como un
literal de string escapado, así el texto del administrador nunca se
interpreta como código.

**Vista previa (R12):** 5 filas de la vista real, con la ejecución
segura de §3.

## 3. Ejecución segura (R13, R33)

Toda lectura (vista previa, combo, reporte, API, validación al guardar
un registro) pasa por una sola función:

```elixir
ConsultasSql.ejecutar(fn -> Repo.all(query) end)
# Repo.transaction: SET TRANSACTION READ ONLY; SET LOCAL statement_timeout = '5s'; ...
```

- **Solo lectura real:** aunque el SQL llame a una función que intente
  escribir, la transacción de solo lectura lo impide.
- **Tiempo máximo:** 5 segundos por defecto. El error `57014`
  (query_canceled) se traduce a `{:error, :tiempo_excedido}` con mensaje
  claro. El `SET LOCAL` muere con la transacción, sin afectar a otras
  conexiones del pool.
- **Dentro de una transacción ya abierta** (ajuste al implementar: la
  validación de R28 corre dentro de la transacción que guarda el
  registro): `SET TRANSACTION READ ONLY` solo se puede al inicio de una
  transacción, así que en ese caso `ejecutar/1` solo aplica el tiempo
  máximo con `SET LOCAL` y lo restaura al terminar. La vista ya fue
  validada al guardarse; el `READ ONLY` sigue aplicando en el combo, el
  reporte, la API y la vista previa.

**Consultas sin schema:** `Ecto.Queryable.to_query("pty_sql_x")` +
`field(v, ^columna)`. Al guardar el SQL se valida que cada nombre de
columna cumpla `^[a-z_][a-z0-9_]{0,62}$` y queda registrado en
`columnas`. Al usarlo, `ConsultasSql.atomo_columna/1` lo convierte con
`String.to_atom/1`, solo con ese formato y en la práctica solo con
nombres ya registrados. (Ajuste al implementar: convertir "una sola vez
al guardar" no basta, porque los átomos no sobreviven un reinicio de la
aplicación.) Es una excepción acotada a la regla de no crear átomos
desde texto del usuario: solo lo hace un administrador, con un número
finito de columnas y un formato controlado. Los parámetros de comparación van con
`type(^valor, :integer)` o el tipo que corresponda.

## 4. Alcance de datos (R20)

**Decisión de diseño (aprobada 2026-09-25):** la Consulta SQL no tiene una
configuración de alcance por rol propia, como un catálogo. Para cada
columna de control que exponga el SQL se aplica la lista que el `Scope`
del usuario ya calcula, con la misma convención de filas `NULL` visibles
que usa `CatalogoGenerico`:

| Columna expuesta | Filtro |
|---|---|
| `branch_id` | `in ^scope.branches_permitidos` |
| `sales_unit_id` | `in ^scope.sales_units_permitidas` |
| `inventory_id` | `in ^scope.inventory_locations_permitidas` |

Sin sesión → cero filas (deny-by-default, como `CatalogoGenerico`). Si
no expone ninguna, no se acota y el tab Configuración muestra el aviso.

**Ajuste al implementar (2026-09-25): el administrador no se acota.**
Esas tres listas son asignaciones explícitas del usuario
(`Autenticacion.alcance_de_usuario/2`), así que un administrador sin
sucursales asignadas tendría listas vacías y no vería nada. En los
catálogos, `Permissions.alcance_tipo_efectivo/2` le da `:global`; aquí se
aplica el mismo criterio con `Permissions.administrador?/2`.

## 5. BC autorizados y dependencias de uso (R14-R18, R30)

- **Lista:** `bcs_autorizados` guarda nombres. El buscador ofrece
  catálogos tipo 1 (maestros y detalles) vía `MetaSchemaContext`.
- **"Qué campos lo usan" (R15):** una sola consulta JSONB sobre
  `meta_schema_detail` (`schema_context_properties->'diccionario'->>'consulta' = ^nombre`),
  agrupada por catálogo. La misma función alimenta R4, R17 y R30.
- **Quitar un BC (R17) o eliminar la Consulta SQL (R30):** si esa
  consulta regresa campos, se rechaza y se listan.

## 6. Diccionario en un campo referencia (R24-R28)

**Metadata del campo** (dentro del mismo `schema_context_properties`,
sin migración):

```json
"diccionario": {"consulta": "pty_sql_empleados_ventas", "descripcion": ["nombre", "numero"]}
```

Los filtros fijos y las dependencias de ese campo llevan una clave
opcional nueva, `"origen": "diccionario" | "destino"` (por defecto
`"destino"`, retrocompatible), para indicar sobre qué columnas aplican
(R27).

**Opciones del combo (R26)**, en `CatalogoGenerico.opciones_referencia/3`
cuando el campo tiene `diccionario`:

```elixir
from(v in "pty_sql_x")
|> alcance_por_columnas(scope)                   # §4
|> join destino solo si hay filtros con origen "destino" (on: d.id == v.id)
|> filtros con origen "diccionario" → sobre v; con origen "destino" → sobre d
|> distinct: v.id, select: {v.id, descripción concatenada " - "}, limit: 500
```

Todo en una sola consulta, dentro de `ConsultasSql.ejecutar/1`.

**Configuración (R24-R25), formulario "Filtros" de `BcMotorLive`:**
sección nueva "Filtrar por diccionario". Lista Consultas SQL tipo 4,
uso Diccionario, `schema_visible: false` y con el BC actual en
`bcs_autorizados`. Al elegir una: se eligen las columnas de descripción
y se verifica R25 con un anti-join con tiempo máximo:

```sql
SELECT count(*) FROM pty_sql_x v
WHERE NOT EXISTS (SELECT 1 FROM <destino> d WHERE d.id = v.id)
```

Si el resultado es mayor que 0, se rechaza.

**Validación al guardar un registro (R28):** se extiende
`MetaSchemaContext.validar_dependencias_referencia/2`, que ya corre en el
changeset de todo catálogo (mismo motivo que los filtros fijos: no
regenerar schemas). Solo si hay `get_change/2`: la misma consulta de
opciones más `where v.id == ^valor`, con `Repo.exists?`.

**Ajustes al implementar (2026-09-25):**
- **Sin alcance en esta validación:** el changeset no conoce la sesión
  del usuario, así que R28 valida contra el Diccionario, la cascada y los
  filtros fijos, pero no contra el alcance por columnas. El combo sí
  aplica el alcance. La cascada se resuelve con los valores del propio
  changeset; un padre sin valor no filtra.
- **Filtros sobre el destino:** se aplican como `v.id IN (subconsulta
  sobre el catálogo destino)` en vez de un join, para reusar
  `CatalogoGenerico.aplicar_filtros/2` tal cual.
- **`scope` nil en el combo** (llamadores internos sin sesión, como el
  grid editable) = sin alcance, mismo criterio que un catálogo.
- **Filtros fijos por origen:** `CatalogoGenerico.filtros_fijos/1` solo
  regresa los de origen "destino"; los de origen "diccionario" salen de
  `filtros_fijos_diccionario/1`. Las dependencias con origen "diccionario"
  llegan con la llave `"diccionario:<columna>"`
  (`separar_filtros_diccionario/1`).
- **Crear una SQL View registra su permiso `leer`:** SPEC-SYS-2209202601
  exige el permiso registrado incluso para el administrador (API y menú).

## 7. Pantallas y API (R1-R3, R19, R21-R23)

- **BC List:** botón **"+ SQL View"** con un modal: etiqueta,
  carpeta/slug con vista previa, uso. Crea el Header (tipo 4,
  `schema_visible: false` por defecto) y la fila de
  `meta_schema_consulta_sql` sin SQL todavía.
- **`ConsultaSqlEditorLive`** en `/sysadmin/bc-list/:nombre/consulta-sql`
  (mismo `live_session` y hook de autorización `{"sysadmin_bc", "editar"}`
  que `ConsultaEditorLive`, por R33). Tabs: **Configuración, Contrato y
  Permisos** (R23).
  - **Configuración:** `panel_encabezado` compartido + selector de uso;
    área de SQL en monoespaciado con "Validar y guardar"; tabla de

    BC, los campos que la usan).
  - **Contrato:** `GET /api/<nombre>`, paginación y formato `meta_campos`
    / `data` / `paginacion`, igual que el de la Consulta Ecto sin
    `totales`.
  - **Permisos:** embebe `CatalogoPermisosLive`. Donde hoy distingue
    `es_consulta` (tipo 3) se generaliza a "solo lectura" (tipos 3 y 4):
    acciones `~w(leer)`, sin configuración de alcance por rol.
- **Menú (R3):** `CatalogoLive` ya decide por `schema_context_type`; se
  agrega el tipo 4 → tabla paginada de solo lectura con las columnas del
  SQL, con alcance.
- **API:** `CatalogoController` ya delega el tipo 3 a
  `ConsultaController`; se agrega el tipo 4 → `ConsultaSqlController.index/2`,
  con la seguridad de API vigente (SPEC-SYS-2209202601).

## 8. Dependencias con catálogos (R29)

Postgres ya bloquea `DROP COLUMN`/`DROP TABLE` sobre algo que una vista
usa, pero con un error técnico. Antes de que
`CatalogoGenerador.eliminar_campo/4` o el borrado de un catálogo corran
su migración, se consulta qué vistas `pty_sql_*` dependen de esa tabla o
columna:

```sql
SELECT DISTINCT v.relname
FROM pg_depend d
JOIN pg_rewrite r ON r.oid = d.objid
JOIN pg_class v ON v.oid = r.ev_class
JOIN pg_class t ON t.oid = d.refobjid
WHERE t.relname = $1 AND ($2::int IS NULL OR d.refobjsubid = $2)
```

Si hay alguna, se rechaza con el mensaje "lo usa la Consulta SQL
«Etiqueta»".

## 9. Publicación (R31-R32)

- **Export/import:** `meta.export` agrega al `.meta.json` del header tipo
  4 un bloque `"consulta_sql"` con `uso`, `sql`, `columnas` y
  `bcs_autorizados`. `importar_contexto/1` crea o actualiza la fila, con
  el mismo criterio de sincronizar lo que cambió que se usa para el resto
  de la metadata.
- **La vista:** viaja por sus migraciones (`*pty_sql_x*.exs`). Siempre
  tienen un timestamp posterior a las tablas que usan, porque una vista
  no puede crearse antes que ellas, así que el orden en el destino es
  correcto.
- **Paquete (`calcular_paquete_publicacion/1`):**
  - para un tipo 4, las tablas de las que depende (misma consulta a
    `pg_depend` de §8) → sus catálogos entran al paquete;
  - para un catálogo con campos que usan un Diccionario, ese Diccionario
    entra al paquete.

## 10. Riesgos a verificar en `03.tasks.md`

- **`CREATE TEMP VIEW` dentro de la validación:** confirmar contra
  Postgres 17 real que la transacción de validación funciona como se
  describe, y que una transacción `READ ONLY` sí permite leer la vista.
- **Funciones con efectos:** la validación no ejecuta el SQL (crear una
  vista y leer sus columnas no corre la consulta), y toda ejecución real,
  incluida la vista previa, pasa por `READ ONLY` (§3). Hay que verificar
  que una función que intenta escribir falla dentro de esa transacción.
- **Renombrar catálogos:** una vista que usa un nombre físico que cambia
  se rompe. Postgres también lo bloquea; el mensaje de §8 lo cubre.
