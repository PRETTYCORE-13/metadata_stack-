# SPEC-ARQ-2209202602 — Propagación de Artefactos de Negocio (Guía de uso)

**Documento:** Guía de uso · Documenta comandos ya existentes y
verificados en el código (`MetaPublicador`, `MetaTepache`,
`motor.propagar_extension` de `SPEC-ARQ-1809202603`) — no hay nada
nuevo que implementar, ver `01.requirements.md`/`02.design.md`.

## 1. Objetivo

Saber qué hacer con un catálogo `pty_*` (ej. `pty_motos`) construido
localmente en tres momentos distintos: mientras todavía no se publicó
en ningún lado, cuando ya está en `unstable` y se quiere llevar a
`testing`/`stable`, y si la máquina donde se construyó se pierde.

## 2. ¿Quién utiliza esta funcionalidad?

Cualquier desarrollador de ADN con el repo clonado y `gh` (GitHub CLI)
autenticado — mismo requisito que ya usa `mix motor.publicar`.

## 3. Conceptos que debo conocer

- Un artefacto de negocio **no tiene canal `testing`/`stable` propio**.
  Viaja empaquetado dentro de la actualización completa del sistema
  (la "extensión"/CORE de `SPEC-ARQ-1809202603`), junto con todos los
  demás catálogos ya publicados — nunca aislado.
- **Publicar** (`mix motor.publicar`) es lo único que deja un catálogo
  respaldado en GitHub — un release `bc-<catalogo>` que se actualiza
  cada vez que se vuelve a publicar (solo queda la última versión, sin
  historial).
- **Tepache** (`mix motor.tepache`) es el respaldo/preview manual para
  cuando todavía NO se quiere publicar nada — nunca toca producción.

## 4. Guía paso a paso

### 4.1 Publicar un catálogo por primera vez (y dejarlo respaldado)

```
mix motor.publicar --sistema=unstable pty_motos
```

`--sistema=` es obligatorio — `unstable` para probar, o el nombre de
un cliente real de `priv/sistemas.json`. Nunca `testing`/`stable`
(esos dos solo reciben por propagación, ver 4.3). Este comando ya deja
`pty_motos` respaldado en GitHub (release `bc-pty_motos`) antes de
desplegar nada — no hace falta ningún paso extra para eso.

### 4.2 Respaldar un catálogo SIN publicarlo todavía

Si `pty_motos` todavía se está construyendo y no quieres desplegarlo a
ningún lado, pero sí quieres poder recuperarlo si se pierde la
máquina:

```
mix motor.tepache pty_motos --descripcion "trabajo en progreso, sin terminar"
```

Confirma un tag `TEPACHE-NNNNNN`. Para recuperarlo en cualquier
máquina (la misma u otra):

```
mix motor.tepache.importar TEPACHE-NNNNNN
```

### 4.3 Llevar un catálogo ya publicado de `unstable` a `testing`/`stable`

No hay un comando "propagar solo este catálogo" — se propaga la
actualización completa del sistema, que ya lo incluye (ver
`02.design.md` §2-3):

```
mix motor.estado_extension <ambiente>
mix motor.propagar_extension <ambiente> unstable testing
mix motor.propagar_extension <ambiente> testing stable
```

**Importante**: si acabas de correr `motor.publicar --sistema=unstable`,
espera a que pase al menos una actualización normal del sistema (un
push cualquiera a `main` — no tiene que ser tuyo ni relacionado a
`pty_motos`) antes de propagar. El deploy directo de `motor.publicar`
usa una imagen con un tag distinto al que `motor.propagar_extension`
sabe mover; la imagen "propagable" es la que arma la actualización
normal, que ya incluye tu catálogo porque quedó respaldado en el paso
4.1. Confirma con `mix motor.estado_extension <ambiente>` que
`unstable` ya corre esa imagen nueva antes de propagar.

### 4.4 Recuperar un catálogo ya publicado en una máquina nueva

Si se perdió la máquina donde se construyó `pty_motos`, pero ya se
había publicado al menos una vez (paso 4.1 en algún momento):

```
mix motor.tepache.importar bc-pty_motos
```

Funciona igual que importar un tepache real — el nombre del tag no
importa, `motor.tepache.importar` baja el único bundle `.tar.gz` del
release que se le pida (ver `02.design.md` §5).

## 5. Ejemplos prácticos

### Ejemplo: publicar y confirmar el respaldo

```
mix motor.publicar --sistema=unstable pty_motos
```
```
== validando pty_motos ==
  sin problemas
...
== guardando bundle en GitHub Releases (bc-<catálogo>) ==
  bc-pty_motos
== disparando BC Deploy en GitHub Actions para "unstable" ==
```

Confirmar que el release quedó: `gh release view bc-pty_motos`.

### Ejemplo: recuperar tras perder la laptop

```
git clone <repo>
cd metadata_stack-
mix deps.get
mix ecto.create
mix motor.tepache.importar bc-pty_motos
```

Resultado esperado: Postgres local termina con `pty_motos` migrado,
metadata + autómata + permisos importados — listo para seguir
editándolo local.

## 6. Casos comunes

- **"Publiqué a `unstable` pero `motor.propagar_extension` no ve mi
  catálogo todavía"** — normal, ver 4.3: falta que pase una
  actualización normal del sistema. `mix motor.estado_extension` te
  dice qué hash corre en `unstable` ahora mismo.
- **"¿Por qué al propagar se mueven también otros 999 catálogos que no
  toqué?"** — es por diseño, no hay forma de propagar uno solo (R4,
  `02.design.md` §3). El control está en qué publicas a `unstable`.
- **"Publiqué dos veces el mismo catálogo, ¿tengo las dos versiones
  guardadas?"** — no, el release `bc-<catalogo>` solo conserva la
  última (R2) — sin historial navegable de publicaciones anteriores.
