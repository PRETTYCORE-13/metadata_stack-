# SPEC-ARQ-2209202602 — Propagación de Artefactos de Negocio

**Documento:** Design · Documentación retroactiva del mecanismo
existente (ver `01.requirements.md` §1) — no hay decisión técnica
nueva que tomar acá, solo el CÓMO real de lo que R1-R7 describen desde
el punto de vista de quien usa el sistema.

## 1. Componentes involucrados

| Componente | Rol |
|---|---|
| `MetadataApp.MetaPublicador` (`lib/metadata_app/meta_publicador.ex`) | Arma el `.tar.gz` de un catálogo (+ dependencias), lo sube a `bc-<catalogo>` en GitHub Releases, dispara `bc-deploy.yml`. |
| `MetadataApp.MetaTepache` (`lib/metadata_app/meta_tepache.ex`) | Mismo empaquetado que `MetaPublicador`, pero publica a un release `TEPACHE-NNNNNN` propio y nunca dispara un deploy. Del lado receptor: baja, migra e importa en Postgres local. |
| `.github/workflows/bc-deploy.yml` | Deploy directo de UN publish (`motor.publicar`) a un sistema puntual (`unstable` o un cliente). Imagen con tag `bc-<catalogo>-<run_number>`. |
| `.github/workflows/ci.yml` | Build normal, disparado por cualquier push a `main`. Imagen con tag = hash completo del commit (`github.sha`). Este es el único tag que `mix motor.propagar_extension` sabe mover. |
| `mix motor.propagar_extension` | Mueve, sin reconstruir, la imagen (por hash de commit) de `unstable→testing` o `testing→stable` (`SPEC-ARQ-1809202603`). |

## 2. Flujo completo: de `pty_motos` local a `stable`

```
[1] Desarrollador ADN construye pty_motos localmente (BPB)
        │
        │  mix motor.publicar --sistema=unstable pty_motos
        ▼
[2] MetaPublicador.armar_bundle/1
        → tar.gz: schema + migraciones + meta.json + motor.json +
          plantillas.json + reglas/
        │
        ▼
[3] MetaPublicador.persistir_bundle/2
        → gh release upload bc-pty_motos bundle.tar.gz --clobber
        → ESTE ES EL RESPALDO. A partir de acá, pty_motos sobrevive
          aunque la máquina de origen desaparezca (R1/R2).
        │
        ▼
[4] MetaPublicador.disparar_deploy/3
        → dispara bc-deploy.yml con sistema=unstable
        → bc-deploy.yml RESTAURA TODOS los bc-* (no solo pty_motos,
          ver R3) antes de compilar, arma imagen
          ghcr.io/.../metadata_stack:bc-pty_motos-<run>, la despliega
          a unstable.
        → unstable YA corre pty_motos. Pero esta imagen NO tiene tag
          de hash de commit — motor.propagar_extension no la puede
          referenciar todavía.
        │
        │  (en paralelo o después: CUALQUIER push normal a main)
        ▼
[5] ci.yml build-image
        → restaura TODOS los bc-* (incluye pty_motos, ya en GitHub
          desde el paso 3) antes de compilar
        → imagen ghcr.io/.../metadata_stack:<github.sha>
        → deploy job actualiza unstable con ESTA imagen
        │
        │  mix motor.estado_extension <ambiente>   (confirmar hash)
        │  mix motor.propagar_extension <ambiente> unstable testing
        ▼
[6] testing corre exactamente esa imagen — pty_motos incluido, junto
    con TODOS los demás artefactos ya publicados hasta ese momento
    (R4 — no hay selección posible).
        │
        │  mix motor.propagar_extension <ambiente> testing stable
        ▼
[7] stable corre la misma imagen.
```

## 3. Por qué "todo o nada" es la decisión ya tomada (no un descuido)

El comentario de `MetaPublicador.persistir_bundle/2` lo dice explícito:
> "el Release mismo ES el manifest de 'este catálogo debe quedar
> siempre vivo': no hay ningún archivo de texto aparte que mantener
> sincronizado ni commitear."

Cada release `bc-<catalogo>` es la única fuente de verdad de "este
artefacto debe estar en toda imagen futura". `ci.yml`/`bc-deploy.yml`
no seleccionan cuáles restaurar — restauran todos, siempre. Esto
garantiza que la imagen que se valida en `unstable` es *exactamente*
(byte por byte, nunca reconstruida a mitad de camino) la que llega a
`testing` y después a `stable` — la alternativa (seleccionar
artefactos por ambiente) abriría la puerta a que un ambiente tenga una
combinación de catálogos que nunca se probó junta en ningún lado.

El costo, ya aceptado: con 1000 artefactos publicados, promover
`unstable→testing` los mueve a todos. El control real está en qué se
publica a `unstable` en primer lugar (R1), no en el paso de
propagación (R4).

## 4. El caso sin cubrir: antes del primer publish

R5 documenta el hueco real: mientras `pty_motos` solo existe en la
máquina local (nunca se corrió `motor.publicar`), no hay ningún
`bc-pty_motos` en GitHub — nada que restaurar, nada que recuperar.

`mix motor.tepache pty_motos` (R6) cubre esto sin necesitar un publish
real: mismo empaquetado (`MetaPublicador.armar_bundle/1`, reusado
directo por `MetaTepache.exportar/2`), pero a un release
`TEPACHE-NNNNNN` que nunca dispara ningún deploy ni entra al
restaurado de `ci.yml`/`bc-deploy.yml` (esos dos filtran
específicamente por prefijo `bc-`, ver §2 paso [5] — un `TEPACHE-*`
nunca se mezcla con una imagen real).

## 5. Recuperación en máquina nueva

`MetaTepache.descargar/1` no distingue el prefijo del tag — baja el
único asset `*.tar.gz` del release que se le pida, sea `TEPACHE-000042`
o `bc-pty_motos`. Por eso `mix motor.tepache.importar bc-pty_motos`
(R7) funciona igual que importar un tepache real: baja el bundle,
migra el Postgres local, e importa metadata + autómata + permisos —
sin que la máquina que se perdió haya respaldado nada por su cuenta.
