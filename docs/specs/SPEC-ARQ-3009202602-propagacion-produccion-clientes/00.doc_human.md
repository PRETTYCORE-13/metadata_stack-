# SPEC-ARQ-3009202602 — Propagación a Producción de Clientes (por oleadas)

**Documento:** Explicación general · **Fase:** 🔲 borrador, en revisión.

## ¿Qué problema resuelve?

Hoy, cuando una mejora ya pasó por `unstable` y `testing` y quedó lista
en `stable`, llevarla a cada cliente real (como `crm` o el gimnasio) se
hace **uno por uno**, a mano, por terminal — sesión de esta misma
conversación tras conversación: correr `mix
motor.propagar_extension_a_sistema` para "crm", esperar, revisar que no
falló, y repetir para el siguiente cliente. Con 2 o 3 clientes no pesa.
Con 10, 30, 100, se vuelve lento, repetitivo, y fácil de olvidar un
cliente o de hacerlo en el orden equivocado.

Esta spec agrega la capacidad de actualizar **varios clientes a la
vez**, de forma controlada: primero un grupo chico de clientes
"piloto" (los que sirven de prueba antes de arriesgar a todos), y
recién si esos salen bien, el resto. Si algo falla en el camino, se
frena antes de tocar a los que faltan — nunca sigue de largo
"esperando que no pase nada".

## ¿Cómo funciona, a grandes rasgos?

Es una extensión de lo que ya existe (`SPEC-ARQ-1809202603`), no un
mecanismo nuevo desde cero: el origen de todo siempre es `stable` — lo
mismo que hoy aplica un cliente a la vez. Lo nuevo es poder elegir
**varios clientes** en una sola operación, en vez de repetir el mismo
comando N veces.

- Se elige qué clientes actualizar: uno, varios, o "todos los que
  todavía no tienen la versión de `stable`".
- Los clientes marcados como **piloto** se actualizan primero, solos.
  Recién cuando todos esos terminan bien, empieza el resto — nunca al
  mismo tiempo.
- Hace falta escribir un motivo (o número de ticket) y que una
  **segunda persona del equipo**, distinta de quien lo pide, lo
  apruebe — mismo criterio de "cuatro ojos" que ya se usa para dar de
  baja un sistema completo.
- Si un cliente falla, por defecto se detiene ahí: los que ya
  terminaron quedan como están, el que falló se revierte a como
  estaba, y los que faltaban no se tocan hasta que alguien decida qué
  hacer.
- Queda un registro de qué cliente terminó bien, cuál falló, y quién
  aprobó cada tanda — para poder revisarlo después sin tener que
  reconstruir la historia de memoria.

## ¿Qué NO cambia?

El mecanismo para actualizar **un solo cliente** sigue exactamente
igual (`mix motor.propagar_extension_a_sistema`, `SPEC-ARQ-1809202603`)
— esta spec no lo reemplaza, lo envuelve para poder pedirlo para varios
clientes de una vez. Tampoco cambia cómo se mueve una versión entre
`unstable`/`testing`/`stable` — eso sigue siendo responsabilidad
exclusiva de esa misma spec.

## ¿Quién usa esto y cuándo?

El equipo de plataforma, el día que haya más de un puñado de clientes
reales y actualizarlos uno por uno deje de ser práctico. Con la
cantidad de clientes de hoy, el mecanismo actual (uno a la vez) sigue
siendo válido — esta spec queda lista para cuando haga falta, no
reemplaza el camino actual de un día para otro.

## Lo que esta spec NO hace

No decide sola qué cliente es "piloto" — eso lo marca un administrador
de antemano. No manda correos ni WhatsApp (hoy el sistema solo tiene
notificaciones dentro de la propia aplicación, campanita del panel) —
si en el futuro hace falta avisar por otro medio, es una spec aparte.
No agrega una forma de "fijar" a un cliente en una versión vieja a
propósito — queda como pendiente a decidir (§ de `01.requirements.md`).
