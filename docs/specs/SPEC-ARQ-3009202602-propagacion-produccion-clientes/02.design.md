# SPEC-ARQ-3009202602 — Propagación a Producción de Clientes (por oleadas)

**Documento:** Design · **Fase:** 🔲 borrador, pendiente de construir.

Extiende `SPEC-ARQ-1809202603-propagacion-extensiones`
(`MetadataApp.MotorAlta`, `.github/workflows/actualizar-sistema.yml`,
`PropagacionLive`) — nada de esto reconstruye un despliegue nuevo, todo
envuelve el mecanismo de un-solo-cliente que ya existe.

**Reescrito (30-09-2026)** después de recibir un prototipo clicable
completo del equipo (HTML/JS, sin backend real) que resuelve mejor dos
problemas que la primera versión de este documento intentaba resolver
con código propio — ver `01.requirements.md` §1.1 para el razonamiento
completo. Los cambios de fondo:

- La aprobación de un segundo administrador (R9-R10) se resuelve con
  una función NATIVA de GitHub Actions (**environment protection
  rules**), no con una tabla ni un comando `aprobar` propios.
- El registro (R11-R12) es un archivo `.jsonl` de solo-agregar, no una
  tabla Ecto — ya no hace falta ninguna migración de base de datos
  para esta spec completa.

**Ajustado (08-10-2026)** tras revisar el diseño contra el código y el
servidor reales, antes de construir:

- Se pasa y se compara siempre la **imagen completa**
  (`ghcr.io/…/metadata_stack:<etiqueta>`), igual que
  `actualizar-sistema.yml`. Antes `disparar_lote/3` mandaba como "tag" lo
  que devuelve `MotorAlta.imagen_actual/2` (que ya es la imagen
  completa) y el workflow le volvía a anteponer el registro.
- `stable` con `:latest` bloquea el lote (R3a).
- El servidor no tiene `jq`: las listas de clientes viajan separadas
  por comas.
- El registro vive en `/home/elixir/metadata-propagaciones/` (R11) y la
  línea viaja en base64 (R11a).
- `scripts/desplegar_sistema.sh` viaja al servidor en cada run (§5);
  antes el diseño lo daba por "ya presente" en `/opt/metadata/`.
- Los clientes de una oleada van uno por uno (R6) y el regreso
  automático es solo de imagen (R7a).

## 1. Identidad de quién dispara (más simple que la versión anterior)

La versión anterior de este documento proponía leer `git config
user.name/email`. El prototipo usa algo mejor, ya presente en el flujo
real: **`gh api user`** — la identidad de GitHub con la que `gh` ya
está autenticado en esa máquina (la misma que GitHub usa para decidir
quién disparó el run, y por lo tanto la misma que GitHub compara contra
los revisores al aplicar R10).

```elixir
def identidad_actual do
  case System.cmd("gh", ["api", "user", "--jq", ".login"]) do
    {login, 0} -> {:ok, String.trim(login)}
    {salida, _} -> {:error, "no se pudo resolver la identidad de gh: #{salida}"}
  end
end
```

Se usa solo para mostrarla en pantalla ("Se disparará como @...", igual
que el prototipo) y para escribirla en la línea del registro (§4) — la
comparación real de "quién aprueba no puede ser quien solicitó" la hace
GitHub (R10), esta app no la reimplementa.

## 4. Registro: `propagaciones.jsonl` (R11-R12)

Un archivo en el servidor (mismo host que ya aloja `/home/elixir/backups/`
de `mix motor.baja`), **solo-agregar** — nunca se reescribe ni se borra
una línea. Una línea JSON por CADA intento de disparo (canal o lote),
independientemente de si termina bloqueado, aprobado, o corre:

Ruta: `/home/elixir/metadata-propagaciones/propagaciones.jsonl` (R11).

```json
{"ts":"2026-09-30T20:10:12Z","tipo":"lote","destino":"clientes","imagen":"ghcr.io/prettycore-13/metadata_stack:e41c8b2f6a...","disparado_por":"Urixsg","motivo":"REL-209","clientes":{"piloto":["crm"],"resto":["ennova","abarrotes-bajio","lacteos-sureste"]}}
```

Se escribe **antes** de disparar el `gh workflow run` (registra la
intención, no el resultado — el resultado final vive en el run de
GitHub, R12). Escritura vía SSH desde donde ya corre `MotorAlta` (mismo
canal que usa `mix motor.baja` para sus respaldos). La línea viaja en
base64 (R11a): el alfabeto de base64 no tiene comillas, `$` ni
espacios, así que el motivo nunca se interpreta como shell:

```elixir
@registro "/home/elixir/metadata-propagaciones/propagaciones.jsonl"

def registrar_intento(ambiente, linea_map) do
  b64 = Base.encode64(Jason.encode!(linea_map) <> "\n")

  comando =
    "mkdir -p #{Path.dirname(@registro)} && " <>
      "echo #{b64} | base64 -d >> #{@registro}"

  MetadataApp.Ssh.ejecutar(ambiente, comando)
end
```

La URL del run no va en la línea: la línea se escribe antes de
disparar, cuando el run todavía no existe. La URL que imprime `gh
workflow run` se muestra en pantalla/terminal (§6.1, §6.2), y el run
se encuentra igual en la pestaña "Actions" por fecha y nombre
(`lote → clientes (...)`).

La pantalla/CLI (§6-§7) lo LEE para pintar el historial (parsear cada
línea con `Jason.decode!/1`, más reciente primero) — nunca hace falta
una base de datos para filtrar/ordenar dado el volumen esperado (bajo:
como mucho unas pocas propagaciones a producción por semana).

`listar_intentos/1` (agregada 08-10-2026, tarea C2) lee el archivo
completo por SSH (`cat`; si todavía no existe, lista vacía, no error),
decodifica línea por línea y **salta en silencio una línea dañada** —
una sola línea mala nunca rompe el historial completo. Devuelve
`{:ok, [mapa]}` con el más reciente primero, o `{:error, mensaje}` si
no se pudo conectar.

Para probarlas sin servidor, las dos reciben la función de SSH como
último argumento (default `&MetadataApp.Ssh.ejecutar/2`), mismo
criterio de dependencias inyectables que `MotorAlta.Estado`. Lo mismo
`identidad_actual/1` (§1) con la llamada a `gh`.

## 5. Nuevo workflow: `.github/workflows/actualizar-lote.yml`

Recibe la lista completa en UN solo `workflow_dispatch`, corre la
oleada completa DENTRO del mismo run (a diferencia del diseño anterior
de este documento, que hacía que Elixir disparara N runs sueltos) —
más simple de seguir en la pestaña "Actions" (un run = un lote
completo, no N runs sueltos que hay que correlacionar a mano).

```yaml
name: Actualizar lote (clientes)
on:
  workflow_dispatch:
    inputs:
      imagen: { required: true, description: "Imagen completa que corre en stable (etiqueta fija, nunca :latest)" }
      pilotos: { required: false, default: "", description: "Clientes piloto, separados por comas" }
      resto: { required: false, default: "", description: "Resto de clientes, separados por comas" }
      motivo: { required: true, description: "Motivo o ticket" }

run-name: "lote → clientes (${{ inputs.imagen }})"

jobs:
  lote:
    runs-on: ubuntu-latest
    environment: clientes   # <- R9: pide aprobación de un revisor distinto al que disparó
    steps:
      - uses: actions/checkout@v4

      # El script vive en el repo; viaja al servidor en base64 dentro del
      # mismo ssh-action (sin agregar una acción nueva de copia).
      - name: Empaquetar desplegar_sistema.sh
        id: script
        run: echo "b64=$(base64 -w0 scripts/desplegar_sistema.sh)" >> "$GITHUB_OUTPUT"

      - name: Aplicar por oleadas (piloto primero, uno por uno, detener si falla)
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            set -e
            IMAGEN="${{ inputs.imagen }}"
            PILOTOS="${{ inputs.pilotos }}"
            RESTO="${{ inputs.resto }}"

            # R3a: etiqueta fija, y exactamente la imagen de stable (mismo
            # gate que actualizar-sistema.yml para un solo cliente).
            case "$IMAGEN" in *:latest) echo "Rechazado: $IMAGEN no tiene etiqueta fija."; exit 1;; esac
            IMAGEN_STABLE=$(sudo k3s kubectl get deployment/metadata-stable -n metadata-stack -o jsonpath='{.spec.template.spec.containers[0].image}')
            [ "$IMAGEN" = "$IMAGEN_STABLE" ] || { echo "Rechazado: $IMAGEN no es la imagen de stable ($IMAGEN_STABLE)."; exit 1; }

            # Nombres de cliente: solo minúsculas, dígitos y guiones (son
            # nombres de deployment; nunca texto libre dentro del shell).
            for S in $(echo "$PILOTOS,$RESTO" | tr ',' ' '); do
              case "$S" in *[!a-z0-9-]*) echo "Rechazado: nombre de cliente inválido: $S"; exit 1;; esac
            done

            mkdir -p ~/metadata-scripts
            echo "${{ steps.script.outputs.b64 }}" | base64 -d > ~/metadata-scripts/desplegar_sistema.sh

            aplicar_uno() {
              SISTEMA="$1"
              IMAGEN_ANTERIOR=$(sudo k3s kubectl get deployment/metadata-$SISTEMA -n metadata-stack -o jsonpath='{.spec.template.spec.containers[0].image}')
              bash ~/metadata-scripts/desplegar_sistema.sh "$SISTEMA" "$IMAGEN" || {
                echo "FALLÓ $SISTEMA -- regresando a $IMAGEN_ANTERIOR (solo imagen: revisar su base a mano si ya migró, R7a)"
                sudo k3s kubectl set image "deployment/metadata-$SISTEMA" "app=$IMAGEN_ANTERIOR" -n metadata-stack
                return 1
              }
              echo "OK $SISTEMA"
            }

            DETENIDO=0
            for SISTEMA in $(echo "$PILOTOS" | tr ',' ' ') $(echo "$RESTO" | tr ',' ' '); do
              if [ "$DETENIDO" = "1" ]; then echo "OMITIDO $SISTEMA"; continue; fi
              aplicar_uno "$SISTEMA" || DETENIDO=1
            done
            [ "$DETENIDO" = "1" ] && exit 1 || exit 0
```

Pilotos y resto van en una sola vuelta, pilotos primero (R5): como los
clientes van uno por uno (R6) y una falla detiene todo lo que sigue
(R7), recorrer `pilotos` y después `resto` en el mismo ciclo ya
garantiza que el resto nunca empieza si un piloto falló.

**DRY con `actualizar-sistema.yml` (nota de implementación, Grupo del
`03.tasks.md`)**: el cuerpo real de "aplicar una imagen a un sistema"
(`kubectl set image` + `rollout restart` + `rollout status` + ubicar el
pod + `kubectl exec ... /app/bin/setup`, visto tal cual en
`actualizar-sistema.yml` ya existente) se extrae a
`scripts/desplegar_sistema.sh` — un archivo nuevo en el repo que AMBOS
workflows mandan al servidor en cada run (base64 dentro del mismo
`appleboy/ssh-action`, como arriba, a `~/metadata-scripts/`) y luego
invocan con `<sistema> <imagen>` como argumentos. Así el servidor
siempre corre la versión del commit del run, nunca una copia vieja
que alguien dejó ahí. Evita mantener el mismo bash pegado en dos YAMLs
distintos. `actualizar-sistema.yml` (un solo cliente, ya existente)
pasa a mandar y llamar este mismo script en vez de tener el bash
inline — cambio chico, mismo comportamiento exacto.

## 6. Disparo desde Elixir (contexto + LiveView + mix task)

`MetadataApp.PropagacionProduccion` (contexto Elixir puro):

`MotorAlta.imagen_actual/2` devuelve la imagen COMPLETA
(`ghcr.io/…/metadata_stack:<etiqueta>`, verificado en el código). Todo
este contexto trabaja con la imagen completa, nunca con la etiqueta
sola, y la comparación "ya está al día" es segura porque R3a garantiza
que la imagen de `stable` tiene etiqueta fija.

```elixir
def imagen_stable(ambiente) do
  case MotorAlta.imagen_actual(ambiente, "stable") do
    {:ok, imagen} ->
      if String.ends_with?(imagen, ":latest"),
        do: {:error, "stable corre #{imagen}: propaga antes a stable una imagen por hash (--commit=<hash>)."},
        else: {:ok, imagen}

    {:error, _} = error ->
      error
  end
end

def elegibles(ambiente) do
  with {:ok, imagen_stable} <- imagen_stable(ambiente) do
    lista =
      MotorAlta.leer_sistemas()
      |> Enum.filter(fn {_nombre, datos} -> Map.get(datos, "activo", true) end)
      |> Enum.map(fn {nombre, datos} ->
        cond do
          fijada = Map.get(datos, "version_fijada") ->
            {nombre, {:no_elegible, :version_fijada, fijada}}

          true ->
            case MotorAlta.imagen_actual(ambiente, nombre) do
              {:ok, ^imagen_stable} -> {nombre, {:no_elegible, :al_dia, imagen_stable}}
              {:ok, otra} -> {nombre, {:elegible, otra, Map.get(datos, "piloto", false)}}
              {:error, motivo} -> {nombre, {:error, motivo}}
            end
        end
      end)

    {:ok, imagen_stable, lista}
  end
end

def disparar_lote(ambiente, sistemas_elegidos, motivo) when motivo not in [nil, ""] do
  with {:ok, imagen_stable, lista} <- elegibles(ambiente),
       {:ok, quien} <- identidad_actual() do
    {pilotos, resto} =
      lista
      |> Enum.filter(fn {n, estado} -> n in sistemas_elegidos and match?({:elegible, _, _}, estado) end)
      |> Enum.split_with(fn {_, {:elegible, _, piloto?}} -> piloto? end)

    pilotos = Enum.map(pilotos, &elem(&1, 0))
    resto = Enum.map(resto, &elem(&1, 0))

    registrar_intento(ambiente, %{
      ts: DateTime.utc_now(), tipo: "lote", destino: "clientes", imagen: imagen_stable,
      disparado_por: quien, motivo: motivo, clientes: %{piloto: pilotos, resto: resto}
    })

    System.cmd("gh", [
      "workflow", "run", "actualizar-lote.yml",
      "-f", "imagen=#{imagen_stable}",
      "-f", "pilotos=#{Enum.join(pilotos, ",")}",
      "-f", "resto=#{Enum.join(resto, ",")}",
      "-f", "motivo=#{motivo}"
    ])
  end
end
```

`System.cmd/3` pasa cada argumento sin shell de por medio, así que el
motivo aquí no corre riesgo; el riesgo de R11a es solo en el comando
SSH del registro (§4).

Igual que el mecanismo de canal (`SPEC-ARQ-1809202603`): la
confirmación escrita (R10a, un campo de texto por cliente seleccionado)
se valida ANTES de llegar a esta función, en el `handle_event` de la
LiveView o en el mix task — `disparar_lote/3` asume que ya se validó,
mismo criterio que el resto de `MotorAlta`.

### 6.1 `PropagacionLive` (extensión de la pantalla existente)

### 6.2 Mix task equivalente

```
mix motor.propagar_extension_a_produccion <ambiente> --motivo="<texto>" (--clientes=a,b,c | --todos)
```

Pide la confirmación por cliente de forma interactiva
(`Mix.shell().prompt/1`, uno por uno, mismo criterio que la
confirmación de `mix motor.baja`), y si todas coinciden, llama
`disparar_lote/3` (§6). Igual que el resto de la familia `motor.*`:
imprime la URL del run y recuerda que falta la aprobación de un
segundo administrador en GitHub — el comando termina ahí, no espera a
que el run avance ni se aprueble.
