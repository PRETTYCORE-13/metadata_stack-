# SPEC-ARQ-3009202602 — Propagación a Producción de Clientes (por oleadas)

**Documento:** Requirements · **Fase:** 🔲 borrador, en revisión.

## 1. Propósito y alcance

Punto de partida de esta spec: un documento externo ("spec de
Propagación de ambientes", pegado por el usuario el 30-09-2026) que
propone un mecanismo genérico de propagación con aprobación, oleadas,
Oban, y tablas de auditoría propias. Esta spec **transforma** esa
propuesta para que encaje con lo que ya existe y ya está aprobado en
este repo (`SPEC-ARQ-1809202603-propagacion-extensiones` y
`SPEC-ARQ-0309202601-alta-sistema-nuevo`) — adoptando las ideas que
resuelven un problema real todavía no cubierto, y rechazando
explícitamente las que duplican o contradicen decisiones ya tomadas.
La tabla de la §1.1 resume qué se adopta y qué no, y por qué.

Esta spec **extiende** `SPEC-ARQ-1809202603` — no la reemplaza ni la
reabre. El mecanismo de un-solo-cliente
(`mix motor.propagar_extension_a_sistema <ambiente> <sistema>
<imagen>`) sigue siendo la base: todo lo de acá lo invoca N veces, en
oleadas, nunca lo reimplementa.

### 1.1 Qué se adopta del documento pegado, y qué no

| Oleadas piloto → resto, detener si falla (P8-P9) | **Se adopta** | Mismo problema real, es la parte central del pedido. |
| Motivo/ticket + aprobación de un segundo admin (P5) | **Se adopta**, pero NO con un mecanismo propio — usando las **"environment protection rules" nativas de GitHub Actions** (revisores obligatorios sobre un ambiente `clientes`), idea tomada del prototipo clicable que el equipo compartió (30-09-2026) | GitHub ya bloquea el run hasta que alguien lo apruebe desde su propia web, y **ya impide nativamente que quien disparó el run apruebe su propio run** — exactamente lo que pedía R9/R10 original de este documento, sin construir nada nuevo. Mejor que mi primera propuesta (un comando `aprobar` con su propia tabla). |
| Confirmación escrita (R5/P6) | **Se adopta, ampliada**: en vez de escribir una sola palabra fija (`producción`), se escribe el nombre EXACTO de cada cliente seleccionado (uno por campo, en cualquier orden) — idea tomada del mismo prototipo | Con un solo cliente, escribir "producción" alcanza. Con varios, protege además contra seleccionar el conjunto equivocado de clientes, no solo contra confirmar sin querer. |
| Bloqueo silencioso si la confirmación no coincide (R6) | **Se adopta el CONCEPTO** (no bloquear con aviso, solo no ejecutar) | El valor real es "no reintentar a ciegas ni dar pistas a quien escribe mal a propósito", no una animación puntual. |
| Rollback por cliente al fallar (P9) | **Se adopta**, reusando `digest_anterior`/imagen previa, mismo mecanismo que ya usa el rollback de `SPEC-ARQ-1809202603` R10 | Ya existe, no hay que reinventarlo. |

Con la aprobación resuelta por GitHub y la orquestación de oleadas viviendo DENTRO de un único workflow de GitHub Actions (ver `02.design.md`), no hace falta ningún proceso Elixir de larga duración que sobreviva un reinicio — ese es justamente el problema que Oban resolvía, y acá ya no existe. |

## 2. Selección de clientes (P1-P4 del documento pegado)

R1. EL SISTEMA DEBE permitir elegir, para una propagación a
producción, uno, varios, o todos los clientes **elegibles** de
`priv/sistemas.json` — nunca ninguno por defecto.

R2. EL SISTEMA DEBE considerar "elegible" a un cliente que cumple TODAS
estas condiciones: está registrado y activo, responde al consultar su
imagen actual (mismo mecanismo que `MotorAlta.Estado.consultar_todo/0`
de `SPEC-ARQ-1809202603` §2), su imagen actual es DISTINTA a la que
corre hoy en `stable`, y NO tiene una `version_fijada` configurada
(R4b). "Seleccionar todos" nunca incluye un cliente no elegible.

R2a. Un cliente no elegible (ya al día, o con versión fijada) SÍ puede
marcarse a mano en la selección (nunca se oculta de la lista completa)
— pero el sistema lo omite igual en la ejecución, mostrando el motivo
exacto ("ya tiene esta versión" / "versión fijada") — nunca un
`{:error}` que frene la selección del resto de clientes elegidos.

R3. CUANDO se elige "todos", EL SISTEMA DEBE congelar esa lista de
clientes elegibles en el momento de la solicitud — un cliente dado de
alta después (aunque sea elegible en ese momento) no entra en esa
misma propagación, ni aunque todavía no haya terminado.

## 3. Oleadas (P8-P9 del documento pegado)

R4. EL SISTEMA DEBE marcar cada cliente de `priv/sistemas.json` con un
indicador `piloto` (booleano, default `false`) — dato nuevo en ese
mismo archivo, no una tabla aparte, mismo criterio que el resto de los
datos de un cliente ahí.

R5. CUANDO se dispara una propagación a producción con varios clientes
elegidos, EL SISTEMA DEBE actualizar primero a TODOS los marcados
`piloto` dentro de esa selección, y recién cuando todos esos terminan
(bien o mal) seguir con el resto — nunca en paralelo entre oleadas. Si
ninguno de los elegidos es piloto, la "oleada 1" quedará vacía y se
pasa directo a la oleada 2 sin pedir nada extra.

R6. DENTRO de una misma oleada, EL SISTEMA DEBE actualizar los
clientes de a `N` en paralelo (configurable, default 2) — mismo
patrón de paralelismo controlado que ya usa `Task.async_stream/3` en
`MotorAlta.Estado.consultar_todo/0`.

R7. CUANDO un cliente falla su actualización (el paso de migración o
el `rollout status` no termina bien) y la opción "detener si falla"
está activa (default: activa), EL SISTEMA DEBE: revertir ESE cliente a
su imagen anterior (mismo mecanismo de rollback de R10 de
`SPEC-ARQ-1809202603`), NO iniciar los clientes todavía pendientes de
esa oleada ni de la siguiente, y dejarlos marcados como "omitido" —
nunca seguir de largo asumiendo que un fallo aislado no importa.

R4b. EL SISTEMA DEBE permitir marcar un cliente de `priv/sistemas.json`
con una `version_fijada` (tag de imagen, opcional, default ausente) —
un cliente con este campo presente nunca es elegible (R2) aunque su
imagen actual sea distinta a la de `stable`, hasta que alguien lo
quite a mano editando ese mismo archivo. Confirmado con el usuario
(30-09-2026): ningún cliente real lo necesita hoy — se construye el
campo igual, sin nadie marcado.

## 4. Motivo y aprobación (vía GitHub, sin mecanismo propio)

R8. EL SISTEMA DEBE exigir, para disparar una propagación a
producción, un motivo o ticket no vacío — mismo criterio de campo
obligatorio que ya usa cualquier formulario de este proyecto.

R9. EL SISTEMA DEBE requerir la aprobación de una segunda persona antes
de tocar cualquier cliente — implementado con una **"environment
protection rule"** de GitHub Actions (revisores obligatorios) sobre un
ambiente llamado `clientes`, configurado en el repo de GitHub, nunca
con un mecanismo de aprobación construido a mano en esta app. El run
del workflow queda en estado "Waiting" hasta que alguno de los
revisores configurados lo aprueba desde la propia web de GitHub.

R10. EL SISTEMA (GitHub, no esta app) YA IMPIDE nativamente que quien
disparó el run sea quien lo apruebe — comportamiento documentado de
GitHub Actions para ambientes con revisores obligatorios, no un
chequeo que haya que construir. Esta spec no reimplementa esa
validación.

R10a. EL SISTEMA DEBE pedir, antes de disparar el run (R9), que quien
lo solicita escriba a mano el nombre EXACTO de cada cliente
seleccionado (un campo de texto por cliente, en cualquier orden,
comparado como conjunto) — más estricto que una sola palabra fija:
protege también contra confirmar sin querer un conjunto de clientes
distinto al que se quiso seleccionar.

## 5. Registro (archivo, no tabla — ver §1.1)

R11. EL SISTEMA DEBE agregar una línea a un archivo de registro
solo-agregar en el servidor (`/var/lib/metadata/propagaciones.jsonl`,
una línea JSON por intento, formato a definir en `02.design.md`) al
solicitar una propagación (canal o producción) — motivo, clientes
elegidos con su oleada, quién la disparó. Nunca se edita ni se borra
una línea ya escrita.

R12. EL SISTEMA NO DEBE duplicar en este registro nada que ya se pueda
consultar en vivo de otra fuente confiable: qué imagen corre HOY en
cada cliente sigue siendo siempre k3s vía `imagen_actual/2` (nunca un
valor cacheado en el registro), y el progreso/resultado de una corrida
puntual vive en el propio log del run de GitHub Actions (nunca
replicado línea por línea en el archivo) — mismo principio que
R9a/R11a de `SPEC-ARQ-1809202603`.

## 6. Decisiones

- **Disparo: SSH/`gh` shelleado, igual que hoy — NO se agrega acceso
  directo a la API de Kubernetes en esta spec.** Queda con la MISMA
  limitación ya documentada en `SPEC-ARQ-1809202603` R9c (el propio
  prototipo la muestra como aviso en pantalla): solo funciona
  disparado desde una laptop de desarrollador con `gh`/SSH
  configurados, nunca clickeando desde la URL de un sistema ya
  desplegado. Motivo: darle a la propia app permiso de Kubernetes
  (ServiceAccount) es una decisión de infraestructura que excede esta
  spec — se resuelve sola, más adelante, sin romper nada de lo que se
  construye acá.
- **La pantalla es una extensión de `PropagacionLive`, la que YA
  existe** (`SPEC-ARQ-1809202603` R9) — no una pantalla nueva aparte.
  Se le agrega el botón "Propagar a clientes →" en la tarjeta de
  `stable` y el diálogo de selección múltiple; el resto de la pantalla
  (línea de tiempo, estado de canales) no cambia.
- **También existe un equivalente por terminal**
  (`mix motor.propagar_extension_a_produccion`, ver `02.design.md`)
  — mismo criterio que el resto de la familia `motor.*`, que siempre
  ofrece CLI además de (o en vez de) pantalla.
- **No se agrega ventana de horario permitida.** La aprobación por
  GitHub (R9) ya es el freno humano — alcanza por ahora.
- **Los respaldos de BD por cliente no se purgan automáticamente** —
  mismo criterio que ya usa `mix motor.baja` (queda manual, sin límite
  ni fecha de vencimiento). Se revisita si el espacio en disco del
  servidor se vuelve un problema real.

## 7. Fuera de alcance

- Todo lo ya resuelto por `SPEC-ARQ-1809202603` (propagar
  `unstable→testing→stable`, un solo cliente a la vez, idempotencia,
  selección de commit, rollback de código/BD, pantalla de línea de
  tiempo) — esta spec no lo repite, lo reusa.
- Oban, y cualquier motor de jobs nuevo (ver §1.1).
- Notificaciones por correo o WhatsApp (ver §1.1) — la notificación de
  aprobación pendiente ya la manda GitHub nativamente a los revisores
  del ambiente `clientes`.
- Ventanas de mantenimiento (§6, rechazado por ahora).
- Acceso directo a la API de Kubernetes / ServiceAccount (§6,
  pendiente).
- Cualquier cambio al menú "Plataforma" (Ambientes de Deploy/Panel
  Control/Propagación existentes) — conversación aparte, sin spec
  todavía.
