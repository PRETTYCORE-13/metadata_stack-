# SPEC-SYS-1709202603 — Baja de Sistema

**Documento:** Guía de uso · Grupos A-B, 100% verificados en real
(2026-09-21).

## 1. Objetivo

Dar de baja un sistema completo (base de datos, aplicación en k3s, DNS,
Caddy, y su registro) con un solo comando — con respaldo automático de
la base y confirmación explícita antes de borrar nada.

## 2. ¿Quién utiliza esta funcionalidad?

El equipo de Desarrollo, desde terminal (`mix motor.baja`), con el repo
clonado y credenciales SSH del ambiente cargadas en
`/sysadmin/ambientes` (mismo requisito que `mix motor.alta`). No tiene
pantalla dedicada — solo terminal.

## 3. Conceptos que debo conocer

- Solo se puede dar de baja un sistema que esté registrado en
  `priv/sistemas.json` (un cliente real dado de alta) — nunca un canal
  de plataforma (`unstable`/`testing`/`stable`).
- El respaldo de la base sale SIEMPRE, sin pedirlo aparte — es el
  primer paso, antes de tocar cualquier otra cosa.
- La confirmación pide escribir el nombre EXACTO del sistema — no
  alcanza con un "sí"/Enter.

## 4. Guía paso a paso

### 4.1 Dar de baja un sistema

```
mix motor.baja <ambiente> <sistema>
```

Ejemplo real:

```
mix motor.baja Metadata crm
```

El comando muestra qué va a borrar y pide confirmación:

```
Vas a dar de baja "crm" por completo:
  - su base de datos (db_crm)
  - su Deployment/Service/Secret en k3s
  - su registro DNS y su bloque en Caddy
  - su entrada en priv/sistemas.json

Este paso es IRREVERSIBLE -- la base de datos se borra sin backup automático.

Escribí el nombre del sistema ("crm") para confirmar:
```

Escribiendo `crm` y Enter, corre todo en orden: respaldo → k3s → base →
DNS/Caddy → registro → verificación final. Cualquier otra respuesta
cancela sin tocar nada.

Si se corta a mitad de camino (una falla de red, por ejemplo), correr
el mismo comando de nuevo retoma donde quedó — no hay que limpiar nada
a mano ni preocuparse por duplicar pasos.

### 4.2 Dónde queda el respaldo

En el servidor, en `/home/elixir/backups/db_<sistema>_<timestamp>.sql`
— un archivo SQL plano por cada baja, con fecha y hora en el nombre.

### 4.3 Restaurar un respaldo (procedimiento manual, sin automatizar)

1. Recrear la base vacía:
   ```
   sudo k3s kubectl exec -n metadata-stack aws-postgres-0 -- psql -U appuser -d postgres -c 'CREATE DATABASE "db_<sistema>";'
   ```
2. Cargar el respaldo:
   ```
   cat /home/elixir/backups/db_<sistema>_<timestamp>.sql | sudo k3s kubectl exec -i -n metadata-stack aws-postgres-0 -- psql -U appuser -d db_<sistema>
   ```
3. Correr `mix motor.alta <ambiente> <sistema> <imagen>` normal — como
   la base ya existe con todo migrado, el paso de crear la base es
   idempotente y no rompe nada.

**Riesgo real, encontrado verificando esto en vivo**: si pasó mucho
tiempo entre el respaldo y la restauración, el paso de reimportar
catálogos que hace `mix motor.alta` en cada corrida puede chocar con lo
que ya trae el respaldo — no hay garantía de que un respaldo viejo
restaure limpio contra una versión de código mucho más nueva. Cuanto
más reciente el respaldo respecto a la restauración, menor el riesgo.

## 5. Lo que todavía no cubre

- No hay una forma automática de restaurar — el procedimiento de
  arriba es manual.
- No hay ninguna salvaguarda extra para un sistema con datos reales de
  producción, más allá de la confirmación de nombre (R3) y el respaldo
  automático (R7).
- Un sistema con infraestructura real pero cuya alta se cortó antes de
  registrarse en `priv/sistemas.json` no se puede limpiar con este
  comando — hay que borrarlo a mano (ver `02.design.md` §4).
