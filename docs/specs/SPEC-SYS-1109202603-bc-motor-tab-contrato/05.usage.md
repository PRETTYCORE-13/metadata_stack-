# SPEC-SYS-1109202603 — BC Motor: Tab Contrato

**Documento:** Guía de uso · Grupos A-E, 100% verificados (documentación
retroactiva, 2026-09-11).

## 1. Objetivo

Consultar, para un catálogo ya armado en el Motor BC, la documentación
completa y siempre actualizada de su API: qué direcciones existen, qué
hay que mandar, y cómo se ve la respuesta — generada automáticamente a
partir de la configuración real, nunca escrita a mano.

## 2. ¿Quién utiliza esta funcionalidad?

Principalmente gente técnica (de ADN, de plataforma, o de un equipo
externo) que necesita integrar un sistema con la API de un catálogo
puntual, desde el Motor BC (`/sysadmin/bc-list/:tabla/motor` → tab
"Contrato").

## 3. Conceptos que debo conocer

- El tab es 100% derivado: no hay ninguna documentación guardada
  aparte — se recalcula completa en cada visita a partir de los campos,
  estados y transiciones reales del catálogo, así que nunca puede
  desactualizarse.
- Un catálogo "detalle" no tiene su propio tab Contrato — su
  documentación (cómo consultar sus renglones, cómo se arman al dar de
  alta o transicionar) vive en el tab Contrato de su catálogo maestro.
- La transición de alta (la que crea un registro nuevo) nunca aparece
  como una acción aparte — corre automáticamente al crear el registro.

## 4. Flujo general

1. Abrir el tab Contrato de un catálogo que no es detalle.
2. Revisar las tarjetas de lectura (listado y un registro puntual), y —
   si tiene catálogos detalle — las de sus renglones.
3. Revisar la tarjeta de alta (y, si aplica, la variante de alta en
   lote).
4. Revisar una tarjeta por cada transición configurada (si el catálogo
   todavía no tiene ninguna, el tab lo dice explícitamente).

## 5. Guía paso a paso

### 5.1 Consultar los endpoints de lectura

1. Entrar al tab Contrato del catálogo.
2. Las primeras tarjetas siempre documentan consultar el listado
   completo y un registro puntual, con un ejemplo de respuesta armado
   con datos ficticios coherentes con los campos reales.
3. Si el catálogo tiene catálogos detalle, aparece además una tarjeta
   por cada uno para consultar sus renglones, con una nota de que el
   filtro acepta cualquier campo real del detalle, no solo el que
   identifica al registro maestro.

### 5.2 Consultar el endpoint de alta

1. La tarjeta de alta muestra el body de ejemplo — si el catálogo
   tiene detalles, incluye una lista de renglones de ejemplo (siempre
   dos por cada detalle, para dejar claro que no hay límite fijo).
2. Si existe una variante de alta en lote (varios registros en un
   mismo request), aparece en una tarjeta aparte, con un ejemplo
   deliberadamente distinto (sin renglones por item) para no confundir
   "cuántos registros" con "cuántos renglones tiene cada uno".
3. Si el catálogo tiene una transición de alta configurada, aparece un
   aviso aclarando que corre automáticamente dentro de este mismo
   endpoint.

### 5.3 Consultar los endpoints de transición

1. Si el catálogo tiene al menos una transición (además de la de
   alta), aparece una tarjeta para consultar las transiciones
   disponibles desde el estado actual de un registro puntual.
2. Aparece una tarjeta por cada transición normal, con su body de
   ejemplo separado por dueño real (campos del encabezado sueltos,
   campos de cada detalle agrupados bajo "renglones"), y la respuesta
   de ejemplo mostrando cómo queda el registro después de esa
   transición (ya en el estado destino).

## 6. Ejemplos prácticos

### Ejemplo: catálogo sin ningún catálogo detalle

Las tarjetas de lectura y alta no muestran ninguna llave de renglones —
el ejemplo es el mismo de siempre, sin agregar nada extra.

### Ejemplo: transición que no edita ningún campo del encabezado pero sí puede mover renglones

La descripción de esa tarjeta aclara explícitamente que, aunque no
edite ningún campo propio, sí puede mover renglones de un catálogo
detalle — el ejemplo de renglón muestra solo el identificador del
renglón, sin más campos.

## 7. Casos comunes

- **"No encuentro el Contrato de un catálogo detalle"** — no existe
  como tab propio; su documentación está en el tab Contrato de su
  catálogo maestro.
- **"¿Por qué no hay un endpoint separado para la transición de
  alta?"** — porque un registro recién creado nunca tiene un estado
  asignado todavía, así que ese endpoint siempre fallaría; la
  transición de alta corre sola dentro del POST de creación.
- **"El catálogo no muestra ninguna tarjeta de transición"** — todavía
  no tiene ninguna transición configurada; el tab lo indica con un
  texto explícito en vez de una sección vacía.

## 8. Errores y situaciones especiales

- El campo `id` siempre aparece primero en cualquier ejemplo JSON
  (tanto en el nivel raíz como dentro de cada renglón) — es una
  decisión de presentación para que el ejemplo se lea con la
  convención habitual de una API REST.
- Los ejemplos de un registro nunca muestran `estado_id` como campo
  editable directo — el único camino documentado para cambiar de
  estado es una transición.
- Cada tarjeta usa un color distinto según el método (consultar en
  azul, crear en verde, modificar en ámbar, eliminar en rojo) para
  identificar de un vistazo qué tipo de acción es.

## 9. Resultado esperado

El tab Contrato muestra, sin necesitar tocar nada, una tarjeta por cada
acción real disponible sobre el catálogo — coincidiendo siempre con lo
configurado en el tab Configuración (campos, estados, transiciones) en
ese momento, porque se recalcula en cada visita.
