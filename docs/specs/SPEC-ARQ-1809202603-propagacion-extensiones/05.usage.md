# SPEC-ARQ-1809202603 — Propagación de Extensiones (CORE)

**Documento:** Guía de uso · Grupos A-H, 100% verificados en real
(2026-09-21).

## 1. Objetivo

Mover una versión ya construida del núcleo (CORE) de un escalón de
confianza al siguiente (`unstable → testing → stable`), o aplicarla
directo a un cliente — desde terminal o desde una pantalla dedicada,
sin necesitar reconstruir nada ni arriesgar un reinicio innecesario.
También permite volver atrás (rollback) si una versión trae un
problema.

## 2. ¿Quién utiliza esta funcionalidad?

El equipo de plataforma. Hay dos caminos, con distinto requisito de
acceso:

- **Terminal (`mix motor.*`)**: cualquiera con el repo clonado y
  credenciales SSH del ambiente cargadas en `/sysadmin/ambientes`.
- **Pantalla `/sysadmin/propagacion`**: restringida a usuarios
  `super_admin` (gate `sysadmin_propagacion`) — aparece en el grupo
  "plataforma" del menú administrativo.

No es una funcionalidad para usuarios de negocio de los sistemas
cliente.

## 3. Conceptos que debo conocer

- **Canal**: `unstable`, `testing` o `stable` — los tres escalones de
  confianza, en ese orden. `unstable` recibe un deploy automático en
  cada push a `main`; los otros dos se mueven a mano.
- **Cliente**: un sistema real listado en `priv/sistemas.json` (hoy,
  `ennova`).
- **Versión**: el hash corto de un commit de git — no hay un esquema
  de versión aparte, el tag de cada imagen YA es el hash del commit.
- **"Nunca saltar Testing"**: no se puede propagar `unstable → stable`
  directo, ni aplicar a un cliente algo que no pasó por `stable`
  primero. La única excepción es `unstable`, que no tiene "origen"
  (nace del build automático).

## 4. Flujo general

1. Un cambio se pushea a `main` → CI lo construye y lo deploya solo a
   `unstable`.
2. Cuando ese commit se valida ahí, se propaga a `testing` (a mano).
3. Cuando se valida en `testing`, se propaga a `stable` (a mano).
4. Cuando `stable` tiene la versión deseada, se aplica a un cliente
   puntual (a mano, siempre explícito).

En cualquier paso: si el destino YA está en la versión pedida, el
sistema avisa y no hace nada (nunca reinicia de más). Y en cualquier
paso se puede, en vez de tomar "lo último", elegir un commit puntual
del historial — útil cuando lo más reciente en `unstable` todavía no
terminó de validarse.

## 5. Guía paso a paso

### 5.1 Ver qué versión corre en cada lado

```
mix motor.estado_extension <ambiente>
```

Ejemplo: `mix motor.estado_extension Metadata`. Muestra, en una sola
corrida, el hash corriendo en `unstable`/`testing`/`stable` y en cada
cliente. Un destino que no responde (SSH caído, etc.) se muestra con su
propio error, sin ocultar el resto.

### 5.2 Propagar de un canal al siguiente

```
mix motor.propagar_extension <ambiente> <origen> <destino> [--commit=<hash>]
```

Solo dos pares válidos: `unstable testing` o `testing stable`. Pasos:

1. Correr `mix motor.estado_extension <ambiente>` primero, para saber
   qué hash está corriendo en `<origen>`.
2. Si querés propagar exactamente ESE hash: `mix motor.propagar_extension
   <ambiente> <origen> <destino>`, sin flag.
3. Si querés un commit puntual distinto al que corre ahora en
   `<origen>` (ej. `unstable` ya recibió commits más nuevos sin
   validar): agregar `--commit=<hash>` — se valida contra el registro
   de contenedores antes de aplicar nada; si el hash no existe como
   imagen construida, se rechaza con un mensaje claro, nunca dispara
   nada a ciegas.
4. El comando confirma el disparo y da el link al run de GitHub
   Actions para seguir el progreso.

### 5.3 Aplicar una versión ya promovida a un cliente

```
mix motor.propagar_extension_a_sistema <ambiente> <sistema> <imagen>
```

`<imagen>` siempre completa (`ghcr.io/prettycore-13/metadata_stack:<hash>`)
— el workflow del otro lado valida además que sea EXACTO lo que corre
ahora en `stable`; si no coincide, lo rechaza (ningún cliente puede
terminar con algo que no pasó por los tres canales).

### 5.4 Desde la pantalla, sin terminal

**Requisito previo (R9c, 2026-09-22)**: la línea de tiempo de commits
necesita la variable de entorno `GITHUB_TOKEN_LECTURA` configurada en
ese ambiente — un token de GitHub de **solo lectura**
(`contents:read` + `actions:read`). Sin ella, la pantalla muestra un
error explícito en vez de la línea de tiempo (nunca una lista vacía
silenciosa). Vale tanto para `mix phx.server` local como para un
sistema ya desplegado — antes de esta corrección, la pantalla solo
funcionaba corriendo en la máquina de un desarrollador (con `git`/`gh`
instalados); ahora funciona igual en ambos casos.

**Los botones "Propagar..."/"rollback" siguen sin funcionar abiertos
desde un pod ya desplegado** (fuera de alcance de R9c, ver
`01.requirements.md` §6) — para disparar una propagación real, seguir
usando `mix motor.propagar_extension` por terminal, o abrir esta
pantalla desde una máquina de desarrollador.

1. Entrar a `/sysadmin/propagacion` (menú "Plataforma", solo
   `super_admin`).
2. Elegir el ambiente en el selector de arriba (si hay uno solo
   registrado, ya viene elegido).
3. Esperar la carga — consulta la API de GitHub + k3s (SSH) en vivo, no
   hay nada guardado de antes.
4. La lista muestra los commits de `main`, más reciente arriba, cada
   uno con: ícono de estado (✓/✗/○), mensaje, hash corto, autor, quién
   disparó el último run (si hubo), y chips con los canales/clientes
   que están parados en ESE commit ahora mismo.
5. Para propagar un commit puntual: click en "Propagar..." de esa
   fila — se abre un selector con los destinos ofrecibles para ese
   commit (respeta "nunca saltar Testing", el mismo commit puede
   ofrecer distintos destinos según dónde ya esté parado). Click en el
   destino → confirmar. **Necesita correrse desde una máquina con `gh`
   instalado y autenticado (ver aviso arriba)**.
6. Para volver atrás: en el chip de un canal/cliente, aparece un ícono
   ↺ ("Volver a la versión anterior") — solo si el commit anterior
   también cumple la regla de predecesor para ESE destino. Confirmar.
   Mismo requisito que el punto 5.

## 6. Ejemplos prácticos

### Ejemplo: ver el estado antes de tocar nada

```
mix motor.estado_extension Metadata
```

```
== canales ==
  stable: ghcr.io/prettycore-13/metadata_stack:latest
  testing: ghcr.io/prettycore-13/metadata_stack:latest
  unstable: ghcr.io/prettycore-13/metadata_stack:latest

== sistemas (priv/sistemas.json) ==
  ennova: ghcr.io/prettycore-13/metadata_stack:latest
```

### Ejemplo: promover un commit puntual de `unstable` a `testing`

```
mix motor.propagar_extension Metadata unstable testing --commit=08fb6260dc4521414377d960bc825e67ce35568f
```

Resultado esperado: el comando valida que exista una imagen con ese
hash, dispara `actualizar-sistema.yml`, y `testing` termina corriendo
exactamente ese commit — confirmable con `mix motor.estado_extension`
después.

### Ejemplo: pedir de nuevo algo que ya está aplicado

```
mix motor.propagar_extension_a_sistema Metadata ennova ghcr.io/prettycore-13/metadata_stack:latest
```

Si `ennova` ya corre exactamente esa imagen, el comando termina así,
sin disparar ningún workflow:

```
"ennova" ya está en ghcr.io/prettycore-13/metadata_stack:latest -- no se disparó ningún workflow.
```

## 7. Casos comunes

- **"¿Por qué no me deja propagar directo a `stable`?"** — la regla
  "nunca saltar Testing" es a propósito: `stable` solo puede recibir
  algo que ya pasó por `testing`. Hay que promoverlo a `testing`
  primero.
- **"El destino no aparece en el picker de la pantalla"** — significa
  que ese commit todavía no está en el canal predecesor necesario (ver
  §3). El picker lo dice explícito ("todavía no está en ningún canal
  predecesor").
- **Un canal/cliente no responde al consultar estado** — no bloquea la
  consulta de los demás; aparece su propio error en su fila.

## 8. Errores y situaciones especiales

- **Hash inválido en `--commit=`**: rechazado ANTES de disparar nada,
  con mensaje claro de que no existe esa imagen en el registro.
- **Rollback de base de datos**: cuando se revierte un canal/cliente y
  hubo migraciones de por medio, el sistema decide solo si puede
  revertir también la base (tabla/columna nueva y vacía) o si necesita
  intervención manual (cualquier `drop`/`modify`/SQL crudo, o datos
  reales ya cargados) — en ese segundo caso, el código SÍ se revierte,
  pero la base queda como responsabilidad manual del administrador,
  con el motivo exacto mostrado en pantalla.
  **Verificado en real (2026-09-21)**: el mecanismo de clasificación y
  el de reversión puntual de la base se corrigieron (dos bugs reales
  encontrados) y se confirmaron de punta a punta contra `testing` —
  migración de prueba → propagar → rollback de código + base, revirtió
  exactamente lo pedido, nada más (ver `03.tasks.md` tarea 38 para el
  detalle completo).

## 9. Resultado esperado

Después de propagar o hacer rollback, confirmar con
`mix motor.estado_extension <ambiente>` (o refrescando la pantalla)
que el destino quedó exactamente en el hash esperado. Un mensaje de
"sin cambios" es un resultado correcto, no un error — significa que ya
estaba en esa versión.

## 11. Versión en el pie de página

Cualquier usuario autenticado ve, junto al "Prettycore 2026" del pie de
página, la versión que corre en ESE sistema puntual: hash corto de
commit + fecha, ej. "a3f9c21 · 21 Sep 2026" — sin necesitar acceso de
plataforma ni terminal. Útil para un diagnóstico rápido ("¿qué versión
tiene este cliente ahora mismo?") sin depender de nadie con acceso
técnico. En dev/local no aparece nada ahí — no hay ninguna imagen de
release corriendo, así que no hay versión real que mostrar.
