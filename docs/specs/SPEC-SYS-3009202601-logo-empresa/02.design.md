# SPEC-SYS-3009202601 — Logo de empresa

**Documento:** Design · **Fase:** ✅ aprobada (2026-09-30).

Requisitos: `01.requirements.md` (R1–R20).

## D1. Almacenamiento: tabla aparte en Postgres (R15, R17, R20)

Tabla nueva `meta_schema_empresa_logo`, una fila por empresa:

| Columna | Tipo | Nota |
|---|---|---|
| `id` | bigserial | |
| `empresa_id` | FK `meta_schema_empresa`, `on_delete: :delete_all` | índice **único** |
| `contenido` | `bytea` | la imagen tal cual se subió (≤ 200 KB) |
| `content_type` | string | `image/png`, `image/jpeg`, `image/webp`, `image/gif` |
| `ancho`, `alto` | integer | leídos del encabezado de la imagen (D4) |
| `tamano_bytes` | integer | |
| `hash` | string | SHA-256 hex del contenido |
| `inserted_at`, `updated_at` | utc_datetime | |

Y en `meta_schema_empresa` una sola columna nueva: `logo_version`
(string, nullable) = primeros 16 caracteres del `hash`. `nil` = sin logo.

**Por qué así:**
- **En Postgres y no en disco:** con varios pods en k3s, un archivo en
  `priv/static` o en un volumen local solo existe en un pod y se pierde
  en el redeploy (R17). En la base, todas las réplicas ven lo mismo y el
  respaldo de la base ya lo incluye.
- **En tabla aparte y no como columna `bytea` de `Empresa`:**
  `UsuarioAuth.hidratar_empresa_activa/2` carga la `Empresa` en **cada
  request/mount** (`obtener_empresa_de_usuario/2`). Con el `bytea` en la
  misma tabla, cada navegación arrastraría hasta 200 KB por conexión.
  Con la tabla aparte, el scope solo trae `logo_version`, unos pocos
  bytes (R15).
- **`on_delete: :delete_all`** cubre el borrado físico. La baja lógica
  (`delete_guid`) la cubre el controller (D3), que ya filtra
  `is_nil(e.delete_guid)` (R20).

Migración: `priv/repo/migrations/<ts>_crear_meta_schema_empresa_logo.exs`
(tabla de plataforma `meta_schema_*`, no `pty_*`, así que no aplica la
regla del prefijo `pty_<tabla>` en el nombre).

## D2. Contexto `MetadataApp.Autenticacion` (R1, R8)

- Schema nuevo `MetadataApp.Autenticacion.EmpresaLogo` (un módulo por
  archivo, `lib/metadata_app/autenticacion/empresa_logo.ex`).
- `Empresa`: agregar `field :logo_version, :string`. **No** va en
  `cast/3` del `changeset/2`: solo lo escribe el contexto.
- `guardar_logo_empresa(empresa, binario)`: valida con D4 y, dentro de
  una `Repo.transaction`, hace un *upsert* de `EmpresaLogo`
  (`on_conflict: {:replace, [...]}`, `conflict_target: :empresa_id`) y
  actualiza `empresa.logo_version` + `update_guid`. Devuelve
  `{:ok, empresa}` o `{:error, motivo}` con un mensaje en español listo
  para mostrar.
- `quitar_logo_empresa(empresa)`: borra la fila y pone
  `logo_version = nil`, en la misma transacción.
- `obtener_logo_empresa(usuario, empresa_id)`: **una sola consulta**
  que junta `EmpresaLogo` con `Empresa` (`is_nil(delete_guid)`) y
  verifica acceso: el usuario pertenece a la empresa
  (`meta_schema_usuario_empresa` vigente) **o** es `super_admin` (para
  la vista previa en `/sysadmin/empresas` de empresas ajenas). Devuelve
  `%EmpresaLogo{}` o `nil`.

## D3. Servir el logo: controller con caché inmutable (R16, R18, R20)

Ruta nueva en el `scope "/"` con `pipe_through [:browser,
:require_authenticated_usuario]` de `router.ex` (junto a
`/sysadmin/importacion/:plantilla_id/descargar`), porque exige sesión
(R18) y es una respuesta binaria que un LiveView no puede entregar:

```
get "/empresas/:id/logo/:version", EmpresaLogoController, :mostrar
```

`EmpresaLogoController.mostrar/2`:
- `obtener_logo_empresa/2` → si es `nil`, o si `:version` no coincide con
  los primeros 16 caracteres de `hash`, responde **404**.
- Si coincide, responde **200** con `content-type` guardado,
  `cache-control: private, max-age=31536000, immutable`,
  `etag: "<version>"` y `x-content-type-options: nosniff` (ya lo pone
  `put_secure_browser_headers` del pipeline `:browser`).

**Por qué la versión va en la URL:** la URL cambia cuando cambia el
logo, así que el navegador puede guardar cada versión para siempre
(`immutable`) y nunca vuelve a pedirla al navegar. La base solo se
consulta la primera vez que un navegador ve una versión nueva (R16).
Es `private` porque el recurso exige sesión y no debe quedarse en una
caché compartida (proxy/CDN).

## D4. Validación del archivo (R2–R4, R7)

Módulo puro `MetadataApp.Autenticacion.ImagenLogo` (sin dependencias
nuevas y sin tocar la base), con `inspeccionar(binario)`:

1. `byte_size > 200_000` → `{:error, "El logo no puede pasar de 200 KB."}`
2. Formato por **bytes mágicos**, no por la extensión (R2):
   - PNG `89 50 4E 47 0D 0A 1A 0A`: ancho y alto en el chunk IHDR.
   - GIF `GIF87a`/`GIF89a`: ancho y alto en los bytes 6–9 (little-endian).
   - JPEG `FF D8 FF`: se recorren los segmentos hasta el primer SOF0–SOF15
     (salvo DHT/JPG/DAC) y se leen alto y ancho.
   - WebP `RIFF....WEBP`: el encabezado `VP8 `, `VP8L` o `VP8X` según la
     variante.
   - Cualquier otro formato, incluido SVG → `{:error, "Formato no
     permitido: usa PNG, JPG, WebP o GIF."}` (R3).
3. Si no se pueden leer las dimensiones (archivo truncado o corrupto)
   → error "La imagen está dañada o incompleta."
4. Devuelve `{:ok, %{content_type, ancho, alto, tamano_bytes,
   aviso_proporcion}}`, con `aviso_proporcion` en `true` cuando
   `ancho / alto < 2` o `> 6` (R7). Es un aviso, no un error.

La validación vive en el servidor: el `accept:` del input es solo una
comodidad del explorador de archivos, porque cualquiera puede renombrar
un archivo.

## D5. Pantalla `/sysadmin/empresas` (R1, R4–R8)

En `EmpresasLive`, dentro del modal "Editar" que ya existe (mismo
permiso que renombrar, R1):

- `allow_upload(:logo, accept: ~w(.png .jpg .jpeg .webp .gif),
  max_entries: 1, max_file_size: 200_000, auto_upload: true,
  progress: &handle_progress_logo/3)`. Es el mismo patrón que ya usa
  `CatalogoLive` con `:archivo_importacion`.
- Un archivo de más de 200 KB lo rechaza el propio upload con
  `:too_large` **antes de subirlo** (R4), y se muestra el mensaje en
  español.
- Al completarse la subida (`handle_progress_logo/3`, entrada `done?`),
  se hace `consume_uploaded_entry` y se pasa el binario por
  `ImagenLogo.inspeccionar/1`:
  - Si es válido, se guarda **temporalmente** en el assign
    `:logo_pendiente` (`%{binario, content_type, ancho, alto,
    aviso_proporcion}`, ≤ 200 KB, se libera al guardar o cerrar el
    modal) y se muestra la **vista previa** como `data:` URI dentro del
    mismo componente de la top bar (D6), para que se vea idéntica (R6).
    Si `aviso_proporcion`, se muestra "Se verá más chica de lo ideal"
    (R7).
  - Si es inválido, se muestra el error y no se asigna nada.
- La vista previa sale de los bytes **ya validados en el servidor**, no
  del archivo local del navegador. Así, lo que se ve es exactamente lo
  que se va a guardar.
- Botones (con IDs para tests): `#logo-empresa-guardar` →
  `guardar_logo_empresa/2`; `#logo-empresa-quitar` (solo si la empresa
  ya tiene logo) → `quitar_logo_empresa/1`. Si el usuario edita su
  **empresa activa**, se recarga la página (`push_navigate` a la misma
  ruta) para que su top bar muestre el cambio de inmediato.
- Texto de recomendación fijo junto al campo (R5).
- En la tabla de empresas, una columna "Logo" con la miniatura (vía la
  URL de D3) o "—".

## D6. Top bar (R9–R14)

En `MenuLayout.sidebar/1` se agrega el assign `:logo_empresa_url`,
calculado de `current_scope.empresa_activa` sin consultas extra: si
`logo_version` no es `nil`, `"/empresas/#{id}/logo/#{logo_version}"`,
y si no, `nil`. Cambiar de empresa activa ya re-hidrata el scope, así
que el logo cambia solo (R13).

Componente de función `logo_empresa/1` (en `menu_layout.ex`, reusado por
la vista previa de D5):

```heex
<span :if={@src} class="pc-topbar-logo-caja">
  <img src={@src} alt={@nombre} class="pc-topbar-logo-empresa" />
</span>
```

Va dentro de `.pc-topbar-brand`, antes de `.pc-topbar-empresa`. Si no
hay logo, no se genera nada y la top bar queda igual que hoy (R11).

CSS en `assets/css/menu.css` (reemplaza la regla `.pc-topbar-logo`, que
hoy no usa nadie, porque el logo del sistema se movió al sidebar):

```css
.pc-topbar-logo-caja {
  display: inline-flex; align-items: center; justify-content: center;
  height: 32px; max-width: 160px; flex-shrink: 0;
  box-sizing: border-box; border-radius: 6px;
}
.pc-topbar-logo-empresa {
  display: block; max-height: 100%; max-width: 100%;
  width: auto; height: auto; object-fit: contain;
}
/* Contenido oscuro (tema invertido: ver comentario de :root). */
:root[data-theme="light"] .pc-topbar-logo-caja {
  background: #f8fafc; padding: 3px 6px;
}
.pc-topbar-brand { min-width: 0; }
.pc-topbar-empresa {
  min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap;
}
```

- **Nunca se deforma (R9):** `max-height`/`max-width` con `width/height:
  auto` + `object-fit: contain` conservan la proporción; la caja solo
  pone el límite.
- **La altura no cambia (R10):** la caja mide siempre 32 px, que cabe
  en la fila actual (≈30 px de contenido + 6 px de padding arriba y
  abajo), y no depende de la imagen.
- **Tema oscuro (R12):** el fondo claro redondeado solo se aplica cuando
  el contenido es oscuro, que en este sistema es `data-theme="light"`
  (ver el comentario de `:root` en `menu.css`). Dentro de los 32 px, el
  padding le deja al logo 26 px de alto.
- **Celular (R14):** la caja tiene `flex-shrink: 0` y el nombre tiene
  `min-width: 0` + `text-overflow: ellipsis`, así que el nombre cede
  primero. Se revisa junto con la regla de `@media` que ya existe para
  `.pc-topbar` (`menu.css` ~l.1750).
