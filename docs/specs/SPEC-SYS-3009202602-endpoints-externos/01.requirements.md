# SPEC-SYS-3009202602 — Endpoints Externos

**Documento:** Requisitos · **Fase:** 🟡 borrador (2026-09-30).

Notación EARS. §1-§5 describen lo que **ya existe** (desde el
2026-08-06, con el nombre "Acciones externas"), verificado contra el
código el 2026-09-30. §6-§10 son lo **nuevo**.

Términos:

- **Credencial externa**: dirección base y llave de un sistema externo.
- **Endpoint Externo**: una llamada configurada a la API de un sistema
  externo, que usa una credencial externa.
- **Ejecución**: cada vez que un Endpoint Externo se llama.

## 1. Credenciales externas (existente)

R1. EL SISTEMA DEBE permitir al sysadmin de plataforma dar de alta,
editar y dar de baja credenciales externas, con nombre, sistema externo,
dirección base y llave.

R2. EL SISTEMA DEBE guardar la llave cifrada y NUNCA volver a mostrarla
después de capturarla. CUANDO se edita una credencial y el campo de la
llave se deja vacío, EL SISTEMA DEBE conservar la llave anterior.

R3. EL SISTEMA DEBE mostrar, por credencial, la fecha de su última
ejecución, el último error y un resumen de ejecuciones con falla de los
últimos días.

## 2. Definición de un Endpoint Externo (existente)

R4. EL SISTEMA DEBE permitir al sysadmin de plataforma dar de alta,
editar y dar de baja Endpoints Externos, cada uno con: nombre (la
clave con que se llama), etiqueta, credencial, método (GET, POST, PUT,
PATCH o DELETE), dirección, encabezados, cuerpo, orden y "pedir
confirmación antes de ejecutar".

R5. EL SISTEMA DEBE permitir usar en la dirección, los encabezados y el
cuerpo marcadores que se sustituyen al ejecutar: `{campo}` por el valor
de ese campo del registro, `{api_key}` por la llave y `{base_url}` por
la dirección base de la credencial.

R6. Un Endpoint Externo PUEDE pertenecer a un catálogo o a ninguno.
CUANDO pertenece a un catálogo, EL SISTEMA DEBE registrar
automáticamente el permiso "ejecutar_<nombre>" sobre ese catálogo,
negado por defecto hasta que se conceda a un rol.

R6.1. **Agregado 2026-09-30, decisión del usuario.** Un Endpoint
Externo sin catálogo se conserva y se usa solo programando: desde las
reglas de cualquier BC que necesiten un dato o una acción de un sistema
externo, en todos los ambientes (developer y productivos). EL SISTEMA
DEBE permitir que una regla lo llame por su nombre, sin importar el
catálogo del registro. Hoy no es posible: la llamada por nombre solo
busca dentro del catálogo del registro (hallazgo al revisar el código).

## 3. Ejecución desde la ficha (existente)

R7. CUANDO un Endpoint Externo pertenece a un catálogo, EL SISTEMA DEBE
mostrarlo como botón en la ficha de los registros de ese catálogo, solo
a quien tenga su permiso "ejecutar_<nombre>".

R8. CUANDO el Endpoint Externo pide confirmación, EL SISTEMA DEBE
preguntar antes de ejecutarlo, nombrando el sistema externo.

R9. CUANDO el usuario presiona el botón, EL SISTEMA DEBE ejecutarlo sin
congelar la pantalla y mostrar el resultado: correcto o no, el código
de respuesta y el contenido que regresó el sistema externo.

## 4. Ejecución desde el proceso de negocio (existente)

R10. EL SISTEMA DEBE permitir que una regla posterior a un cambio de
estado ejecute un Endpoint Externo del catálogo del registro, por su
nombre, dentro del mismo guardado: CUANDO la regla lo trata como
error, EL SISTEMA DEBE revertir el cambio de estado completo.

R11. Hoy esto exige programar la regla a mano; ningún catálogo real lo
usa todavía (solo existe en pruebas automáticas).

## 5. Registro de ejecuciones (existente)

R12. EL SISTEMA DEBE registrar cada ejecución con: Endpoint Externo,
catálogo y registro, quién la pidió (usuario o proceso), si fue
correcta, código de respuesta, error y duración, y mostrar las últimas
ejecuciones de cada Endpoint Externo.

R13. Límite conocido: CUANDO la ejecución ocurre dentro de un guardado
que termina revirtiéndose, su registro también se pierde.

## 6. Nombre (nuevo)

R14. EL SISTEMA DEBE llamar a esta funcionalidad **Endpoints Externos**
en la pantalla, en el menú y en los mensajes, en lugar de "Acciones
externas". La dirección de la pantalla cambia de forma acorde y la
anterior DEBE redirigir a la nueva.

## 7. Guardar datos de la respuesta (nuevo)

R15. EL SISTEMA DEBE permitir configurar, por Endpoint Externo, un
**mapeo de respuesta**: una lista de pares "dato de la respuesta →
campo del registro", donde el dato se indica por su ruta dentro del
JSON (por ejemplo `data.uuid`).

R16. CUANDO se configura el mapeo, EL SISTEMA DEBE ofrecer solo campos
reales del catálogo del Endpoint Externo y rechazar un campo que no
exista.

R17. CUANDO una ejecución responde correctamente y tiene mapeo, EL
SISTEMA DEBE escribir esos datos en el registro, convertidos al tipo
del campo. CUANDO un dato no viene en la respuesta o no se puede
convertir, EL SISTEMA DEBE tratar la ejecución como fallida, sin
escribir ningún dato parcial, y decir cuál dato falló.

R18. CUANDO la ejecución ocurre dentro de un cambio de estado, EL
SISTEMA DEBE escribir los datos dentro de ese mismo guardado. CUANDO
ocurre desde el botón de la ficha, EL SISTEMA DEBE guardarlos
respetando las mismas validaciones y el mismo control de edición que
cualquier otro guardado del registro.

R18.1. **Decisión del usuario, 2026-09-30 (opción A, respetar el
estado).** CUANDO un Endpoint Externo tiene mapeo de respuesta, EL
SISTEMA DEBE mostrar su botón en la ficha solo si, en el estado actual
del registro, se pueden editar todos los campos de su mapeo. Así nunca
se llama al sistema externo para después no poder guardar el resultado.
Un Endpoint Externo sin mapeo conserva el comportamiento de R7. Para
obtener un dato en un estado donde no se edita (por ejemplo un pedido
cerrado), se modela una transición propia.

R19. EL SISTEMA DEBE permitir usar un Endpoint Externo desde un cambio
de estado **sin programar**, eligiéndolo en la configuración de la
transición, en lugar de escribir la regla a mano (R11).

## 8. Rechazar con el mensaje del sistema externo (nuevo)

R20. EL SISTEMA DEBE permitir configurar, por Endpoint Externo, una
**condición de rechazo** además del código de respuesta: una ruta del
JSON y el valor que significa "no" (por ejemplo `valido = false`), y la
ruta del mensaje a mostrar (por ejemplo `razon`).

R21. CUANDO la respuesta cumple la condición de rechazo, EL SISTEMA
DEBE tratar la ejecución como fallida y mostrar al usuario el mensaje
del sistema externo. Si la ejecución es parte de un cambio de estado,
ese cambio no se guarda.

## 9. Respuesta en el registro de ejecuciones (nuevo)

R22. EL SISTEMA DEBE guardar en el registro de ejecuciones lo que se
mandó y lo que respondió el sistema externo, recortado a un tamaño
máximo, y mostrarlo en el detalle de cada ejecución.

R22.1. EL SISTEMA DEBE conservar el registro de ejecuciones **30 días**
y depurar automáticamente lo más antiguo (decisión del usuario,
2026-09-30).

R23. EL SISTEMA NUNCA DEBE guardar la llave de la credencial en el
registro de ejecuciones, ni en lo mandado ni en la dirección.

R24. EL SISTEMA DEBE conservar el registro de ejecuciones aunque el
guardado que lo originó se revierta (resuelve el límite de R13).

## 10. Ejecución en segundo plano (nuevo)

R25. EL SISTEMA DEBE permitir marcar un Endpoint Externo para ejecutarse
**en segundo plano**. CUANDO lo dispara un cambio de estado, EL SISTEMA
DEBE ejecutarlo solo después de que el cambio quede guardado, sin hacer
esperar al usuario ni retener recursos de la base mientras responde el
sistema externo.

R26. CUANDO una ejecución en segundo plano falla por tiempo, conexión o
error del servidor externo, EL SISTEMA DEBE reintentarla un número
limitado de veces, con espera creciente entre intentos. CUANDO se
agotan, EL SISTEMA DEBE dejarla como fallida y visible en el registro
de ejecuciones, con opción de reintentar a mano.

R27. CUANDO una ejecución en segundo plano responde y tiene mapeo, EL
SISTEMA DEBE guardar los datos en el registro sin volver a disparar el
cambio de estado que la originó.

R28. Un Endpoint Externo en segundo plano NO PUEDE tener condición de
rechazo (R20): el cambio de estado ya se guardó y no hay nada que
rechazar.

R29. CUANDO un Endpoint Externo se ejecuta dentro de un cambio de
estado (no en segundo plano), EL SISTEMA DEBE limitar su tiempo de
espera a un máximo corto, para no retener conexiones de la base con
volumen alto.

## 11. Fuera de alcance

- Autenticaciones distintas a llave en encabezado o dirección (OAuth,
  certificados de cliente).
- Transformar la respuesta con lógica (cálculos, condiciones
  complejas): el mapeo solo copia datos.
- Llamadas en lote de muchos registros a la vez.
- **Sincronización masiva** (traer catálogos completos de otro sistema,
  por ejemplo productos o precios cada noche): SPEC futura, pendiente de
  dimensionar (volumen, frecuencia, paginación de la API externa y qué
  hacer con registros que dejan de venir).
- Unificar esta pantalla con Endpoints en una sola consola de API: se
  trata aparte.

## 12. Preguntas abiertas

Todas resueltas el 2026-09-30:

1. Botón de la ficha con mapeo: respeta el estado (R18.1).
2. Retención del registro de ejecuciones: 30 días (R22.1).
3. Endpoints Externos sin catálogo: se conservan, solo programando
   (R6.1).
