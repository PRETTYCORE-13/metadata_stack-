# SPEC-SYS-1109202606 — BC Motor: Tab Lista

**Documento:** Requirements · **Fase:** ✅ aprobada (2026-09-11) — documentación retroactiva + 1 fix real (R14, código muerto eliminado, ver `03.tasks.md` Grupo D) + 1 sección completa ELIMINADA (2026-09-12, §5, ver R18 y `03.tasks.md` Grupo E) + 1 requisito nuevo implementado (2026-09-22, R19, checkbox visual para columnas booleanas — ver `03.tasks.md` Grupo F) + 1 bug documentado (2026-10-08, R20 y R4 corregido, casillas de visibilidad sin guardar se pierden al reordenar — ✅ aprobado 2026-10-08, ver `03.tasks.md` Grupo G).

**Alcance de esta spec**: documentar (retroactivo, ya implementado)
el tab **"Lista"** de `BcMotorLive` — todo lo que controla cómo
se ve la tabla de un catálogo cuando el usuario final la abre en
`CatalogoLive` (qué columnas, en qué orden, con qué orden de filas
por default, y si carga todo de entrada o espera un filtro). Sexta
spec del módulo BC Motor.

## 1. Visibilidad del tab

R1. EL SISTEMA DEBE mostrar el tab "Lista" para CUALQUIER
catálogo, incluidos los catálogos detalle — a diferencia de Estados/
Transiciones/Diagrama/Contrato/Permisos, un catálogo detalle SÍ tiene
sus propios campos y su propia vista de tabla (la de sus renglones),
independiente de la de su maestro.

## 2. Columnas del GET — tabla unificada

R2. EL SISTEMA DEBE mostrar, en una sola tabla arrastrable, TODAS las
columnas posibles de este catálogo mezcladas: los campos de negocio
del catálogo Y los campos de control del sistema (ID, Estado, TRN,
Folio, Empresa, Sucursal, Almacén, Unidad de venta, Creado por) — con
una etiqueta de tipo ("Control" o "Negocio") por fila para
distinguirlos, nunca dos tablas separadas.

R3. LOS campos de control "Empresa", "Sucursal", "Almacén" y "Unidad
de venta" DEBEN aparecer en esta tabla únicamente cuando el catálogo
tiene Alcance de Datos activado (ver
`SPEC-SYS-1109202605-bc-motor-tab-permisos-alcance` §4) — esas
columnas no existen físicamente en la tabla si Alcance de Datos nunca
se activó.

R4. CADA fila DEBE tener un checkbox de visibilidad independiente
("¿aparece esta columna en la tabla del usuario final?") — con
atajos "Seleccionar todos"/"Deseleccionar todos" que marcan/desmarcan
todos los checkboxes antes de enviar el formulario. Lo marcado y
todavía no guardado debe sobrevivir a cualquier otra acción de la
misma pantalla (ver R20). *(Corregido 2026-10-08: antes decía "sin
round-trip al servidor por cada uno" — esa decisión es la causa del
bug de R20.)*

R5. EL SISTEMA DEBE permitir reordenar estas filas por
arrastre — el orden combinado (control + negocio mezclados) se
guarda una sola vez por catálogo, independiente del "orden" propio
de cada campo de negocio que se usa en el tab Configuración/Ficha/
contrato de API (dos conceptos de orden separados, sin pisarse).

R6. CUANDO un campo del catálogo es elegible como Parámetro estándar
(según su tipo) o tiene Totales configurables, EL SISTEMA DEBE
ofrecer esos controles en la misma fila de la tabla — comportamiento
documentado en `SPEC-SYS-0209202601-parametros-catalogo`, no repetido
aquí.

R7. EL SISTEMA DEBE persistir TODOS los cambios de visibilidad (de
negocio y de control) en un solo submit — nunca un guardado parcial
donde algunos campos queden con la visibilidad vieja porque el
usuario solo tocó una parte de la tabla.

R20. *(Bug, 2026-10-08, a pedido explícito.)* MIENTRAS haya cambios
de visibilidad sin guardar, CUANDO el usuario reordena filas por
arrastre (R5) o cambia cualquier otro control que se guarda al
instante en esta misma tabla (Parámetro, Acotado, tipo de filtro,
Totales, Default — R6), EL SISTEMA DEBE conservar exactamente las
casillas de visibilidad como el usuario las dejó — nunca regresarlas
a lo último guardado en la base. Esos cambios pendientes solo se
persisten con "Guardar columnas" (R7) y se descartan únicamente si el
usuario sale de la pantalla sin guardar.

Comportamiento actual (el bug): al arrastrar una fila, la tabla se
vuelve a pintar con la visibilidad guardada en la base y se pierde lo
marcado/desmarcado sin guardar — si nunca se había guardado, se ven
todas seleccionadas.

## 3. Orden de resultados

R8. EL SISTEMA DEBE ofrecer, en una sección aparte ("Orden de
resultados"), una lista ordenada de campos que define el orden por
default de las filas — el primero de la lista manda, los siguientes
desempatan, cada uno con su propia dirección (ascendente/descendente)
alternable con un clic.

R9. CADA entrada de esta lista DEBE poder moverse (subir/bajar
prioridad) o quitarse individualmente — sin tener que rearmar la
lista completa desde cero para un solo cambio.

R10. EL usuario final DEBE poder seguir cambiando el orden desde la
propia tabla en cualquier momento — este orden es solo el punto de
partida por default, no una restricción permanente.

## 4. Campos por default

R11. EL SISTEMA DEBE ofrecer un interruptor "Campos por default" —
activado, la tabla trae TODOS los registros y columnas apenas se
abre, sin esperar que el usuario final aplique un filtro o búsqueda
primero.

## 5. Filtros por default — ELIMINADO 2026-09-12 (histórico)

Esta sección completa (R12-R14) documentaba el interruptor "Filtros
por default" — independiente de "Campos por default" (R11), acotaba
la tabla por fecha de alta (`fecha_registro`) apenas se abría, con 6
modos reales (Sin acotar / Fecha actual / Mes actual completo / Mes
actual a la fecha / Año actual completo / Fórmula) más el fix de
código muerto del modo `"rango"` (R14, 2026-09-11).

R18. **Eliminado 2026-09-12, a pedido explícito del usuario.**
Motivo: verificado en vivo contra la base real, NINGÚN catálogo tenía
`filtro_default_fecha_modo` configurado (0 filas) — y la
funcionalidad que R12 ofrecía (acotar por fecha apenas se abre la
tabla) ya está cubierta de forma estrictamente más flexible por
`SPEC-SYS-0209202601-parametros-catalogo`: cualquier campo Fecha de
negocio puede marcarse "es_parametro" con el mismo motor de cálculo
de rangos (`FiltrosDefault.rango_fecha/3`, que NO se tocó — sigue
sirviendo a Parámetros), ajustable por el usuario final, no limitado
a la columna de sistema `fecha_registro`. R12/R13 quedan documentados
arriba solo como registro histórico de lo que existió — no describen
comportamiento actual. Ver `02.design.md` §5 (reescrita) y
`03.tasks.md` Grupo E para el detalle completo del borrado.

## 6. Renderizado de columnas booleanas en la tabla (a pedido explícito, 2026-09-22)

Excepción puntual al alcance de §7: cómo se PINTA un valor booleano en
la tabla del usuario final SÍ queda documentado aquí, aunque sea
`CatalogoLive` quien lo renderiza — porque nace directo de una columna
configurada en este mismo tab ("Lista"), no de una regla general
de formato de `CatalogoLive`.

R19. CUANDO una columna visible (de negocio o de control) es de tipo
booleano, EL SISTEMA DEBE mostrar un control de tipo checkbox
en vez del texto "true"/"false" — marcado si el valor es `true`,
desmarcado si es `false` — puramente visual (no editable desde la
tabla, es un parseo de presentación, no un formulario).

## 6b. Nombre del tab (2026-10-08, a pedido explícito)

R21. EL SISTEMA DEBE nombrar este tab **"Lista"** (antes "Get Config"),
igual en el paso opcional de la barra de avance del Motor y en el tab
equivalente del editor de Consultas SQL. Solo cambia el texto visible:
las llaves internas (`getview`, `get_config`), las funciones
(`panel_get_view`) y las rutas no cambian.

## 7. Fuera de alcance de esta spec

- La **llave de identificación de la Ficha** estuvo en este tab hasta
  2026-10-08; ahora vive en el tab Formulario (SPEC-SYS-1109202607 §6c,
  R17-R20).

- El detalle de Parámetros estándar y Totales por columna
  (`SPEC-SYS-0209202601-parametros-catalogo`).
- Cómo `CatalogoLive` consume esta configuración en tiempo real, con
  la única excepción de R19 (§6) — el resto del renderizado (texto,
  fechas, números, etc.) sigue fuera de esta spec.
